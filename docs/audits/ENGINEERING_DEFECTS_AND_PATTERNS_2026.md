# 📋 РЕЕСТР ДЕФЕКТОВ И ПАТТЕРНОВ ОШИБОК ДЛЯ ПЕРЕДАЧИ ДРУГОМУ AI-АГЕНТУ

Этот документ содержит структурированный список всех критических архитектурных, финансовых, инфраструктурных и логических ошибок, выявленных и устраненных в проекте за **24–25 сентября 2026 года**. Передайте этот список агенту для аудита аналогичной кодовой базы.

## 1. 🗄️ База данных PostgreSQL, MVCC и Транзакции

### 1.1. Внешние сетевые вызовы (HTTP/AI) внутри сериализуемых транзакций (`Transaction Lock Exhaustion`)
* **Суть дефекта:** Внутри `runSerializableTransaction` или `db.$transaction` вызывался внешний HTTP-запрос (в нашем случае — AI-классификатор ссылок `IntelligenceLinkAnalyzer.analyze` с таймаутом до 10 секунд).
* **Последствия:** Транзакция держала строчные блокировки строк PostgreSQL секундами, вызывая каскадные `could not serialize access due to concurrent update (40001)`, очереди блокировок и исчерпание пула соединений.
* **Исправление:** Любой внешний сетевой вызов (API, AI, HTTP, DNS, SMTP, Telegram) **обязан выполняться ДО входа в транзакцию** либо откладываться в фоновую очередь/хук после фиксации (`Deferred Post-Commit Hook`).
* **Как искать:** Поиск вызовов `fetch(`, `http`, `axios`, `ai.`, `redis.` внутри функций-колбэков `$transaction(` и `runSerializableTransaction(`.

---

### 1.2. Transaction Escape: использование глобального `db` вместо транзакционного клиента `tx`
* **Суть дефекта:** Внутри транзакции разработчик или AI случайно вызывал методы глобального синглтона `db.securityEvent.create(...)` или `db.user.update(...)` вместо переданного в колбэк экземпляра `tx`.
* **Последствия:** Операция выполнялась в отдельном независимом соединении вне контекста транзакции. При откате основной транзакции побочный эффект сохранялся (нарушение ACID), а в тестах на моках или при сериализации происходил дедлок.
* **Как искать:** Поиск вхождений `db.` внутри тел `async (tx) => { ... }`.

---

### 1.3. Отсутствие частичных индексов (Partial Indexes) на быстрорастущих очередях
* **Суть дефекта:** Выборки активных заказов (`status IN ('PENDING', 'IN_PROGRESS')`) или тикетов шли по общему индексу `status`, содержащему миллионы архивных записей (`COMPLETED`, `CANCELED`).
* **Последствия:** `Bitmap Index Scan` деградировал до секунд при росте таблицы.
* **Исправление:** Создание частичных индексов PostgreSQL:
  ```sql
  CREATE INDEX CONCURRENTLY idx_orders_active_queue 
  ON "Order" (status, "createdAt") 
  WHERE status IN ('PENDING', 'IN_PROGRESS');
  ```
* **Как искать:** Проверить запросы воркеров и очередей — если они фильтруют по 2-3 активным статусам из 10, необходим partial index.

---

### 1.4. Деградация MVCC из-за дефолтного Autovacuum (`Table & Index Bloat`)
* **Суть дефекта:** В таблицах с постоянными частыми апдейтами балансов (`User`) и статусов (`Order`) скапливались миллионы «мертвых» строк (`dead tuples`). Дефолтный порог автовакуума в 20% (`scale_factor = 0.2`) на таблице в 1 000 000 строк запускал очистку только после 200 000 изменений!
* **Исправление:** 
  1. Установка `fillfactor = 85` на часто обновляемые таблицы (резервирует 15% места на странице под Heap-Only Tuple updates без перезаписи индексов).
  2. Агрессивный автовакуум для горячих таблиц:
     ```sql
     ALTER TABLE "User" SET (autovacuum_vacuum_scale_factor = 0.05, autovacuum_vacuum_threshold = 500);
     ALTER TABLE "Order" SET (autovacuum_vacuum_scale_factor = 0.05, autovacuum_vacuum_threshold = 1000);
     ```

---

### 1.5. Каскадное удаление финансовых и аудиторных записей (`Cascade vs Restrict`)
* **Суть дефекта:** В связях Prisma стояло `onDelete: Cascade` для пользователей к их финансовым комиссиям (`Commission.referrer`) и тикетам (`Ticket.user`). При удалении пользователя или тестовой зачистке удалялся юридический аудит.
* **Исправление:** Замена на `onDelete: Restrict`. Пользователь с финансовой историей не может быть физически удален каскадом — только мягкое удаление (`isDeleted: true`) или анонимизация PII.

---

### 1.6. Недостающие индексы внешних ключей (Foreign Key Unindexed Scans)
* **Суть дефекта:** Поля отношений (`referredById`, `staffRoleId`, `promoCodeId`, `replyToId`, `periodId`) не имели `@index`.
* **Последствия:** При операциях удаления или джойнах PostgreSQL выполнял полный `Seq Scan` родительской таблицы.

## 2. 💰 Финтех, Ledger-First, Балансы и Расчеты

### 2.1. Нарушение принципа Ledger-First (`Мутация до проводки`)
* **Суть дефекта:** Сначала изменялся баланс пользователя `tx.user.update(...)`, и только потом создавалась запись в журнале аудита `tx.ledgerEntry.create(...)`.
* **Последствия:** При сбое валидации, падении БД или конфликте ограничений на шаге создания проводки деньги списывались/начислялись, а запись в леджере отсутствовала.
* **Золотое правило:** **Сначала `tx.ledgerEntry.create()`, затем мутация баланса `tx.user.update()`**.

---

### 2.2. TOCTOU-гонка и уход баланса в минус при списаниях (`Constraint 23514 Crash`)
* **Суть дефекта:** Код читал баланс: `if (user.balance >= amount) { await tx.user.update({ data: { balance: { decrement: amount } } }) }`.
* **Последствия:** Между проверкой и апдейтом параллельный процесс списывал деньги. В БД срабатывал `CHECK (balance >= 0)`, и транзакция падала с сырой ошибкой PostgreSQL `23514 check_violation` вместо контролируемого бизнес-ответа.
* **Исправление:** Атомарное обновление с предикатом достаточности средств:
  ```typescript
  const updated = await tx.user.updateMany({
    where: { id: userId, balance: { gte: absAmountCents } },
    data: { balance: { decrement: absAmountCents } }
  });
  if (updated.count === 0) {
    throw new WalletInsufficientFundsError();
  }
  ```

---

### 2.3. Выход за границы доверия (`Trust Boundary Escape`)
* **Суть дефекта:** В отдельных сервисах (например, при одобрении карантина или бонусов) разработчики делали прямой апдейт баланса: `tx.user.update({ data: { balance: { increment: amount } } })`, минуя единый финансовый шлюз (`WalletOps`).
* **Последствия:** Терялся централизованный аудит, проверка лимитов, проверка мульти-тенантности и защита от двойного начисления.
* **Правило:** Любое движение средств — **строго через централизованный класс/модуль операций** (`WalletOps.credit`, `WalletOps.charge`, `WalletOps.refund`, `WalletOps.quarantineApprove`). Прямые апдейты `balance` в прикладном коде запрещены.

---

### 2.4. Вычисления с плавающей точкой (Floating Point) вместо целочисленных копеек (`BigInt / ExactMath`)
* **Суть дефекта:** Использование `Math.round(amount * percent / 100)` и чисел `Number` для денег.
* **Последствия:** Ошибки округления IEEE 754 (например, `0.1 + 0.2 = 0.30000000000000004`), расхождение дебета и кредита леджера на копейки, накопление финансовой погрешности.
* **Правило:** Все суммы в БД хранятся строго в **копейках/центах целыми числами (`BigInt`)**. Расчеты производятся через целочисленное деление `(amountBigInt * percentBigInt) / 100n`.

---

### 2.5. Недетерминированные ключи идемпотентности (`Date.now() Anti-pattern`)
* **Суть дефекта:** Генерация ключей с текущим временем: `idempotencyKey: 'refund-' + orderId + '-' + Date.now()`.
* **Последствия:** Ключ уникален при каждом перезапуске/повторе! Защита от дублей не работает — при сбое сети повторный вызов списывал или возвращал деньги второй раз.
* **Исправление:** Ключи обязаны быть строго **детерминированными** на основе сущности: `idempotencyKey: \`refund_\${order.id}_\${targetStatus}\``.

---

### 2.6. Отрицательный реферальный баланс при отмене заказа (`Negative Referral Leak`)
* **Суть дефекта:** Заказ выполнен $\to$ рефереру начислен бонус $\to$ реферер вывел деньги $\to$ заказ отменен/возвращен $\to$ система списывает бонус у реферера.
* **Последствия:** Если у реферера на реферальном балансе уже 0, баланс уходил в минус либо операция падала из-за constraint violation, блокируя отмену заказа клиенту.
* **Исправление:** При отзыве комиссии учитывать текущий остаток (`Math.min(currentBalance, commAmount)`) либо явно документировать овердрафт в леджере как отдельную проводку `REFERRAL_REVERSAL`.

---

### 2.7. Ошибочный расчет НДС и порогов УСН (ст. 145 НК РФ)
* **Суть дефекта:** При расчете годового оборота для лимита УСН (20 млн ₽ в РФ с 2026 г.) из входящих платежей вычитались возвраты клиентам.
* **Последствия:** Налоговая база искажалась. По закону порог освобождения от НДС считается **по входящему валовому объему (Gross Revenue)** без уменьшения на сумму возвратов.

---

## 3. 🌐 Мультитенантность и Изоляция Брендов (Multi-Tenancy)

### 3.1. Утечка данных и межтенантный IDOR (`Tenant Bleeding`)
* **Суть дефекта:** 
  1. Поиск реферера по коду: `where: { referralCode }` без `tenantId`. Пользователь регистрировался на сайте А с кодом с сайта Б, и комиссии улетали в чужой бренд.
  2. Оператор сайта А мог изменить баланс клиенту сайта Б (`where: { id: userId }` без проверки `tenantId`).
  3. Создание тикетов саппорта по проблемному платежу создавало тикет без `tenantId`, делая его невидимым для оператора бренда.
* **Исправление:** Любой `findUnique`, `updateMany`, `deleteMany` к пользовательским и финансовым данным **обязан содержать `tenantId`** в селекторе `where`.

---

### 3.2. Хардкод брендов в кодовой базе (`['smmplan', 'flux']`)
* **Суть дефекта:** В фоновых кронах (синхронизация курсов валют ЦБ РФ, оптимизатор цен, сборщик метрик) был зашит массив `for (const tenant of ['smmplan', 'flux'])`.
* **Последствия:** При добавлении третьего сайта (White-Label) для него не обновлялись курсы валют и не пересчитывались тарифы.
* **Исправление:** Динамическая выборка из базы: `const tenants = await db.tenant.findMany({ where: { isActive: true } })`.

---

### 3.3. Разделение пространства имен кэша и очередей Redis
* **Суть дефекта:** Ключи блокировок и кэша хранились глобально: `smart:disabled`, `catalog:categories`.
* **Последствия:** Отключение функции на одном сайте отключало ее на всех сайтах платформы.
* **Правило:** Ключи Redis обязаны включать идентификатор тенанта: `smart:${tenantId}:disabled`, `catalog:${tenantId}:categories`.

---

### 3.4. Изоляция почтовых отправлений и уведомлений
* **Суть дефекта:** Письма клиентам уходили с единого дефолтного домена или с общим шаблоном брендинга.
* **Исправление:** Разрешение почтового адреса отправителя (`fromEmail`), SMTP-настроек и шаблона строго по `tenantId` тикета или заказа.

---

## 4. 📬 Очереди BullMQ, Redis и Фоновые Процессы

### 4.1. Дедлок дедупликации очередей (`Duplicate jobId Deadlock`)
* **Суть дефекта:** Фоновый свипер создавал задачу в BullMQ со статичным ID: `jobId: \`orphan-\${order.id}\``.
* **Последствия:** Если задача уже завершилась или упала и осталась в истории BullMQ, вызов `queue.add()` с тем же `jobId` молча игнорировался! Заказ зависал навсегда.
* **Исправление:** Добавление уникального суффикса: `jobId: \`dispatch-\${order.id}-\${Date.now()}\`` и настройка очистки `removeOnComplete: 100`, `removeOnFail: 500`.

---

### 4.2. Утечка таймеров и Node.js Event Loop (`clearTimeout in Promise.race`)
* **Суть дефекта:** Таймаут запроса к Redis реализовывался через `Promise.race([promise, timeoutPromise])`, где `setTimeout` не очищался при успешном завершении `promise`.
* **Последствия:** При 10 000 запросов в минуту в памяти Node.js оставались десятки тысяч активных дескрипторов таймеров, вызывая утечку памяти.
* **Исправление:** Сохранять ссылку на таймер и вызывать `clearTimeout(timer)` в блоке `finally`.

---

### 4.3. Вечная блокировка задачи при сбое добавления в очередь (`Refill / Dispatch Lock Hang`)
* **Суть дефекта:** Статус заказа или рефилла переводился в `PENDING`/`IN_PROGRESS`, и ставилась Redis-блокировка `order:dispatch_lock`. Затем вызывался `queue.add()`. Если Redis падал или очередь была перегружена, транзакция прерывалась, но блокировка в Redis оставалась висеть 2 часа!
* **Исправление:** При ошибке постановки в очередь — явный откат статуса в `ERROR` и атомарное удаление блокировки в блоке `catch`. При ручном перезапуске заказа оператором — обязательный сброс блокировки.

## 5. 🛡️ Безопасность, Секреты и Аудит

### 5.1. Неасинхронный вызов аудита (`Fire-and-forget auditAdmin`)
* **Суть дефекта:** В Next.js Server Action или API роуте вызов `auditAdmin({ action: 'REFUND', ... })` делался без `await`.
* **Последствия:** В Serverless/Node.js рантайме после возврата ответа процесс может немедленно заморозиться или завершиться. Сетевой запрос на запись лога в БД обрывался, и аудит терялся.
* **Правило:** Любой аудит действий с деньгами или доступом **обязан вызываться с `await auditAdminAwaitable()`**.

---

### 5.2. Утечка PII и секретов в логах (`Scrubbing & Redaction`)
* **Суть дефекта:** В журнал логов (`SecurityEvent`, `TelegramErrorLog`) сохранялись полные дампы тела запросов и стектрейсы, содержавшие токены провайдеров, пароли, номера телефонов и API-ключи.
* **Исправление:** Внедрение обязательного перехватчика очистки данных (`redactSensitiveTokens`), заменяющего `Bearer ...`, `apiKey`, `password`, `connectionString` на `[REDACTED]`.

---

### 5.3. ReDoS (Regular Expression Denial of Service)
* **Суть дефекта:** Полиномиальные регулярные выражения для парсинга email и ссылок социальных сетей (с вложенными квантификаторами `(a+)+`).
* **Последствия:** При подаче специально сформированной строки парсер зависал на 100% CPU одного ядра на десятки секунд.
* **Исправление:** Замена на детерминированные линейные выражения и ограничение длины входящей строки `input.slice(0, 2048)` до применения regex.

---

## 6. 🌐 Сетевая Надежность и HTTP-Запросы

### 6.1. Зависание `fetch` без `AbortSignal.timeout`
* **Суть дефекта:** Внешние HTTP-запросы к API платежных шлюзов, поставщиков услуг и Telegram вызывались стандартным `fetch(url, options)` без сигнала отмены.
* **Последствия:** Если удаленный сервер зависал или удерживал TCP-сокет без ответа, процесс Node.js держал соединение открытым неограниченно долго, исчерпывая сокеты и вызывая тайм-аут всего шлюза.
* **Правило:** Каждый исходящий сетевой вызов обязан иметь **явный таймаут**:
  ```typescript
  fetch(url, { signal: AbortSignal.timeout(5000), ... });
  ```

---

### 6.2. Таймауты сокетов в SMTP-клиентах
* **Суть дефекта:** `nodemailer` конфигурировался без `connectionTimeout` и `socketTimeout`.
* **Последствия:** При сетевой фильтрации (ТСПУ / блокировки провайдеров) отправка письма зависала на 15 минут, блокируя воркер почты.
* **Исправление:** Явные параметры `connectionTimeout: 10000`, `greetingTimeout: 10000`, `socketTimeout: 15000`.

---

## 7. 🧩 Архитектура Кода, Prisma Schema и Server Actions

### 7.1. Обращение к несуществующим полям схемы Prisma (`Phantom Fields via 'any'`)
* **Суть дефекта:** В коде и тестах использовались поля, которых физически не было в `schema.prisma` (например, `user.status`, `ticket.closedAt`, `order.cost`, `order.refillStatus`, `promoCode.tenantId`).
* **Почему пропускалось:** Из-за приведений типов `as any` или spread-операторов `...(order.tenantId ? { tenantId: order.tenantId } : {})` компилятор TypeScript молчал, но в рантайме Prisma падала с ошибкой: `Unknown argument 'tenantId'`.
* **Исправление:** 
  1. Внедрение AST-сканера для полного запрета использования `any` в кодовой базе.
  2. Использование типизированных фабрик сущностей (`createTestUser`, `createTestOrder`).

---

### 7.2. Сырые `throw new Error` в Next.js Server Actions
* **Суть дефекта:** В Server Action выбрасывалось исключение: `throw new Error('Неверный статус')`.
* **Последствия:** В production-режиме Next.js глушит сообщение об ошибке в целях безопасности и возвращает неинформативное: `An error occurred in the Server Components render`, ломая интерфейс пользователя.
* **Правило:** Server Actions обязаны возвращать типизированный контракт `{ success: boolean, error?: string, data?: T }` и оборачивать логику в `try/catch`.

---

### 7.3. Drip-Feed Floor Инвариант в чекауте и B2B API
* **Суть дефекта:** При заказе накрутки с растягиванием по времени (Drip-Feed: $Q$ — общее количество, $N$ — число запусков) проверялось только общее количество $Q \ge \text{minQty}$.
* **Последствия:** Клиент заказывал 100 подписчиков на 10 запусков (по 10 шт в запуск). Поставщик имел минимальный лимит 50 шт на заказ. Заказ принимался, деньги списывались, но при отправке поставщик отклонял каждый транш с ошибкой `Quantity less than minimum`.
* **Инвариант:** Обязательная валидация на этапе приема:
  $$\left\lfloor \frac{Q}{N} \right\rfloor \ge \text{minQty}$$
