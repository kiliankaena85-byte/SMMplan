# 🧠 FinTech Support Balance UX & Cognitive Ergonomics (15-Year Best Practices)

Этот скилл аккумулирует золотые стандарты и методологии проектирования операторских финансовых интерфейсов от мировых финтех-гигантов (**Stripe, Shopify, Revolut, Amazon CS, Linear**) и исследований **Nielsen Norman Group** по предотвращению когнитивных сбоев (*Slips vs. Mistakes*).

---

## 1. 🛑 Анатомия ошибок оператора (Human Factors)

При работе с балансом клиентов оператор службы поддержки находится в условиях когнитивной перегрузки (параллельные чаты, спешка, стресс). В 94% инцидентов ошибочных списаний/начислений виноват не оператор, а плохой дизайн формы:

| Тип ошибки | Описание | Причина в плохом UI | Защитный механизм (Anti-Slip) |
| :--- | :--- | :--- | :--- |
| **Slip (Промах / Автопилот)** | Хотел начислить, но случайно списал (или нажал не ту кнопку). | Использование одного поля со знаком минус (`-100`) или одинаковых кнопок. | **Explicit Direction Toggle**: жесткое переключение сегмента `[➕ Начислить]` / `[➖ Списать]` с изменением цвета и текста кнопки. |
| **Mistake (Ложная модель)** | Не понял, сколько станет на балансе после комиссии или списания. | Отсутствие расчета «на лету». | **Live Math Projection**: блок `Было: 500 ₽` $\to$ `Операция: -142 ₽` $\to$ `Станет: 358 ₽`. |
| **Double-Click (Задвоение)** | Дважды нажал Submit из-за задержки сети. | Отсутствие блокировки и ключа идемпотентности. | **Idempotency Lock + Debounce**: `isPending` блокировка + уникальный UUID запроса. |
| **Context Loss (Опечатка в сумме)** | Ошибся при ручном переносе суммы из заказа в тикете. | Необходимость копировать суммы вручную. | **Predictive Context Chips**: чипы с суммами проблемных заказов клиента в 1 клик. |

## 2. 🏛️ Золотой стандарт интерфейса изменения баланса

### А. Принцип разделения полярности (Polarity Segregation)
❌ **ЗАПРЕЩЕНО:** Просить оператора вводить минус (`-`) для списания. Это главная причина инцидентов.
✅ **ОБЯЗАТЕЛЬНО:**
- Поле ввода суммы **ВСЕГДА строго положительное число** (`> 0`).
- Направление операции выбирается через явный **Сегментированный переключатель (Segmented Control)**:
  - `➕ Начисление (Credit / Бонус)` — Зеленый акцент (`text-emerald-600`, `border-emerald-500`).
  - `➖ Списание (Debit / Коррекция)` — Красный акцент (`text-rose-600`, `border-rose-500`).

### Б. Живой калькулятор проекции (Live Balance Math)
В процессе ввода суммы под полем моментально рендерится уравнение:
```
[ Текущий баланс: 1 250.00 ₽ ]  →  [ + 142.36 ₽ ]  →  [ Итоговый баланс: 1 392.36 ₽ ]
```
Если выбрано списание и сумма превышает баланс:
```
[ Текущий баланс: 50.00 ₽ ]  →  [ - 142.36 ₽ ]  →  ❌ [ Ошибка: Недостаточно средств ]
```

### В. Предиктивные подсказки из контекста (AI / Context-Aware Assistance)
Интерфейс анализирует последние события клиента:
1. **Проблемный заказ:** Если у клиента есть заказ в статусе `FAILED` или `PARTIAL`, выводится кнопка:
   `💡 Заказ #8291 (частично выполнен) — остаток 42.80 ₽` (клик автозаполняет сумму и обоснование).
2. **Последний заказ:** `💡 Последний заказ #9102 (150.00 ₽)`.
3. **Открытый тикет:** Автоматически подставляет `#Тикет 412` в поле обоснования.

### Г. Динамический глагол на кнопке подтверждения
Кнопка действия не должна называться «Отправить» или «Сохранить». Она содержит точный предикат:
- При начислении: `«Начислить +142.36 ₽ на баланс»` (зеленая кнопка).
- При списании: `«Списать −142.36 ₽ с баланса»` (красная кнопка).

## 3. 🛡️ Чеклист верификации для агентов

1. [ ] Поле ввода запрещает ввод отрицательных чисел.
2. [ ] Переключатель направления (Начисление / Списание) визуально контрастен.
3. [ ] Динамическая плашка «Было $\to$ Станет» обновляется на каждый ввод символа.
4. [ ] Кнопка Submit содержит конкретный глагол, сумму и цвет направления.
5. [ ] Присутствуют контекстные чипы для быстрой вставки сумм из заказов.
6. [ ] Поле комментария требует минимум 5 символов и предлагает шаблоны.
7. [ ] Вся транзакция защищена `WalletOps` и `idempotencyKey`.
