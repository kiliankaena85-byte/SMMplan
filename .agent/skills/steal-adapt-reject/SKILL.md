# Steal-Adapt-Reject — матрица решений

## When to activate

- Пользователь принёс референс конкурента и спрашивает «можно ли это использовать»
- После competitor-decode анализа нужно принять решение по каждому элементу
- При brainstorming дизайна с конкурентными референсами
- Клиент просит «сделайте как у X» — нужен структурированный ответ
- Формируется библиотека паттернов с оценками

## КРИТЕРИИ РЕШЕНИЙ

### STEAL — взять напрямую
- Паттерн работает universally (психологический принцип доказан)
- Наш ICP совпадает с ICP конкурента
- Техническая реализуемость ≥ 8/10
- Не противоречит нашему позиционированию

### ADAPT — адаптировать
- Идея верная, но визуальное решение ≠ наш бренд
- Принцип работает, но для другого сегмента — нужна кастомизация
- Частичная реализация достаточна для нашего контекста
- Есть технические ограничения, требующие альтернативы

### REJECT — отклонить
- Противоречит нашей аудитории или стратегии
- Требует ресурсы, которых нет
- Противоречит нашему позиционированию
- Работает ТОЛЬКО в контексте бренда конкурента

## ФОРМАТ ВЫВОДА

Для каждого элемента:

```text
ЭЛЕМЕНТ: [название]
РЕШЕНИЕ: STEAL / ADAPT / REJECT
ОБОСНОВАНИЕ: [почему]
АДАПТАЦИЯ: [если ADAPT — что именно менять]
РИСК: [потенциальная проблема]
PRIORITY: High / Medium / Low
```

## Step-by-step execution protocol

1. **List elements**: Составить список всех элементов из конкурентного анализа
2. **Check ICP fit**: Для каждого — совпадает ли с нашим Ideal Customer Profile
3. **Check brand fit**: Соответствует ли нашему tone of voice и позиционированию
4. **Check feasibility**: Оценить техническую и ресурсную реализуемость
5. **Apply matrix**: Принять решение STEAL / ADAPT / REJECT для каждого элемента
6. **Document**: Зафиксировать обоснование для каждого решения
7. **Prioritize**: Ранжировать STEAL и ADAPT элементы по приоритету
8. **Save to brain/**: Записать решения в `.gemini/antigravity/brain/competitors/`

## Scope boundaries

### DOES
- Принимать структурированные решения по адаптации конкурентных паттернов
- Обосновывать каждое решение с точки зрения ICP, бренда и ресурсов
- Приоритизировать элементы для реализации
- Связывать решения с результатами competitor-decode

### DOES NOT
- Копировать элементы напрямую без анализа (это РЕЖИМ 1 — запрещён)
- Принимать решения без учёта контекста нашего проекта
- Заменять feasibility-check (дополняет его)
- Гарантировать что STEAL-элемент сработает (нужен тест)

## Error handling

| Scenario | Response |
|----------|----------|
| Не хватает данных для решения | Запустить competitor-decode или feasibility-check для недостающих осей |
| Элемент попадает в «серую зону» между ADAPT и REJECT | Классифицировать как ADAPT с пометкой «high risk» |
| Клиент настаивает на REJECT-элементе | Объяснить риски, предложить ADAPT-версию с минимальным риском |
| Противоречивые критерии (бренд — да, ресурсы — нет) | Пометить как «needs decision», показать trade-off клиенту |
