## Глава 2: Мульти-тенантность: SMMplan (B2B) vs SMMflux (B2C) — изоляция ст. 54.1 НК РФ

Архитектура OmniSMM 1.0 построена на строгой модели **Row-Level Tenant Partitioning**:

1. **SMMplan (`smmplan.pro`)**:
   - Назначение: Корпоративный B2B-сегмент (маркетинговые агентства, блогеры, юридические лица).
   - Функционал: Работа по расчетному счету (безналичный расчет с НДС 22%), акты выполненных работ (УПД), детальная табличная аналитика, фильтрация по провайдерам.
2. **SMMflux (`smmflux.ru`)**:
   - Назначение: Розничный высокоскоростной B2C-сегмент.
   - Функционал: Radiant Aurora неоновый дизайн, быстрый чекаут в 3 шага, поддержка гостевых заказов без предварительной регистрации, СБП, мгновенная оплата.

> [!CRITICAL]
> **Изоляция ст. 54.1 НК РФ (Налоговый барьер):**  
> Балансы пользователей, заказы, промокоды и бухгалтерские проводки брендов **SMMplan** и **SMMflux** физически разделены полем `tenantId`. Пользователь SMMflux не имеет доступа к балансу SMMplan, а выручка учитывается раздельно.  
> *Внимание:* Брендов **Lovable** и **SMMboost** не существует. При обнаружении старых ссылок система нормализует `lovable` &rarr; `flux`.

## Глава 3: Сетевой контур, безопасность и официальный туннель Tailscale Funnel

Ввиду блокировок Cloudflare API и cloudflared на территории РФ (сбои TLS handshake ТСПУ):
- **Официальный туннель**: **Tailscale Funnel**.  
  Внешний публичный адрес узла: `https://desktop-25m6el7.tailbb9d28.ts.net`.
- **Внутренний проксинг**: Запросы транслируются на `http://127.0.0.1:3000`.
- **Сетевой биндинг**: Сервер Next.js запускается с `HOSTNAME="0.0.0.0"` и `PORT="3000"`, что гарантирует доступность изнутри контейнеров и через туннели.
- **Stage-контур**: Дополнительный изолированный инстанс тестирования запускается на порту `3005` (`smmplan_stage`). Боевой контейнер (`:3000`) при сборках не затрагивается.

## Глава 4: Переменные окружения (.env) и хранилище секретов AES-256-GCM Vault

Все конфиденциальные данные (ключи эквайринга, токены провайдеров API, SMTP пароли) хранятся в защищенном виде.

### 4.1. Категории секретов:
1. **Системные ключи (.env)**:
   - `DATABASE_URL`: Строка подключения к PostgreSQL (`postgresql://postgres:***@db:5432/smmplan`).

2. **Динамические секреты (AES-256 Vault в БД)**:
   - Ключи YooKassa (ShopID, SecretKey), CryptoBot API Token, Alfa-Bank API, токены провайдеров SMM.
   - В UI и логах секреты маскируются: `sk_live_••••••••3aF9`.
   - Проверка наличия секретов в исходном коде выполняется CI-скриптом: `node scripts/check-bundle-secrets.mjs`.

## Глава 7: Математика P&L: Gross, COGS, Net Profit, комиссия эквайринга, налог УСН

Все расчеты выполняются в целочисленных копейках `BigInt` (ExactMath):

1. **Валовая выручка (Gross Revenue)**:
   $$\text{Gross} = \sum \text{Пополнения балансов через шлюзы} + \sum \text{Прямые оплаты заказов}$$
2. **Себестоимость провайдеров (COGS)**:
   $$\text{COGS} = \sum (\text{ProviderPriceUSD} \times \text{ExchangeRate} \times \text{Quantity} / 1000)$$
3. **Комиссия эквайрингов (Acquiring Fees)**:
   - ЮKassa (карты/СБП): ~2.8% – 3.5%;
   - CryptoBot: ~1.0%;
   - Банковский безнал: 0%.
4. **Налог УСН**:
   - При объекте «Доходы»: $6\%$ от поступившей выручки (либо $1\%$ при региональных льготах).
   - С учетом налоговой реформы 2026 года (ФЗ № 176-ФЗ / 425-ФЗ): при превышении порога **20 000 000 ₽** дополнительно исчисляется НДС по ставке **22%**.
5. **Чистая операционная прибыль (Net Profit)**:
   $$\text{Net Profit} = \text{Gross} - \text{COGS} - \text{Acquiring Fees} - \text{Taxes} - \text{OPEX}$$

---

## Глава 8: Клиентские обязательства (Liabilities) и коэффициент покрытия казначейством

- **Обязательства (Liabilities)**: Суммарный объем неистраченных клиентских средств на внутренних балансах `User.balance`.
- **Казначейские активы (Assets)**: Сумма остатков на расчетном счете в банке + остатки в кабинетах ЮKassa и CryptoBot.
- **Коэффициент финансового покрытия ($K_{cov}$)**:
  $$K_{cov} = \frac{\text{Assets}}{\text{Liabilities}} \times 100\%$$
  - $K_{cov} \ge 120\%$: Абсолютная устойчивость (Зеленая зона).
  - $100\% \le K_{cov} < 120\%$: Нормальная ликвидность (Желтая зона).
  - $K_{cov} < 100\%$: Кассовый разрыв (Красная зона, зажигается P0-алерт владельцу).

## Глава 9: Телеметрия инфраструктуры: очереди воркеров, задержки, статус кэшей

В правом нижнем углу дашборда выводится блок телеметрии очереди BullMQ:

## Глава 11: Жизненный цикл заказа: PENDING -> PROCESSING -> IN_PROGRESS -> COMPLETED/PARTIAL/ERROR

Каждый заказ проходит через строгий конечный автомат (State Machine):

```
                     ┌──────────────┐
                     │   PENDING    │
                     └──────┬───────┘
                            │ (Успешный вызов API провайдера)
                            ▼
                     ┌──────────────┐
                     │  PROCESSING  │
                     └──────┬───────┘
                            │ (Провайдер начал налив)
                            ▼
                     ┌──────────────┐
                     │ IN_PROGRESS  │
                     └──────┬───────┘
        ┌───────────────────┼───────────────────┐
        ▼                   ▼                   ▼
 ┌─────────────┐     ┌─────────────┐     ┌─────────────┐
 │  COMPLETED  │     │   PARTIAL   │     │    ERROR    │
 │ (100% налито)│     │(Сдача клиенту)    │(Сбой шлюза) │
 └─────────────┘     └─────────────┘     └──────┬──────┘
                                                │
                                    (Failover / Retry / Cancel)
```

- **PENDING**: Заказ создан и оплачен клиентом, ожидает отправки воркером.
- **PROCESSING**: Заказ успешно принят шлюзом провайдера, ожидает запуска в соцсети.
- **IN_PROGRESS**: Накрутка запущена, счетчик увеличивается.
- **COMPLETED**: Заказ выполнен в полном объеме.
- **PARTIAL**: Провайдер остановил выполнение (например, из-за лимита соцсети). Система автоматически возвращает деньги за недолитый остаток.
- **ERROR**: Провайдер отклонил заказ (закрытый профиль, неверная ссылка, нехватка баланса). Требуется вмешательство диспетчера.
- **CANCELLED**: Заказ отменен с полным возвратом средств.

## Глава 12: Карточка заказа: лог ответов провайдера, Start Count, Remainder, телеметрия

При клике на заказ открывается модальное окно деталей:
- **Start Count**: Начальное количество подписчиков/просмотров на момент запуска заказа.
- **Remains (Остаток)**: Сколько единиц поставщику осталось докрутить.
- **Лог ответа шлюза (Raw JSON Response)**: Точный ответ удаленного сервера поставщика с кодом HTTP и телом ответа. Позволяет мгновенно определить причину отклонения.

## Глава 13: Аварийный отказ поставщика (Failover): безопасная смена шлюза без списаний

Если заказ упал в статус `ERROR`:
1. Оператор открывает карточку заказа.
2. В блоке «Резервная маршрутизация (Failover)» выбирает альтернативного провайдера, у которого активна аналогичная услуга.
3. Нажимает кнопку **«Применить Failover и отправить»**.
4. **Финансовая защита**:  
   С клиента **не списываются** дополнительные средства. Разница в себестоимости относится на операционные расходы платформы.

## Глава 14: Частичное выполнение (PARTIAL): автоматический расчет сдачи клиенту

Если поставщик закрыл заказ со статусом `PARTIAL` и указал остаток `remains = 300` из 1000:
1. Система вычисляет процент недовыполнения: $300 / 1000 = 30\%$.
2. Сумма сдачи рассчитывается от розничной цены заказа:  
   $$\text{Сумма возврата} = \text{Цена заказа} \times \frac{\text{Remains}}{\text{Quantity}}$$
3. Автоматически создается проводка `LedgerEntry` с типом `REFUND`.
4. Баланс клиента мгновенно увеличивается на сумму сдачи, а в тикетах или Telegram отправляется уведомление.

## Глава 15: Управление гарантийными докрутками (/admin/refills)

- Раздел `/admin/refills` аккумулирует заявки клиентов на восстановление списавшихся показателей.
- Если у услуги заявлена гарантия (например, 30 дней), клиент может нажать «Запросить докрутку».
- Если провайдер поддерживает автодокрутку по API — система вызывает команду `refill`.
- Если автодокрутка отклонена провайдером — заявка попадает оператору со статусом `MANUAL_REVIEW`. Оператор проверяет текущий счетчик и принимает решение: повторить запрос к поставщику либо запустить новый компенсирующий заказ бесплатно.

## Глава 16: Умный Drip-Feed (/admin/smart) и железный инвариант Drip-Feed Floor (minQty)

### 16.1. Математический инвариант Drip-Feed Floor
При разделении крупного заказа на порции (например, 10 000 подписчиков по 500 в сутки в течение 20 дней):
$$\lfloor \text{Общий объем} / \text{Количество запусков} \rfloor \ge \text{service.minQty}$$
- Если объем на один запуск окажется меньше `minQty` услуги поставщика, провайдер вернет фатальную ошибку `Quantity less than minimum`.
- Система на уровне валидатора чекаута и панели `/admin/smart` **жестко блокирует** установку недопустимых параметров, предотвращая потерю заказов.

# ТОМ VI. КАТАЛОГ УСЛУГ, ТАРИФЫ И ЦЕНООБРАЗОВАНИЕ (CATALOG DOMAIN)

## Глава 24: Каталог розничных услуг (/admin/catalog): жесткий стандарт strictly ₽/шт

В административной панели OmniSMM 1.0 действует фундаментальный стандарт:
- **Запрет на умножение на 1000**: Нигде в клиентском UI или админке нельзя писать «Цена за 1000 шт».
- Все расчеты производятся за 1 штуку. Например:
  - Услуга: «Telegram Подписчики Быстрые (РФ 🇷🇺)»
  - Себестоимость поставщика: `$0.80 / 1000 шт` &rarr; при курсе 90 ₽ = `0.072 ₽ / шт`.
  - Розничная цена с наценкой 80%: `0.13 ₽ / шт`.
  - Клиент заказывает 250 шт &rarr; к списанию: `250 * 0.13 = 32.50 ₽`.

## Глава 25: Формула наценки и пакетное управление маржинальностью категорий

В `/admin/catalog` доступна кнопка **«Пакетное обновление наценки»**:
1. Администратор выбирает категорию (например, `ВКонтакте -> Подписчики в сообщество`).
2. Задает желаемую наценку в процентах (например, `+65%`).
3. Система мгновенно пересчитывает розничную цену всех активных услуг в данной категории и сбрасывает кэш витрин в Redis (`catalog-smmplan`, `catalog-flux`).

## Глава 26: Дерево социальных сетей и категорий (/admin/catalog/categories)

Иерархия каталога:
`Социальная сеть (Network)` &rarr; `Категория (Category)` &rarr; `Услуги (Services)`.
- Поддерживается drag-and-drop сортировка позиций в меню витрины.
- Тумблер `Скрыть категорию`: мгновенно снимает с публикации всю категорию без удаления входящих в нее услуг.

## Глава 27: Бесшовное слияние категорий (Category Merge Modal)

При импорте от разных поставщиков могут возникать дублирующие категории.
Для их объединения:
1. Открыть `/admin/catalog/categories`.
2. Нажать иконку слияния на дубликате.
3. Выбрать целевую каноническую категорию.
4. База данных выполняет безопасную миграцию внешних ключей `Service.categoryId = canonicalId`, после чего удаляет пустую категорию-дубль.

---

## Глава 28: Семантическое разрешение TargetType: POST vs CHANNEL (resolveServiceTargetType)

- Поле `Service.targetType` определяет совместимость услуги с типом ссылки:
  - `CHANNEL`: каналы, паблики, группы, профили;
  - `POST`: публикации, фото, видео, клипы, рилс;
  - `STORY`: истории с 24-часовым жизненным циклом;
  - `COMMENT`: комментарии к записям;
  - `POLL`: опросы и голосования.
- **Обязательное правило ядра**: во всех выборках и фильтрах каталога используется функция `resolveServiceTargetType(service)`, которая выводит правильный тип даже при отсутствии явного поля в базе.

## Глава 29: Карантин цен (/admin/catalog/quarantine): порог скачка >30% и защита маржи

- **Порог срабатывания**: если при фоновой синхронизации закупочная цена услуги выросла на $\ge 30\%$, услуга немедленно блокируется и отправляется в карантин (`/admin/catalog/quarantine`).
- Розничная цена для клиентов **не меняется автоматически**, защищая от непредвиденных списаний.
- Администратор обязан изучить причину скачка в карантине: одобрить новый тариф либо переключить услугу на резервного поставщика.

# ТОМ VII. NO-CODE СТУДИЯ ПАТТЕРНОВ ССЫЛОК И БИБЛИОТЕКА REGEX

## Глава 30: Управление паттернами ссылок (/admin/catalog/patterns) и тестовый стенд

Раздел позволяет создавать и тестировать регулярные выражения для валидации клиентских ссылок без программирования. Стенд содержит поле ввода ссылки и моментально подсвечивает результат проверки зеленым или красным индикатором.

---

## Глава 31: Защита от ReDoS (катастрофического возврата регулярных выражений)

- **Опасность ReDoS**: Некорректно составленное регулярное выражение со вложенными квантификаторами `(a+)+` может подвесить процесс Node.js на 100% CPU при обработке специально сформированной ссылки злоумышленника.
- **Встроенный ReDoS-валидатор**: При сохранении паттерна система тестирует его на время выполнения (timeout 50 мс). Если регулярное выражение уходит в циклический возврат, сохранение отклоняется.

# ТОМ VIII. ИНТЕГРАЦИЯ С ПРОВАЙДЕРАМИ API И ИМПОРТ (PROVIDERS DOMAIN)

## Глава 33: Подключение провайдеров API (/admin/providers): параметры, балансы, шифрование

Интеграция с поставщиками по стандартному протоколу SMM API v2:
- **Базовый URL**: эндпоинт поставщика (например, `https://smmpanel.com/api/v2`).
- **Ключ API**: шифруется в Vault по алгоритму AES-256-GCM.
- **Поддерживаемые методы**:
  - `action=services`: получение каталога;
  - `action=add`: создание заказа;
  - `action=status`: проверка статуса;
  - `action=refill`: запуск гарантийной докрутки;
  - `action=balance`: запрос текущего баланса.

---

## Глава 34: Мастер импорта Cherry-Pick (/admin/providers/import): Приоритет №1 администратора

- При ручном сопоставлении категорий в мастере импорта выбор администратора имеет **Приоритет №1**.
- Алгоритмический автоанализатор полностью отключается для выбранных позиций.
- Услуги сохраняются в базу данных ровно с теми привязками, которые указал оператор.

---

## Глава 35: Теневой каталог в Redis (Shadow Catalog) и барьер Zero-Unknown-Platform

- При синхронизации каталога поставщика данные буферизуются в Redis (`provider:shadow:{id}`).
- **Zero-Unknown-Platform Guard**: Если при импорте не удается со 100% гарантией определить соцсеть услуги, она отбраковывается на входе. Запрещено присваивать неизвестным услугам категорию наугад.

---

## Глава 36: Здоровье шлюзов и предохранитель Circuit Breaker (/admin/providers/health)

- **Circuit Breaker** следит за частотой сетевых ошибок поставщика:
  - 5 ошибок подряд &rarr; статус `OPEN` (шлюз изолируется на 5 минут);
  - Через 5 минут &rarr; статус `HALF-OPEN` (пробный единичный запрос);
  - При успехе &rarr; статус `CLOSED` (шлюз возвращается в штатную работу).

# ТОМ IX. ФИНАНСЫ, КАЗНАЧЕЙСТВО И БАНКОВСКИЙ БЕЗНАЛ (FINANCE DOMAIN)

## Глава 38: Бухгалтерский журнал двойной записи LedgerEntry (/admin/transactions)

Журнал проводок — фундамент финансовой безопасности:
- Поля записи: `id`, `userId`, `tenantId`, `type`, `amount` (копейки), `balanceBefore`, `balanceAfter`, `idempotencyKey`, `orderId`, `createdAt`.
- Запрет Transaction Escape: внутри финансовых транзакций используется строго переданный контекст `tx.*`. Использование глобального `db.*` блокируется линтером.

## Глава 39: Казначейство (/admin/finance/treasury): счета, остатки на шлюзах, курсы ЦБ РФ

- Единый экран для сверки балансов эквайрингов (ЮKassa, CryptoBot) и расчетного счета компании.
- Кнопка **«Синхронизировать курс ЦБ РФ»**: запрашивает официальный XML-курс доллара с сайта Банка России и обновляет параметр `exchangeRateUSD` с фоновым пересчетом себестоимости.

## Глава 40: Заявки на пополнение баланса (/admin/finance/balance-requests): безнал B2B

1. B2B-клиент загружает платежное поручение.
2. Бухгалтер сверяет поступление суммы по банковской выписке.
3. Нажатие «Одобрить»: средства зачисляются через `WalletOps.credit()`, статус заявки переходит в `COMPLETED`.

---

## Глава 41: Монитор подозрительных операций и антифрод (/admin/fraud-monitor)

Система антифрода автоматически переводит в карантин транзакции со следующими признаками:
- Пополнение баланса на сумму $> 50 000$ ₽ с новой банковской карты;
- Более 5 неудачных попыток ввода карт подряд с одного IP;
- Массовая регистрация аккаунтов с одинаковыми платежными реквизитами.

---

## Глава 42: Маркетинг и промокоды (/admin/marketing): скидки (DISCOUNT) vs ваучеры (VOUCHER)

- `DISCOUNT`: Скидка в процентах при оформлении (например, промокод `START2026` на 10%).

# ТОМ XII. РЕГЛАМЕНТЫ АВАРИЙНЫХ СИТУАЦИЙ (DISASTER RECOVERY RUNBOOKS)

## Регламент DR-01: Активация режима аварийных техработ (KillSwitch) и сброс кэшей Redis
1. Открыть `/admin/settings` &rarr; секция «Техническое обслуживание».
2. Включить рубильник «Режим техработ» и подтвердить в модальном окне.
3. Витрины мгновенно закрываются баннером 503 Service Unavailable.
4. Выполнить команду сброса кэша:
   ```bash
   npx tsx scripts/flush-redis-cache.ts
   ```
5. После проведения работ выключить тумблер техработ.

## Регламент DR-02: Сбой валидатора ссылок (Link Engine Malfunction)
1. Открыть `/admin/catalog/patterns`.
2. Протестировать проблемную ссылку в No-Code стенде.
3. Сгенерировать исправленный паттерн через встроенный ИИ-помощник Gemini Flash.
4. Нажать кнопку «Сбросить кэш правил валидации».

## Регламент DR-03: Внезапное обнуление баланса провайдера или блокировка API-ключа
1. Зайти в `/admin/providers/health` и выявить отключенный шлюз.
2. В `/admin/orders` отфильтровать заказы со статусом `ERROR`.
3. Применить групповое действие «Массовый Failover на дублирующего поставщика».
4. Пополнить счет поставщика или обновить ключ в Vault.

## Регламент DR-04: Расхождение клиентского баланса и бухгалтерского Леджера
1. Запустить проверочный скрипт:
   ```bash
   npx tsx scripts/audit-ledger-consistency.ts
   ```
2. При обнаружении математического расхождения открыть карточку клиента.
3. Провести балансирующую корректировку через `WalletOps.adminAdjust()` с обязательным комментарием.

## Регламент DR-05: Конфликт Telegram-поллинга (Error 409 Conflict)
1. Открыть `/admin/settings?tab=telegram`.
2. Нажать «Сбросить вебхук и принудительно очистить очередь».
3. Проверить в диспетчере процессов отсутствие дублирующего инстанса бота.

## Регламент DR-06: Экстренная изоляция скомпрометированного аккаунта сотрудника
1. Открыть `/admin/settings/team`.
2. Нажать кнопку «Разжаловать до USER» напротив аккаунта сотрудника.
3. Система мгновенно отзывает все активные сессии сотрудника в Redis и закрывает доступ к административной панели.
