# 👥 Скилл: Synthetic Grill Focus Group 2.0 (gsd-grill-focus-group)

## Назначение
Этот скилл предназначен для интерактивного «допроса» (Grill-интервью) и всесторонней критики архитектурных решений, планов внедрения (PLAN.md / implementation_plan.md) и UI/UX дизайнов силами **продвинутой синтетической фокус-группы**. 

Вместо того чтобы задавать неудобные вопросы создателю или пользователю, скилл запускает симуляцию 5–7 экспертных ИИ-персон с выраженными OCEAN-профилями, которые жестко тестируют предложенный план на прочность. Скилл заземляет их на реальные боли клиентов из базы поддержки, организует изолированные раунды ответов (Sequential Isolation) для борьбы с конформизмом, проводит аудит качества симуляции (Critic Pass) и размечает высказывания тегами (открытое кодирование).

> [!NOTE]
> Скилл полностью автоматизирует процесс `/grill-me`, избавляя пользователя от когнитивной нагрузки и выдавая готовые Actionable Hypotheses и карту минимизации рисков.

## When to use
- **При получении нового плана внедрения:** Для жесткой верификации до начала кодинга.
- **При возникновении спорных UI/UX вопросов:** Когда нужно проверить дизайн-систему или доступность на соответствие WCAG AAA.
- **Перед выпуском релиза (Preflight):** Чтобы проанализировать потенциальные аварийные ситуации, гонки данных, рассинхронизацию воркеров и edge-cases.

## Вызов
`/gsd-grill-focus-group [путь к файлу плана или текст технического предложения]`

## Научный фундамент и Модель (2026)
- **Engine (КРИТИЧНО):** Скилл выполняется исключительно с использованием наиболее актуальной модели **gemini-3.5-flash** в соответствии с общим ИИ-контрактом проекта.
- **Методология:** Качественные фокус-группы (Р. Мертон, С. Белановский), Grounded Theory (кодирование кодовыми тегами), метод «Адвоката Дьявола» (Devil's Advocacy), анализ Edge-Cases (FMEA), поведенческий анализ (NNGroup, PersonaCite), Anti-Sycophancy протоколы.
- **Позиционирование:** Интеллектуальный фильтр первого уровня (Quality Gate V1) перед выносом изменений на реальный билд или ревью.

## Ограничения синтетических критиков (ОБЯЗАТЕЛЬНО ЗНАТЬ)
1. **Отсутствие физического опыта:** Персоны не запускают код в браузере, а оценивают его логически и концептуально.
2. **Склонность к вежливости (Sycophancy):** ИИ по умолчанию стремится соглашаться. Данный скилл содержит форсированные установки деструктивного анализа для борьбы с соглашательством.
3. **Контекстные рамки:** Группа видит только те файлы и планы, которые ей переданы, или к которым у агента есть доступ через инструменты чтения.

## Scope boundaries
### Что делает этот скилл:
- Анализирует технические и архитектурные планы.
- Заземляет персон на структуру жалоб из `src/actions/support/ticket.ts`.
- Симулирует 5-7 ИИ-персон с выраженными OCEAN-профилями и полярными групповыми ролями.
- Проводит изолированную симуляцию интервью с оценкой эмоций (Chain-of-Feeling).
- Делает аудит качества симуляции модератором (Critic Pass).
- Проводит кодирование высказываний и генерирует Actionable Hypotheses.
- Проверяет соблюдение строгих стандартов проекта (Next.js 16, React 19, Tailwind 4, HeroUI v3).

### Чего этот скилл НЕ делает:
- Не вносит изменения в исходный код (не кодит).
- Не запускает юнит-тесты или тесты сборки (для этого есть `gsd-preflight-check`).
- Не заменяет реальные интервью с живыми пользователями (является лишь экспертной симуляцией).

## 🤖 State Machine (Инструкция для ИИ-Агента)

### STATE 1: CONTEXT & RAG-LITE GROUNDING (Заземление контекста)
- **1.1 Изучение предложения:** Агент считывает переданный план (например, `implementation_plan.md` или `PLAN.md`) с помощью `view_file` или парсит переданный текст.
- **1.2 RAG-Lite Grounding:** Агент **ОБЯЗАН** заземлить фокус-группу на реальные боли. Агент читает `src/actions/support/ticket.ts` с помощью `view_file`, чтобы понять формат поддержки, и вычленяет типичные боли СНГ SMM-клиентов (например: "деньги списались, подписчиков нет", "заказ висит в Pending", "не распознает ссылку на канал", "цены в UI не сходятся с балансом").
- **1.3 Архитектурный Контракт:** Агент сопоставляет план с правилами кодовой базы Smmplan (февраль 2026):
  - Next.js 16.0.10 (Removals, Connection APIs)
  - React 19.0.0 (useActionState, ref prop, use)
  - Tailwind CSS 4.0.0 (CSS-first config, @theme block)
  - HeroUI v3 (dot notation API)
  - Prisma 5 (Singleton, Isolation)
  - Ценообразование: розничная цена в рублях за 1 шт in UI (`pricePerUnitRub`).
  - Маппировка `targetType` in `link-analyzer`.
  - Запрет на `"use server"` в файлах страниц (`page.tsx`).

### STATE 2: SCREENER & PERSONA SYNTHESIS (Скринер и Персоны)
- **2.1 Скринер:** Составить краткий Скринер-фильтр (профессиональный отсев маркетологов и ИИ-сикофантов, проверка содержательного опыта респондентов).
- **2.2 Синтез группы критиков:** Агент генерирует 5–7 синтетических респондентов. Каждая персона — структурированный профиль:
  - **Имя, Возраст, Роль в группе** (Лидер / Молчун / Devil's Advocate / UX Inspector / QA Architect / Арбитражник-практик / Конформист).
  - **OCEAN-профиль** (с максимальным полярным разбросом, не все средние).
  - **Заземление** (конкретная боль, полученная из тикетов или логов в State 1.2).
  - **Установка на честность** (например, для скептика: *"Обязан найти минимум 2 критических изъяна в любом пункте плана"*).

### STATE 3: GUIDE DESIGN (Проектирование Гайда)
Агент составляет Гайд интервью по принципу воронки:
- **I. Вступление (Ice-breaker):** Представление, правила ("нет правильных ответов"), разогревающий вопрос.
- **II. Основная часть (3 блока вопросов):**
  - Блок 1: Архитектурные риски и надежность (failOpen в лимитере, Redis, базы данных).
  - Блок 2: Доступность и UX (WCAG AAA контрастность кнопок, фиксированные размеры чекбоксов).
  - Блок 3: Edge-Cases и Практичность (что будет при сбое сети, увидят ли клиенты популярные платформы).
  - *Правило:* Категорический запрет на наводящие или закрытые вопросы. Использование проективных техник.
- **III. Завершение (Outro):** Финальное слово участников.

### STATE 4: SEQUENTIAL ISOLATION SIMULATION (Симуляция)
- **4.1 Изолированный опрос:** Каждая персона "отвечает" на вопросы гайда последовательно и изолированно, не видя ответов других участников группы на этом раунде.
- **4.2 Chain-of-Feeling:** Ответы начинаются с эмоционального тега: `[Имя] (чувствует: [эмоция]): [текст]`.
- **4.3 Модерация дебатов:** Модератор сталкивает мнения лбами: зачитывает скептическое мнение Devil's Advocate конформисту и лидеру и просит их отреагировать. Лично обращается к молчунам.

### STATE 5: CRITIC PASS (Проверка Критиком)
Агент переключается в роль строгого Критика и оценивает симуляцию:
- **Sycophancy Check:** Не согласились ли ИИ-персоны слишком быстро?
- **Depth Check:** Были ли ответы поверхностными?
- **Devil's Advocate Check:** Выполнил ли скептик свою разрушительную роль?
- **Knowledge Gap Check:** Было ли додумывание несуществующих фактов?
- *Вывод:* Фиксация 3-4 "красных флагов" симуляции.

### STATE 6: QUALITATIVE ANALYSIS & REPORTING (Анализ и Отчет)
- **6.1 Открытое кодирование:** Каждое ключевое высказывание размечается смысловыми тегами (например, `#speed-over-security`, `#accessible-contrast`, `#fail-open-risk`).
- **6.2 Итоговый отчет:** Агент записывает отчет в `focus_group_report.md` в папке артефактов и выводит пользователю ссылку на него без дублирования текста.

## Step-by-step execution protocol
1. **Считать файл плана:** Используйте инструмент `view_file` для чтения указанного пользователем файла плана.
2. **Провести RAG-Lite заземление:** Прочтите `src/actions/support/ticket.ts` для извлечения реальных болей.
3. **Разработать Скринер, Персоны и Гайд:** Выведите структурированное описание Скринера, 5-7 персон с OCEAN-профилями и Гайда воронки.
4. **Запустить Симуляцию (Раунды 1-3)**: Смоделируйте диалог-критику с изоляцией ответов, эмоциональными префиксами и активной модерацией.
5. **Выполнить Critic Pass**: Напишите краткий отчет о качестве симуляции и красных флагах.
6. **Выполнить кодирование и сгенерировать отчет**: Разметьте результаты тегами, сформулируйте Actionable Hypotheses и запишите отчет в `focus_group_report.md`. Выведите ссылку пользователю.

## Error handling
- **Если файл плана пуст или не найден:** Вывести сообщение об ошибке `"Указанный файл плана не найден. Пожалуйста, предоставьте корректный путь."` и прервать выполнение с кодом `1`.
- **Если обнаружен критический рассинхрон с архитектурным контрактом (например, использование "use server" in page.tsx):** Агент обязан автоматически выставить статус готовности `Red` и заблокировать дальнейшее планирование до исправления ошибки.
- **Если ИИ-персоны соглашаются с планом на 100%:** Применить анти-консенсусный trigger и принудительно перезапустить Раунд 1 с требованием найти 3 фатальных изъяна.
