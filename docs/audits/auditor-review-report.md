## 🔍 Выявленные дефекты и уязвимости

### 1. 🔴 Критический Race Condition при оплате с баланса (Double-Spend / Race-to-Checkout)
* **Проблема**: В `checkoutAction` при использовании `gateway === 'balance'` проверка баланса пользователя происходит на строке 288 (`if (user.balance < finalTotalCents)`). Однако списание средств с баланса происходит позже, внутри вызова `PaymentGatewayFactory.getGateway('balance').createPayment(...)`, который выполняется **ВНЕ** атомарной Prisma-транзакции `db.$transaction` (строка 318).
* **Сценарий атаки**:
  1. Пользователь имеет баланс `1000` копеек.
  2. Пользователь отправляет два параллельных запроса на создание заказа стоимостью `1000` копеек каждый.
  3. Оба запроса одновременно проходят предварительную проверку баланса (строка 288), так как баланс в БД все еще `1000`.
  4. Обе транзакции создания заказов (строка 318) успешно коммитятся, создавая два заказа.
  5. Вне транзакции вызывается списание баланса для обоих заказов, уводя баланс пользователя в `-1000` копеек (овердрафт), либо один из платежей завершается ошибкой, но заказ при этом остается созданным в БД.
* **Решение**: Перенесите списание баланса непосредственно внутрь `db.$transaction`. Списание должно выполняться атомарно с проверкой баланса на уровне БД (SELECT FOR UPDATE аналог в Prisma):
  ```typescript
  // Внутри db.$transaction:
  const updatedUser = await tx.user.update({
    where: { id: user.id, balance: { gte: finalTotalCents } },
    data: { balance: { decrement: finalTotalCents } }
  });
  // Если баланс недостаточен, Prisma выбросит ошибку P2025 (Record not found), и транзакция откатится.
  ```

### 2. 🟠 Нарушение атомарности (ACID) при сбое платежного шлюза
* **Проблема**: Если вызов платежного шлюза `gatewaySvc.createPayment` падает с ошибкой, скрипт выполняет ручной откат (строка 407) через `db.payment.update` и `db.order.update`, переводя их в статусы `CANCELED` и `ERROR` соответственно.
* **Риск**: Эти операции выполняются не в транзакции. Если в момент вызова шлюза или ручного отката произойдет сбой сети, перезапуск контейнера или падение процесса Node.js, БД останется в неконсистентном состоянии (например, заказ останется в статусе `AWAITING_PAYMENT`, хотя платеж по нему не создался, или промокод останется использованным без возможности восстановления).
* **Решение**: 
  - Либо перенесите инициализацию платежного шлюза до транзакции создания заказа (если API шлюза позволяет подготовить платеж без ID заказа в БД).
  - Либо используйте паттерн Saga/Outbox: сохраняйте транзакцию создания заказа, а фоновый воркер пусть обрабатывает отправку в платежные шлюзы и отмену при сбоях.

### 3. 🟡 Уязвимость Race-to-Refund / Double-Credit в `retryCheckoutAction`
* **Проблема**: В `retryCheckoutAction` при проверке статуса YooKassa (строка 506):
  ```typescript
  const isActuallyPaid = await checkYookassaStatusSync(order.payment.gatewayId);
  if (isActuallyPaid) {
    await paymentService.confirmPayment(...);
  }
  ```
  Метод `confirmPayment` вызывается без распределенной блокировки (Mutex) и вне атомарной транзакции проверки текущего статуса платежа.
* **Риск**: Если в этот же миллисекундный интервал придет реальный вебхук от YooKassa, метод `confirmPayment` будет вызван параллельно дважды. Если внутри `confirmPayment` нет строгой проверки `where: { status: 'PENDING' }` при обновлении статуса платежа, баланс пользователя будет пополнен дважды за один и тот же платеж.
* **Решение**: Убедитесь, что внутри `paymentService.confirmPayment` update статуса платежа в БД происходит строго атомарно:
  ```typescript
  const affected = await tx.payment.updateMany({
    where: { id: paymentId, status: 'PENDING' },
    data: { status: 'SUCCESS' }
  });
  if (affected.count === 0) {
    throw new Error("Платеж уже был обработан ранее");
  }
  ```

### 4. 🟢 Архитектурные замечания и Next.js 16
* **Плюсы**:
  - Динамические импорты тяжелых библиотек (`jose`, `notifications`) внутри функций ускоряют Cold Start и оптимизируют оперативную память.
  - Привязка `idempotencyKey` корректно обрабатывает повторные сабмиты форм.
  - Присутствуют проверки на заблокированных пользователей (`user.isActive === false`).
* **Технический долг**:
  - Большое количество комментариев `eslint-disable-next-line` для типов `any` и неиспользуемых переменных (`crypto`, `orderService`). Рекомендуется провести очистку неиспользуемого импорта.
