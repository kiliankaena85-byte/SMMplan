# Регламент реагирования на инциденты безопасности (Incident Response Protocol)

**Документ версии 1.0 — SMMplan Security & SecOps**

---

## 1. Классификация инцидентов и уровни критичности

| Уровень | Описание | Пример инцидента | SLA реакции |
|---|---|---|---|
| **SEV-1 (CRITICAL)** | Компрометация платежных данных, уязвимости с возможностью RCE, утечка мастер-ключей шлюзов | Утечка `YOOKASSA_SECRET_KEY`, утечка `APP_ENCRYPTION_KEY`, несанкционированное зачисление баланса | **<= 15 минут** |
| **SEV-2 (HIGH)** | Утечка API-ключей провайдеров, обход авторизации (IDOR), массовый отказ в обслуживании | Утечка ключей SMM-панелей поставщиков, скомпрометированный токен администратора | **<= 1 час** |
| **SEV-3 (MEDIUM)** | Утечка некритичных данных (логи без секретов), локальный XSS в личной панели | Некорректный рендеринг имени профиля, спам-атака на форму тикетов | **<= 4 часа** |
| **SEV-4 (LOW)** | Мелкие дефекты конфигурации, предупреждения линтеров безопасности | Отсутствие заголовка в статическом ресурсе | **<= 24 часа** |

## 2. Алгоритм реагирования (Step-by-Step)

```
[1. Обнаружение] ──> [2. Локализация (Containment)] ──> [3. Ликвидация] ──> [4. Восстановление] ──> [5. Post-Mortem]
```

### Шаг 1: Обнаружение и оповещение
1. Алерты поступают из систем мониторинга (Loki, Redis rate-limit, Sentry/Pino error logs) или внешней баунти-программы.
2. Дежурный инженер переводит статус системы в режим **SEV Incident Active**.

### Шаг 2: Локализация (Containment)
При компрометации API-ключей или сессий:
1. **API-ключи шлюзов/провайдеров**: Заблокировать ключи в панели провайдера (ЮKassa/CryptoBot/SMM-панели).
2. **Сессии пользователей/админов**: Выполнить сброс всех сессий в Redis (`REDIS_CLI FLUSHDB` или удаление паттерна `session:*`).
3. **Блокировка компрометированного IP**: Добавить IP в бан-лист Nginx / Cloudflare.

### Шаг 3: Ротация секретов (Secret Rotation Protocol)
При утечке секретных ключей среды (`.env`):
1. Сгенерировать новые ключи в безопасном менеджере паролей:
   * `JWT_SECRET`: `openssl rand -hex 32`
   * `APP_ENCRYPTION_KEY`: `openssl rand -hex 32`
   * `CRON_SECRET`: `openssl rand -hex 32`
2. Обновить переменные в серверном `.env` файле и CI/CD secrets.
3. Выполнить перезапуск контейнеров приложения: `powershell ./scripts/deploy-hybrid.ps1` или перезапуск Docker-контейнеров.

### Шаг 4: Ликвидация и сверка данных
1. Провести сверку финансового реестра (Financial Reconciliation):
   * Запустить утилиту проверки балансов: `npm run check-balances`.
   * Проверить несоответствия между логами выплат и фактическими транзакциями БД.
2. Провести откаты несанкционированных транзакций в `WalletLedger`.

### Шаг 5: Анализ и Post-Mortem
В течение 48 часов после ликвидации инцидента составьте Post-Mortem отчёт:
* Причина инцидента (Root Cause Analysis).
* Хронология событий.
* Принятые меры и недопущение повторения.
