# Antigravity — Аудит безопасности PostgreSQL

## Назначение скилла

Antigravity — это рабочий инструмент специалиста по безопасности, который должен
за несколько часов превратить «какую-то» инсталляцию PostgreSQL в проверяемый,
защищённый и комплаенс-готовый объект. Скилл НЕ заменяет полноценный пентест с
активной эксплуатацией — он даёт **детерминированный, воспроизводимый аудит**,
который можно запускать в CI/CD, перед релизом и при расследовании инцидентов.

Скилл построен на методологии **реверс-инжиниринга**: вместо предположения «у нас
всё нормально», мы реконструируем реальное состояние системы из артефактов
(`postgresql.conf`, `pg_hba.conf`, `pg_roles`, `pg_stat_activity`, логов,
образов Docker, манифестов Terraform/K8s) и сверяем его с моделью угроз.

## Когда НЕ применять

- Аудит MySQL/MariaDB, Oracle, MSSQL, SQLite — скилл заточен под PostgreSQL.
- Проектирование БД «с нуля» без существующих артефактов — используй
  `secure_configuration.md` как чеклист, но не запускай аудиторские скрипты.
- Активная эксплуатация (real pentest with payloads against production) — это
  выходит за рамки оборонительного аудита и требует отдельного письменного scope.

## Методология реверс-инжиниринга (4 фазы)

Каждый аудит проходит четыре фазы. Не пропускай фазы — они построены так, что
каждая следующая использует артефакты предыдущей.

### Фаза 1 — Реконструкция (Reconstruction)

Цель: построить точную модель «как оно сейчас работает» из артефактов, а не из
документации (документация часто лжёт или устарела).

Собери эти источники:
1. `postgresql.conf` — основная конфигурация сервера.
2. `pg_hba.conf` — правила аутентификации (кто и как может подключиться).
3. `pg_ident.conf` — маппинг системных пользователей на роли PostgreSQL.
4. Вывод `\du` и `pg_roles` + `pg_authid` — все роли и их атрибуты.
5. Вывод `\dp+` для критичных таблиц + `information_schema.role_table_grants`.
6. `pg_extension` — установленные расширения.
7. `pg_stat_activity` — активные сессии (какие пользователи реально подключены).
8. Логи PostgreSQL (обычно `/var/log/postgresql/` или `pg_log/`).
9. `Dockerfile` / `docker-compose.yml` / Helm chart / Terraform manifest — если
   деплой через IaC.
10. Версия сервера: `SELECT version();` — критично для сопоставления с CVE.

Запуши эти данные в таблицу реконструкции — шаблон в `assets/report_template.md`.

### Фаза 2 — Декомпозиция (Decomposition)

Цель: разбить систему на атомарные компоненты и проверить каждый против
контрольного списка уязвимостей.

Компоненты и их reference-файлы:
| Компонент | Что проверяем | Reference |
|-----------|---------------|-----------|
| Аутентификация | SCRAM/MD5/trust, pg_hba, пароли, brute-force | `references/authentication_security.md` |
| Авторизация | Роли, GRANT, RLS, SEARCH_PATH, PUBLIC | `references/authorization_rls.md` |
| Сеть и TLS | Шифры, сертификаты, открытые порты, MITM | `references/network_tls.md` |
| Расширения | dblink, FDW, plpython, plv8, postgis CVE | `references/extensions_security.md` |
| Файловая система | COPY PROGRAM, lo_import, права файлов | `references/filesystem_os.md` |
| SQL-инъекции | Параметризация, ORM, динамический SQL | `references/sql_injection.md` |
| Конфигурация | postgresql.conf hardening | `references/secure_configuration.md` |
| Контейнер | Docker/K8s образы, секреты, volumes | `references/docker_k8s_security.md` |

### Фаза 3 — Сопоставление с угрозами (Threat Mapping)

Цель: для каждой находки из фазы 2 определить:
- **Класс уязвимости** по CWE / OWASP Top 10.
- **Конкретный CVE** (если применимо) — используй `references/vulnerabilities_database.md`.
- **Вектор атаки** — кто и как может эксплуатировать (внешний атакующий /
  инсайдер / скомпрометированный сервис).
- **CVSS-оценку** и **реальный риск** для данного контекста.
- **Связь с комплаенсом** — какие требования нарушены (см.
  `references/compliance_mapping.md`).

### Фаза 4 — Патч и верификация (Remediation & Verification)

Цель: для каждой находки выдать:
1. **Конкретный патч** — SQL-команда, изменение конфига, обновление пакета.
2. **Анти-пример** — как НЕ надо делать (часто встречающаяся ошибочная «починка»).
3. **Команда верификации** — как проверить, что патч сработал.
4. **Регресс-риски** — что может сломаться при применении патча.

## Порядок действий при вызове скилла

### Шаг 1. Уточни контекст

Если пользователь не указал, спроси (одним сообщением, не растягивая):
- Версия PostgreSQL (`SELECT version();`).
- Среда: on-prem bare metal, Docker, Kubernetes, managed (RDS/Cloud SQL/Azure).
- Есть ли доступ к `pg_hba.conf` и `postgresql.conf` (для managed-БД — нет).
- Цель: аудит / харденинг / расследование инцидента / проверка комплаенса.
- Есть ли репозиторий с SQL-миграциями или кодом приложения — для проверки SQLi.

### Шаг 2. Собери артефакты

Если у пользователя есть доступ к серверу — запусти исполнимые скрипты из
`scripts/` в следующем порядке (всегда только для чтения, ничего не меняем):

1. **`scripts/sql_audit.sql`** — psql-скрипт. Запуск:
   ```bash
   psql -h <host> -U <user> -d postgres -f scripts/sql_audit.sql \
     -v ON_ERROR_STOP=0 > sql_audit_$(date +%F).log 2>&1
   ```
   Скрипт собирает: версии, расширения, роли, привилегии, RLS-политики,
   pg_hba-эффективные правила, небезопасные настройки, последние ошибки в логе.

2. **`scripts/bash_checks.sh`** — проверка файловой системы и конфигов:
   ```bash
   sudo bash scripts/bash_checks.sh > bash_checks_$(date +%F).log 2>&1
   ```
   Проверяет: права на `data/`, наличие `postgresql.conf` и `pg_hba.conf`,
   версию установленного пакета, TLS-сертификаты, открытые порты.

3. **`scripts/python_scanner.py`** — комплексный сканер через psycopg2:
   ```bash
   python3 scripts/python_scanner.py \
     --host <host> --port 5432 --user <user> --database postgres \
     --output json > scan_$(date +%F).json
   ```
   Запускает 30+ проверок и выдаёт структурированный JSON с уровнем риска.

4. **`scripts/iac_linter.py`** — если есть манифесты IaC:
   ```bash
   python3 scripts/iac_linter.py --path ./infra/ --format markdown
   ```
   Проверяет Terraform/K8s-манифесты на небезопасные настройки (public access,
   weak TLS, дефолтные пароли, отсутствующий шифр at-rest).

**Важно**: если у пользователя НЕТ доступа (например, чёрный ящик), переходи
сразу к Фазе 3 — пассивный анализ по тому, что есть (логи, манифесты, код).

### Шаг 3. Прочитай соответствующие reference-файлы

Не пытайся удержать всё в голове. После сбора артефактов:
1. Прочитай `references/vulnerabilities_database.md` — для версии пользователя
   найди соответствующие CVE.
2. Прочитай reference-файлы для компонентов, где найдены находки (см. таблицу
   выше).
3. Для инцидентов — обязательно `references/incident_response.md`.
4. Для комплаенс-аудита — `references/compliance_mapping.md`.

### Шаг 4. Сформируй отчёт

Используй шаблон `assets/report_template.md`. Отчёт должен содержать:

1. **Executive Summary** — 3-5 предложений для нетехнической аудитории.
2. **Методология** — какие фазы пройдены, какие артефакты собраны.
3. **Карта атаки** — диаграмма в Mermaid: векторы от атакующего к активам.
4. **Находки** — каждая в формате:
   - ID (FIND-001)
   - Заголовок
   - Severity (Critical / High / Medium / Low / Info)
   - CWE / CVE
   - Описание уязвимости
   - Доказательство (вывод скрипта / лог / конфиг)
   - Уязвимый код или конфиг (анти-пример)
   - Патч (с конкретной командой)
   - Верификация
   - Комплаенс-нарушения
5. **Дорожная карта исправлений** — приоритизированный список.
6. **Приложения** — полные выводы скриптов.

Сохрани отчёт в `/home/z/my-project/download/antigravity_report_<дата>.md`.

## Принципы написания находок

### Принцип доказательства

Каждая находка должна сопровождаться **воспроизводимым доказательством** —
командой, которую может запустить второй аудитор и получить тот же результат.
«Мне кажется, что тут небезопасно» — НЕ находка. «`pg_hba.conf` строка 5
содержит `host all all 0.0.0.0/0 trust`, что позволяет подключение без пароля
из любого IP; проверка: `grep -n trust pg_hba.conf`» — находка.

### Принцип анти-примера

Для каждого патча показывай **анти-пример** — как часто пытаются «починить» и
почему это не работает. Это критично: 60% «исправлений» SQLi, которые мы видели
на практике, на самом деле не работают (фильтрация кавычек, regex на UNION и
т.д.). Анти-примеры накапливают культурное знание о том, как НЕ делать.

### Принцип минимально-инвазивного патча

Патч должен быть минимальным и обратимым. Не предлагай «переписать всё на RLS»
— предложи:
1. **Hotfix** — что сделать за 5 минут, чтобы закрыть дыру.
2. **Правильное исправление** — что сделать в течение спринта.
3. **Долгосрочное** — архитектурное изменение, если нужно.

## Базовые принципы безопасности PostgreSQL (memorize)

Эти принципы — фундамент. Если в находке нарушен любой из них, это находка:

1. **Least Privilege**: роль приложения должна иметь минимально необходимые
   права. Никогда `GRANT ALL ON *.* TO 'app_user'`.
2. **Defense in Depth**: SSL + pg_hba + роли + RLS + сетевая изоляция. Каждый
   слой должен быть в состоянии остановить атаку.
3. **Fail Closed**: при ошибке аутентификации / авторизации — отказ, не fallback.
   `trust` в `pg_hba.conf` — это fail open.
4. **Audit Everything**: `log_connections`, `log_disconnections`, `log_statement
   = 'ddl'`, pgAudit для DML. Логи — единственный способ обнаружить инцидент.
5. **Secrets Never in Code**: пароли в `~/.pgpass` (chmod 600), env vars с
   секретами в K8s Secrets (не в ConfigMap), Vault для production.
6. **Encrypt at Rest and in Transit**: TLS 1.2+ для соединения, LUKS / dm-crypt
   для диска, `pgcrypto` для колонок с PII.
7. **Patch Promptly**: PostgreSQL minor releases включают security fixes.
   Подписка на pgsql-announce — обязательна.

## Ускоренные сценарии

### Сценарий A: «Быстрая проверка перед релизом» (15 минут)

Используй, когда времени мало. Запусти только:
1. `scripts/sql_audit.sql` (5 минут).
2. Проверь топ-5 самых частых проблем из `references/vulnerabilities_database.md`
   (раздел «Топ уязвимостей по частоте»).
3. Выдай список из 3-5 критичных находок без полного отчёта.

### Сценарий B: «Расследование инцидента» ( forensic )

Следуй `references/incident_response.md`. Последовательность:
1. НЕ ВЫКЛЮЧАЙ сервер — потеряешь volatile evidence в `pg_stat_activity`.
2. Сделай snapshot диска (для анализа файловой системы).
3. Дамп `pg_stat_activity`, `pg_stat_statements`, логов.
4. Ищи индикаторы из `incident_response.md` → раздел «IoC».
5. Только потом — изоляция (firewall, смена паролей, отзыв сертификатов).

### Сценарий C: «Аудит комплаенса» (PCI DSS / GDPR / ФЗ-152)

Следуй `references/compliance_mapping.md`. Для каждого требования фреймворка
выбери соответствующую проверку из скриптов и заполни матрицу соответствия в
`assets/report_template.md` → раздел «Compliance Matrix».

## Финальные указания

- **Не бойся быть длинным в отчёте**. Аудит безопасности — это документ, который
  читают месяцы. Лучше пересказать, чем недосказать.
- **Не выдумывай CVE**. Если не уверен — посмотри в
  `references/vulnerabilities_database.md` или скажи «нет известного CVE для
  этой версии, но поведение соответствует CWE-XXX».
- **Показывай работу**. Включай выводы скриптов в отчёт как code blocks — это
  доказывает, что аудит реально проводился, а не генерировался из головы.
- **Объясняй почему**, а не только что. «Используй SCRAM-SHA-256» — слабо.
  «Используй SCRAM-SHA-256, потому что MD5 уязвим к pass-the-hash и rainbow
  tables, а SCRAM использует challenge-response с солью» — хорошо.

Теперь переходи к нужным reference-файлам и скриптам по мере необходимости.
