### 1.1 Главный вывод

**Контур денег — самая зрелая часть кодовой базы.** Видно наследие нескольких волн аудитов: вебхуки защищены IP-allowlist'ами, HMAC-подписью с `timingSafeEqual`, окном anti-replay, лимитом размера тела, мьютексами и идемпотентностью; подтверждение платежа перепроверяется живым запросом к API шлюза и сверяет суммы до копейки; списания баланса идут через WalletOps с идемпотентными ключами; в чекауте есть защита от IDOR, карантин услуг, лимиты 54-ФЗ и JIT-подтверждения.

## 2. Детальные находки

### CHK-01 [P1] Откат ошибки шлюза не гасит второй заказ media-group

**Симптом.** Клиент оформляет заказ с медиагруппой (два заказа: основная ссылка + последнее медиа, один платёж ×2). Платёжный шлюз падает на `createPayment`. Платёж помечается `CANCELED`, основной заказ — `ERROR`… а **второй заказ остаётся `AWAITING_PAYMENT`** навсегда: он не активируется (платёж отменён), не показывается как ошибка, не попадает ни в один отчёт. Молчаливый зомби в заказах клиента.

**Код** (`src/actions/order/checkout.ts:723-749`):
```ts
const rollbackPromises = [
  db.payment.update({ where: { id: result.paymentId }, data: { status: 'CANCELED' } }),
  db.order.update({ where: { id: result.orderId }, data: { status: 'ERROR', ... } })
  // ← result.secondOrderId не входит в откат
];
```

**Эталон рядом:** `mass.ts` в аналогичной ситуации делает правильно — `db.order.updateMany({ where: { paymentId: result.paymentId }, ... })` гасит ВСЕ заказы платежа.

**Фикс (одна строка по духу):** заменить одиночный `order.update` на `order.updateMany({ where: { paymentId: result.paymentId } })` — как в mass.ts. Плюс тест: чекаут c mediaGroup + падение шлюза → оба заказа `ERROR`, платёж `CANCELED`, промокод возвращён.

### CHK-02 [P2] Guest-путь массовых заказов без passwordHash-щита

**Симптом.** Обычный чекаут защищён: гостю с email существующего аккаунта с паролем — отказ («войдите в аккаунт»). Массовый заказ (оба экшена: `massOrderCheckoutAction` и `structuredMassOrderCheckoutAction`) — **не защищён**: находит пользователя по `email_tenantId` и спокойно вешает на него заказы.

**Следствия:** злоумышленник может (1) замусорить историю заказов жертвы, (2) вызвать письма «заказ оплачен» на чужой email, (3) повлиять на loyalty-метрики/автоматические награды чужого аккаунта (PromoAutomation считает по userId). Захвата сессии нет — `createSession` только для `isNewUser`, но внедрение заказов — реальный вектор.

**Фикс:** перенести блок из `checkout.ts:347-349` в оба guest-пути mass.ts:
```ts
if (user.passwordHash && !session) {
  throw new Error("Этот email уже зарегистрирован. Войдите в аккаунт для оформления заказа.");
}
```
(+ тест: guest mass-order на email существующего парольного аккаунта → отказ.)

### CHK-03 [P2] Demo-payment создаёт реальные платежи без guard'ов

**Симптом.** `createDemoPaymentAction` вызывается страницей `/client-demo` (публичный маршрут). Экшен: без авторизации, без проверки `isTestMode`/`NODE_ENV`, без rate limit — создаёт `Payment(PENDING)` у выбранного шлюза и **реальный** `createPayment` в YooKassa/Robokassa/CryptoBot для пользователя `demo@smmplan.pro`.

**Риски:** (а) в проде работает генератор живых платёжных ссылок на demo-аккаунт — оплата такой ссылки зачислит реальные деньги на баланс demo-пользователя (кто владеет ящиком `demo@…smmplan.pro`?); (б) demo-пользователь создаётся с `passwordHash: "DEMO_USER_NO_PASSWORD"` — магия в данных; (в) метрика платёжных шлюзов замусоривается.

**Фикс:** обернуть экшен в `if (!await SettingsManager.isTestMode() && process.env.NODE_ENV === 'production') throw` (или фичфлаг `client_demo`), убрать hardcoded-пароль (оставить null — гостевой профиль), и проверить, закрыт ли `/client-demo` в проде (CHK-08).

### CHK-04 [P2] Захардкоженный e2e-аккаунт в прод-пути

`mass.ts`, генерация платежа: `isTestMode: isTestMode || user.email === 'e2e-tester@test.com'`. Это прямая тема плана `023-production-test-mode-leakage`: реальная оплата этим email создаст `isTest`-заказ → Ghost Proxy перехватит → деньги собраны, исполнение не пойдёт. Сейчас риск только если ящик под контролем тестировщика, но паттерн «волшебный email в бизнес-логике» — мина при передаче базы/поддержке.

**Фикс:** убрать email-условие; e2e-тестам передавать тестовый режим окружением (`ENABLE_DEV_ROUTES`/`isTestMode` уже есть), а не магической строкой.

### CHK-05 [P2] calculatePriceAction без rate limit

Публичный экшен расчёта цены (витрина, без auth): каждый вызов — `db.service.findUnique` + `marketingService.calculatePrice` (промо, тарифные уровни). Соседние чувствительные экшены лимитированы (`checkoutCore` 15/60, `massCheckoutCore` 5/60, `retryCheckoutCore` 10/60), этот — нет. Поверхность для DB-спама и перебора промокодов калькулятором.

**Фикс:** `await RateLimitService.check("priceCalc", 60, 60, true)` в начале.

### CHK-06 [P3] Legacy-путь в confirmPayment — УТОЧНЕНИЕ ПРИ РЕАЛИЗАЦИИ D1

> **Уточнение при реализации D1:** ветка достижима через retryCheckoutAction; двойного списания нет (взаимоисключение через статус); решение — тест-фиксация вместо удаления.

Ветка «single order» (`payment.orderId`) не достижима для обычных новых заказов: текущие чекауты создают Payment без `orderId` (связь через `Order.paymentId`, активация — корзинной веткой `findMany({ paymentId })`). Однако она достижима через `retryCheckoutAction` (retry создаёт Payment с `orderId`). Двойного списания нет — обе ветки взаимоисключающи: первая переводит заказ в `PENDING`, вторая ищет только `AWAITING_PAYMENT`. Решение D1: тест-фиксация retry-сценария + документирующий комментарий вместо удаления.

## 3. Что сделано хорошо (важные подтверждения)

- **Вебхуки — эталонно.** YooKassa: IP-allowlist официальных диапазонов, HMAC-SHA256 с `timingSafeEqual`, окно свежести 30 минут (anti-replay), лимит 64 КБ, мьютекс `webhook_payment_{id}`, идемпотентность по статусу, алерты SecurityAlertService на каждую аномалию. Robokassa: проверка подписи Password#2 + IP-диапазоны. CryptoBot: HMAC от sha256(token). Общий `confirmPayment`: в проде перепроверка живым запросом к API шлюза (`PAYMENT_NOT_SUCCEEDED`, `PAYMENT_AMOUNT_MISMATCH`), отказ «orphan webhook» без PENDING-платежа, Guard'ы gatewayId/валюты/точной суммы.
- **Сдача зачисляется корректно:** при оплате «минимум 10 ₽» кредитуется полная сумма, списывается `order.charge` — остаток остаётся на балансе (как и обещает текст платежа).
- **Чекаут:** идемпотентность (`idempotencyKey` обязателен для баланса, conflict → возврат существующего заказа), мьютекс на балансе пользователя, откаты промокода с защитой от отрицательных счётчиков, IDOR-щит парольных аккаунтов, кросс-тенантная проверка услуги, карантин/cooldown, JIT-подтверждения, запретный контент, лимит 15 000 ₽ без Telegram (115-ФЗ).
- **Magic-link:** TTL 15 минут, флаг `used`, IP-rate-limits (15/час + alert при брутфорсе), чистка истёкших токенов.
- **Массовые заказы:** пер-заказные идемпотентные ключи (`${key}_order_${idx}`), rate limit 5/мин, корректный откат `updateMany` по paymentId.
