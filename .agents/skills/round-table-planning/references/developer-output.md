# Формат вывода для разработчика

Этот файл описывает, **как модератор презентует план пользователю**. Главный принцип: разработчику не нужен 16-разделочный отчёт — ему нужно готовое проработанное решение, которое он может начать исполнять сразу.

## Принцип

Разработчик открывает чат и хочет увидеть:
1. **Что делать** (суть решения в 1 абзаце)
2. **Какие есть варианты** (1-2 альтернативы с trade-offs)
3. **Пошаговый рецепт** (конкретные действия в порядке исполнения)
4. **Что не пропустить** (критичные моменты)
5. **Где детали** (ссылка на полный план в файле)

Полный план-документ (со всеми разделами: STRIDE, perf budgets, SLO, схема БД и т.д.) **сохраняется в файл** в `/home/z/my-project/download/`, а в чат идёт **короткая выжимка**.

## Принципы написания

### Пиши как рецепт, а не как ТЗ

❌ Плохо: «Спроектировать схему БД для заказа»
✅ Хорошо: «Создай миграцию `0042_create_order_groups.sql` с таблицами `order_groups`, `orders`, `payments`. Поля: id UUID PK, user_id UUID FK, status TEXT CHECK. Индексы: idx_og_user_created на (user_id, created_at DESC).»

Разработчик должен иметь возможность **начать делать** сразу после прочтения, без дополнительных вопросов.

### Конкретика важнее полноты

Если в чате не упомянута какая-то деталь (например, точный тип поля) — это OK, она есть в полном плане в файле. В чате — суть и ключевые решения.

### Каждый шаг — проверяемый

Если в шаге нет «Проверь:» — шаг бесполезен. Разработчик не поймёт, когда шаг готов. Критерий готовности — конкретный: «endpoint возвращает 200 с {valid: true}», «миграция применена, \d order_groups показывает таблицу», «тест `checkout.test.ts` зелёный».

### «Если ошибка» — частые грабли

Не теоретические ошибки, а **реальные частые проблемы**. Например: «Если oEmbed API возвращает 429 — добавь retry с backoff, не падай». Это экономит часы отладки.

### Trade-offs — честно

Не «выбрали X потому что лучше», а «выбрали X потому что в нашем контексте Y важнее Z. Если у вас Z критичнее — выбирайте альтернативу». Это даёт разработчику свободу пересмотреть решение под свой контекст.

### Краткость — это уважение

Разработчик занят. Длинный чат-вывод = не прочитан. Цель: **разработчик прочитает чат за 2-3 минуты и поймёт, что делать**. Если не укладывается — режь длину, переноси в файл.

```
## 🎯 Готовое решение

Делаем бесшовный flow заказа в СММ-панели через модель OrderGroup → Orders → Payment.
Пользователь может оформить 1 или N заказов (на разные соцсети) и оплатить одним
платежом. Атомарность через DB-транзакцию на создание заказов, Stripe call вне TX.
Webhook + polling fallback для надёжности оплат.

## 📋 Варианты на выбор

### Вариант A (рекомендуемый): OrderGroup с webhook + polling fallback
- **Суть:** OrderGroup содержит N orders, оплачивается одним payment intent.
  Webhook от Stripe обновляет статус, polling фолбэчит если webhook не пришёл.
- **Плюсы:** чистая модель, атомарность, future-proof для refunds
- **Минусы:** 5 таблиц, сложнее миграция
- **Когда выбрать:** для production-СММ-панели с ожидаемым ростом

### Вариант B: Плоская модель (1 заказ = 1 платёж)
- **Суть:** каждый заказ — отдельный платёж, массовый = N параллельных платежей
- **Плюсы:** проще схема, быстрее MVP
- **Минусы:** плохой UX (5 платежей за 5 заказов), проблемы с refunds
- **Почему не рекомендуем:** требование «один платёж» явное

## 👣 Пошаговая инструкция (Вариант A)

**Шаг 1: Миграция БД**
- Сделай: создай `migrations/0042_create_orders.sql` с таблицами order_groups,
  orders, payments, refunds, audit_log. Схема в полном плане.
- Проверь: `\dt` показывает все 5 таблиц, constraints активны
- Если ошибка: если FK на users падает — проверь, что users.id имеет тип UUID
- Время: M

**Шаг 2: Backend — валидация ссылок + корзина**
- Сделай: endpoints /services/validate-link (с SSRF protection), /cart/* (Redis, idempotent)
- Проверь: POST /services/validate-link с instagram.com/X возвращает {valid: true,
  platform: 'instagram', services: [...]}
- Если ошибка: если oEmbed таймаутит — добавь timeout 5с и retry
- Время: M

**Шаг 3: Backend — чекаут + webhook**
- Сделай: /checkout (TX для INSERT, Stripe вне TX), /payments/webhook (HMAC verify)
- Проверь: webhook с подделанным signature возвращает 401; с правильным — 200 и
  order_group.status='paid'
- Если ошибка: если Stripe не присылает webhook — проверь webhook URL в dashboard
- Время: L

**Шаг 4: Frontend UI**
- Сделай: страница заказа с 3 режимами (single/multi), корзина при 2+, post-payment
  экран с polling
- Проверь: Lighthouse LCP <2.5 сек, CLS <0.1, e2e тесты зелёные
- Если ошибка: если CLS >0.1 — добавь min-height на контейнеры с async content
- Время: L

**Шаг 5: Upstream integration + refunds**
- Сделай: BullMQ worker, при paid → upstream API, при partial/failed → Stripe refund
- Проверь: тест с 3 success + 2 failed → 2 refund, 3 completed
- Если ошибка: если upstream частично падает — проверь что refund создаётся в таблице
- Время: M

**Шаг 6: Observability + canary**
- Сделай: метрики RED, Grafana dashboard, alerts, feature flag, canary 5%→100%
- Проверь: dashboard показывает воронку, alert срабатывает при error rate >2%
- Если ошибка: если метрики не идут — проверь correlation_id пробрасывается
- Время: M

## ⚠️ Критичные моменты (не пропустить)

- **HMAC verification на webhook** — без этого кто угодно может подделать оплату
- **Stripe call ВНЕ DB transaction** — иначе держим DB connection 1.2 сек
- **Ownership check на /order-groups/:id** — иначе IDOR, любой видит чужие заказы
- **SSRF protection на /services/validate-link** — иначе можно дёрнуть внутренние IP
- **Idempotency-key на /checkout** — иначе race condition = double charge
- **Stripe.js только на /checkout** — иначе +30KB к initial bundle, LCP падает

## 🔀 Trade-offs

| Решение | Выбрали | Альтернатива | Почему |
|---------|---------|--------------|--------|
| Модель | OrderGroup + Orders | Плоская (1 order = 1 payment) | Требование «1 платёж = N заказов» |
| Корзина | Появляется при 2+ | Всегда показывать | Не раздражает одиночные заказы |
| Webhook | + polling + cron fallback | Webhook-only | Без fallback = недоставленные оплаты |
| Upstream partial | Авто-refund | Manual review | UX: пользователь сразу получает деньги |
| Frontend bundle | Code split, Stripe.js lazy | Всё в main | LCP <2.5сек критичен для конверсии |
```

## Когда использовать компактный vs полный формат

| Ситуация | Формат чата | Полный план в файле |
|----------|-------------|---------------------|
| Лёгкая задача (2-3 роли) | Компактный (4-5 шагов) | Опционально |
| Средняя (4-5 ролей) | Компактный (5-7 шагов) | ✅ Обязательно |
| Высокая (6-7 ролей) | Компактный (6-8 шагов) | ✅ Обязательно |

**Принцип:** чат-вывод всегда компактный. Полный план в файл — для средних и высоких сложностей.

## Антипаттерны

❌ **Не выводи весь план в чат** — разработчик не прочитает, потеряется в деталях
❌ **Не пиши «спроектировать архитектуру»** — это не шаг, это задача
❌ **Не пропускай «Проверь:»** — без критерия готовности шаг бессмыслен
❌ **Не прячь trade-offs** — разработчик должен понимать, почему так, чтобы пересмотреть если что
❌ **Не делай 10+ шагов в чате** — если шагов больше 8, группируй или переноси в файл
❌ **Не пиши абстрактные «Если ошибка: обратись к документации»** — конкретные грабли или ничего
