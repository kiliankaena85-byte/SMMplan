# Round Table Planning — скилл для Antigravity (расширенная версия)

Скилл, который улучшает стандартный процесс планирования Antigravity: вместо плана от одного агента, план составляется **круглым столом узких специалистов** под руководством модератора. Расширенная версия включает **10 ролей** под все аспекты современной веб-разработки.

## Концепция

В стандартном подходе Antigravity-агент составляет план в одиночку, играя сразу все роли — архитектора, продуктолога, тестировщика, security, performance инженера. Это приводит к перекосам: либо техническим деталям без пользовательской ценности, либо продуктовым приоритетам без учёта рисков, либо пропущенным edge-cases, security-угрозам или performance budget.

**Круглый стол** решает проблему радикально:
- Каждый аспект плана прорабатывает **узкий специалист**
- Специалисты работают **последовательно**, критикуя предложения предыдущих
- Модератор **динамически выбирает состав** под конкретную задачу (3-7 ролей из 10)
- Глубина 3-4 шага вперёд — видны последствия каждого решения

## Состав скилла

```
round-table-planning/
├── SKILL.md                          # Главный файл: описание, триггеры, workflow
├── README.md                         # Этот файл
└── references/
    ├── triage.md                     # Фаза 1: быстрый анализ задачи, выбор Level 0/1/2/3
    ├── moderator.md                  # Роль модератора (открытие + синтез)
    ├── subagent-orchestration.md     # Level 2+: запуск ролей через invoke_subagent
    ├── architect.md                  # Техника: Архитектор
    ├── data-engineer.md              # Техника: Data Engineer (БД, миграции)
    ├── security-engineer.md          # Техника: Security (STRIDE threat model)
    ├── performance-engineer.md       # Техника: Performance (backend latency)
    ├── frontend-performance.md       # Техника: Frontend Performance (CWV, bundle)
    ├── devops-sre.md                 # Техника: DevOps/SRE (CI/CD, observability)
    ├── seo-ssr-specialist.md         # Техника: SEO/SSR (rendering, metadata)
    ├── ux-designer.md                # Продукт: UI/UX (flow, экраны, состояния)
    ├── product-manager.md            # Продукт: PM (сценарии, метрики, rollout)
    ├── qa-engineer.md                # Качество: QA (DoD, edge-cases, тест-стратегия)
    ├── developer-output.md           # Формат чат-вывода для разработчика (рецепт)
    ├── plan-template.md              # Полный план (17 разделов, для Level 3)
    └── plan-template-compact.md      # Компактный план (для Level 2)
```

## Умная адаптивность (новое)

Скилл не запускается для каждой задачи. Сначала **Triage** (Фаза 1, 30-60 сек) определяет уровень:

| Level | Название | Состав | Когда | Время | Вывод |
|-------|----------|--------|-------|-------|-------|
| 0 | Skip | — | Тривиальная, 1 система, <50 строк | 0 | Код сразу |
| 1 | Lite | Triage + Архитектор + QA (один агент) | 2 системы, типовая фича | 1-2 мин | Чат-рецепт |
| 2 | Standard | Triage + 4-5 ролей через subagents | 3+ системы, новые требования | 3-5 мин | Чат + compact-план в файл |
| 3 | Deep | Triage + 6-7 ролей через subagents | Архитектурные изменения, миграции, платежи | 5-10 мин | Чат + полный план (17 разделов) |

См. `references/triage.md` для полной матрицы принятия решения.

## Реальная параллельная работа через subagents (новое)

Antigravity поддерживает `invoke_subagent` — скилл использует это для Level 2+:
- Каждая роль = отдельный subagent с изолированным контекстом
- Параллельный запуск 5-7 ролей одновременно
- Убирает self-agreement bias (один агент не критикует сам себя)
- Резюме раундов (200-300 слов) передаются между subagents, не полный текст

См. `references/subagent-orchestration.md` для деталей.

## Динамический выбор состава

Не все задачи требуют всех 10 ролей. Модератор выбирает 3-7 ролей под конкретную задачу.

### Матрица выбора по типу задачи

| Тип задачи | Рекомендуемые роли |
|------------|-------------------|
| **Backend-фича** (API, бизнес-логика) | Архитектор, Data Engineer, QA + (Performance, DevOps, Security по контексту) |
| **Frontend-фича** (UI, interactivity) | Архитектор, UI/UX, QA + (Frontend Perf, SEO если публичная) |
| **Публичная страница** (лендинг, блог) | Архитектор, UI/UX, SEO, QA + (Frontend Perf, DevOps) |
| **Платёжный/auth flow** | Архитектор, Security, Data Engineer, QA + (Performance, DevOps, UI/UX) |
| **Миграция БД** | Data Engineer, Архитектор, QA + (DevOps, Performance) |
| **Performance optimization** | Performance (или Frontend perf), Архитектор, QA + (DevOps) |
| **Рефакторинг крупного модуля** | Архитектор, QA, (Data Engineer если БД) + (DevOps, Security) |
| **Интеграция стороннего API** | Архитектор, Security, QA + (Performance, DevOps) |
| **Multi-tenant архитектура** | Архитектор, Data Engineer, Security, QA + (Performance, DevOps) |

## Установка в Antigravity 2.0

Antigravity 2.0 поддерживает skills через стандартную структуру `.agents/skills/` (workspace) или `~/.gemini/config/skills/` (global). Наш скилл полностью совместим с этим форматом.

### Способ 1: Workspace skill (для конкретного проекта)

1. Скопируй каталог `round-table-planning/` в:
   ```
   <workspace-root>/.agents/skills/round-table-planning/
   ```
2. Перезапусти Antigravity или открой проект заново.
3. Скилл автоматически активируется (агент видит name+description из SKILL.md).

### Способ 2: Global skill (для всех проектов)

1. Скопируй каталог в:
   ```
   ~/.gemini/config/skills/round-table-planning/
   ```
2. Перезапусти Antigravity.
3. Скилл доступен во всех проектах.

### Структура после установки

```
<workspace-root>/.agents/skills/round-table-planning/
├── SKILL.md              # агент видит name+description, читает при активации
└── references/           # агент читает при необходимости (progressive disclosure)
    ├── triage.md
    ├── moderator.md
    ├── subagent-orchestration.md
    ├── architect.md
    ├── ... (другие роли)
    ├── developer-output.md
    ├── plan-template.md
    └── plan-template-compact.md
```

Antigravity использует progressive disclosure: сначала видит только name+description, потом читает SKILL.md если релевантно, потом — конкретные `references/*.md` по мере необходимости.

### Проверка установки

После установки открой новый разговор в Antigravity и попроси:
> «Спланируй через круглый стол [описание сложной задачи]»

Агент должен:
1. Активировать скилл (читать SKILL.md)
2. Запустить Фазу 1 (Triage)
3. Вывести `## 🔍 Triage: Level N — Название`
4. Если Level 1+ — перейти к раундам

## Использование

### Автоматическая активация

Скилл активируется при обнаружении сложной задачи:
- Затронуто 2+ системы или модуля
- Требуется изменение архитектуры
- Неоднозначные требования
- Риск регрессий
- Затронуты аутентификация, платежи, PII
- Публичные страницы (SEO-значимый контент)
- Пользователь прямо просит спланировать

### Принудительный запуск

Используй фразы:
- «спланируй через круглый стол»
- «round table для этой задачи»
- «проработай план узкими специалистами»
- «оцени подход комплексно»
- «threat model для этой задачи»
- «продумай UX комплексно»

### Принудительный пропуск

- «просто сделай, без круглого стола»
- «быстрый план, не углубляйся»

## Структура раундов

```
Шаг 0: Триггер → агент распознаёт сложную задачу
Шаг 1: Открытие модератора → состав, порядок, фокус, глубина
Шаг 2: Техническая группа
  2a. Архитектор → задаёт фундамент (последовательно)
  2b. Data Engineer → схема БД под архитектуру (последовательно)
  2c-g. ПАРАЛЛЕЛЬНО (после 2a+2b):
    ├ Security → STRIDE threat model
    ├ Performance (backend) → latency, запросы
    ├ Frontend Performance → CWV, bundle
    ├ DevOps/SRE → CI/CD, observability
    └ SEO/SSR → rendering, метаданные
Шаг 3: Продуктовая группа
  3a. UI/UX → user flow, экраны, состояния
  3b. PM → сценарии, метрики, rollout
Шаг 4: QA → DoD, edge-cases, тест-стратегия, rollback
Шаг 5: Синтез модератора → Trade-offs + два уровня вывода
Шаг 6: Презентация пользователю → чат-рецепт + полный план в файл
```

Не все шаги 2a-2g обязательны — moderator выбирает состав под задачу.

### Параллелизм ролей

После Архитектора и Data Engineer технические роли (Security, Performance, Frontend Performance, DevOps, SEO) работают **параллельно** — они критикуют архитектуру и схему, между собой пересекаются мало. Это ускоряет процесс без потери глубины.

## Два уровня вывода

Главный принцип: **разработчику — рецепт, не отчёт**.

### Чат-вывод (для разработчика, 2-3 мин чтения)
Формат: `references/developer-output.md`

1. **🎯 Готовое решение** — 1 абзац, суть
2. **📋 Варианты на выбор** — 1-2 варианта с плюсами/минусами/«когда выбрать»
3. **👣 Пошаговая инструкция** — конкретные шаги (Сделай / Проверь / Если ошибка / Время)
4. **⚠️ Критичные моменты** — 3-7 блокеров и граблей
5. **🔀 Trade-offs** — таблица: что выбрали, от чего отказались, почему
6. **📄 Полный план** — ссылка на файл
7. **✅ Подтверждение** — какой вариант выбираем

### Полный план в файл (для деталей)
- **Высокая сложность (6-7 ролей):** `references/plan-template.md` (17 разделов)
- **Средняя сложность (4-5 ролей):** `references/plan-template-compact.md`
- **Лёгкая (2-3 роли):** опционально
- Сохраняется в `/home/z/my-project/download/plan-[task-name].md`

Включает: схему БД, STRIDE threat model, performance budgets, SLO, тест-стратегию, rollback-план, все edge-cases, observability детали.

## Финальный план включает (16 разделов)

**Обязательные:**
1. Цели и контекст
2. Пошаговый план с DoD
3. Альтернативы (минимум 2)
4. Риски и митигация (включая STRIDE-угрозы)
12. Тест-стратегия
13. Rollout и rollback
15. Резюме решений
16. Запрос подтверждения

**Условные (включаются если роль участвовала):**
5. UX-спецификации (Mermaid flow, экраны, состояния)
6. Архитектурные детали
7. Схема данных и миграции
8. Security checklist (auth matrix, защита данных, compliance)
9. Performance budgets (backend latency + frontend CWV)
10. DevOps requirements (CI/CD, observability, SLO, DR)
11. SEO/SSR requirements (rendering, metadata, structured data)

## Адаптация под команду

### Добавление новой роли

1. Создай файл `references/<role>.md` по образцу существующих.
2. Опиши: оптику роли, что оценивает, что не оценивает, deliverables, принципы, конфликты, блокеры релиза, передачу эстафеты.
3. Добавь роль в `SKILL.md` в разделы «Доступные роли» и «Матрица выбора».
4. Укажи, в какой группе (Техника/Продукт/Качество) роль выступает и порядок.
5. Обнови `plan-template.md` — добавь раздел под deliverables роли.
6. Обнови `moderator.md` — добавь критерии включения роли.

### Изменение порядка раундов

В `SKILL.md` найди раздел «Порядок раундов» и скорректируй.

### Изменение глубины

В `SKILL.md` найди таблицу «Сложность → Глубина».

### Изменение формата вывода

Замени `references/plan-template.md` на свой шаблон. Главное — сохрани обязательные разделы, иначе потеряется ценность круглого стола.

## Примеры использования

### Пример 1: Добавление OAuth-аутентификации

**Состав:** Архитектор, Data Engineer, Security, UI/UX, QA (5 ролей)

**Почему:** auth = Security critical, миграция БД = Data Engineer, новый flow = UI/UX. SEO не нужен (не публичная), Frontend Perf не нужен (кнопка не влияет на bundle).

### Пример 2: Редизайн главной страницы

**Состав:** UI/UX, Frontend Performance, SEO, Архитектор, QA (5 ролей)

**Почему:** публичная страница = SEO + Frontend Perf, новый UX = UI/UX. Security не нужен (нет sensitive data), Data Engineer не нужен (не затрагивает БД).

### Пример 3: Миграция PostgreSQL → MySQL

**Состав:** Data Engineer, Архитектор, DevOps, Performance, QA (5 ролей)

**Почему:** миграция = Data Engineer главный, downtime risk = DevOps, query rewrites = Performance. UI/UX не нужен (невидимо пользователю), Security не нужен (не затрагивает auth).

## Кастомизация

Все файлы на русском. Если нужен английский — переведи `SKILL.md` и `references/*.md`, сохранив структуру.

## Troubleshooting

### Скилл не активируется

- Проверь, что `SKILL.md` находится в правильной директории
- Проверь, что в `description` поля YAML frontmatter указаны триггерные слова
- Попробуй запустить явно: «спланируй через круглый стол»

### Агент пропускает раунды

- Проверь, что в `SKILL.md` workflow описан явно
- Если задача лёгкая, агент может адаптировать состав — это нормально
- Если проблема постоянная — усили `description`

### План получается поверхностным

- Проверь, что роли действительно критикуют предыдущие раунды, а не работают параллельно
- Увеличь глубину в `SKILL.md`
- Добавь больше ролей в состав

### План слишком длинный

- Уменьши состав ролей (moderator может исключить ненужные)
- Используй лёгкий шаблон для простых задач
- Сократи глубину до 2-3 шагов
