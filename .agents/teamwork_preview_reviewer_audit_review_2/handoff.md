## Findings / Выявленные замечания и расхождения с кодом

### [Major] Расхождение в уровне изоляции транзакции `logManualCompensation`
*   **Что**: В аудит-отчете утверждается, что экшн `logManualCompensation` использует уровень изоляции `Serializable` в транзакции Prisma для защиты от Race Conditions:
    ```typescript
    await db.$transaction(async (tx) => { ... }, { isolationLevel: 'Serializable' });
    ```
*   **Где**: `src/actions/support/compensation.ts` (строка 56) и `admin_usability_audit_report.md` (строка 104).
*   **Почему это проблема**: При чтении реального кода файла `src/actions/support/compensation.ts` на строке 56 обнаружено, что вызов транзакции выглядит как `await db.$transaction(async (tx) => {` **без** передачи второго параметра опций `{ isolationLevel: 'Serializable' }`. Это означает, что транзакция в действительности выполняется на уровне по умолчанию (`Read Committed` в PostgreSQL).
*   **Рекомендация**: Это критическое упущение кода. Хотя PostgreSQL использует блокировку строк (`FOR UPDATE`) при выполнении `update` (уменьшении лимита доверия оператора), для 100% защиты от аномалий неконсистентного чтения (write skew) необходимо явно добавить `{ isolationLevel: 'Serializable' }` в код экшена, как это и было заявлено в отчете.

### [Minor] Серверная проверка прав роли при получении себестоимости (`canSeeRates`)
*   **Что**: Ролевая видимость закупочных цен (`canSeeRates`) вычисляется на сервере в `page.tsx` и прокидывается пропом в `OrderClient` и `columns`.
*   **Почему**: Это безопасно для страницы заказов, но при рефакторинге и вынесении `OrderDrawer` в общий переиспользуемый компонент для чата необходимо убедиться, что `canSeeRates` проверяется на уровне Server Actions (например, `fetchOrderDetailsAction`), чтобы операторы с ролью `SUPPORT` не могли перехватить себестоимость через прямые запросы к API.
*   **Рекомендация**: Добавить серверную валидацию прав роли в `fetchOrderDetailsAction` перед возвратом поля `providerCost` (возвращать `null`, если роль пользователя `SUPPORT`).

## Challenges / Вызовы и стресс-тесты

### [Medium] Риск взаимной блокировки и абортов транзакций СУБД (PostgreSQL Deadlocks under Serializable Isolation)
*   **Оспариваемое предположение**: Использование уровня изоляции `Serializable` гарантирует 100% безопасность `logManualCompensation` при конкурентных запросах.
*   **Атакующий сценарий / Сценарий сбоя**: Уровень изоляции `Serializable` в PostgreSQL работает по принципу оптимистического контроля. Если два оператора поддержки одновременно проводят компенсацию одному и тому же пользователю, или если в этот же момент фоновый воркер списывает средства с баланса пользователя, PostgreSQL обнаружит конфликт зависимостей чтения/записи (rw-antidependency) и принудительно прервет одну из транзакций с ошибкой `40001 (serialization_failure)`. Оператор увидит ошибку на экране, а списание лимита зависнет.
*   **Масштаб ущерба**: Сбой транзакции, фрустрация поддержки, возможные повторные случайные клики.
*   **Защитный механизм (Mitigation)**: Внедрить механизм автоматического повторения транзакции (Retry Loop - декоратор `transactionalRetry`) при возникновении ошибок `P2034` (Prisma Serializable Conflict) с экспоненциальной задержкой (exponential backoff) до 3 попыток, либо использовать пессимистическую блокировку строки пользователя на чтение (`db.$queryRaw` с `SELECT ... FOR UPDATE`).

### [Low] Переполнение разрядности типа numericId (Int32 Overflow)
*   **Оспариваемое предположение**: Поиск по `numericId` через `parseInt(q, 10)` безопасен.
*   **Атакующий сценарий**: Если злоумышленник или оператор по ошибке введет в поисковую строку гигантское число (например, `999999999999999999`), `parseInt` вернет значение, превышающее максимальный размер 32-битного знакового целого числа в PostgreSQL (`2147483647`). Prisma упадет с необработанной ошибкой переполнения типа (`QueryInterpretationError`), вызвав 500-й сбой страницы заказов.
*   **Масштаб ущерба**: Временная недоступность интерфейса поиска заказов для оператора.
*   **Защитный механизм (Mitigation)**: Перед добавлением `where.numericId = numId` в Prisma-запрос убедиться, что число укладывается в границы Int32:
    ```typescript
    if (!isNaN(numId) && q === String(numId) && numId >= -2147483648 && numId <= 2147483647) {
      where.numericId = numId;
    }
    ```

# 3. HANDOFF REPORT / 5-КОМПОНЕНТНЫЙ ОТЧЕТ О ПЕРЕДАЧЕ

## 1. Observation / Наблюдения
*   **Баг A (Пропуск `userId`)**: `src/app/admin/orders/page.tsx` считывает `q`, `status`, `cursor`, но полностью опускает параметр `userId` (строки 42-45). Сервис `src/services/admin/order.service.ts` не имеет поля `userId` in `OrderSearchParams` (строка 19).
*   **Баг B (Сброс Drawer при пагинации)**: В `src/app/admin/orders/components/order-client.tsx` на строках 449-452 `selectedOrder` рассчитывается через `data.find()`. Массив `data` содержит только текущие 50 строк страницы.
*   **Лимиты и компенсации**: Бэкенд-экшн `logManualCompensation` в `src/actions/support/compensation.ts` (строка 56) в транзакции `db.$transaction` не содержит настроек `isolationLevel: 'Serializable'`, вопреки утверждению в отчете (строка 104).
*   **Интеграция Drawer в Чат**: В `src/app/admin/tickets/[id]/page.tsx` ссылка на заказ ведет на внешний `/admin/orders?edit_order_id=...` (строка 121), что уводит оператора из контекста диалога.

## 2. Logic Chain / Логическая цепочка
1. Ссылки из сайдбара ведут на `/admin/orders?userId=X`.
2. Так как страница заказов не парсила `userId`, Prisma не применяла этот фильтр, выдавая глобальный список.
3. Оператор видит чужие заказы вместо заказов конкретного клиента $\rightarrow$ Баг A подтвержден.
4. Ссылка «Перейти к заказу» ведет на `?edit_order_id=Y`.
5. Если заказ `Y` на 2-й странице, `data.find` в `order-client.tsx` возвращает `undefined` $\rightarrow$ Drawer не открывается $\rightarrow$ Баг B подтвержден.
6. Разработчик применил серверное упреждающее решение (`unshift` в `orders`), гарантирующее присутствие `Y` на клиенте, что является превосходной альтернативой клиентскому `useEffect` из отчета.
7. Отсутствие явного Serializable-уровня в `logManualCompensation` создает потенциальную угрозу race condition при высоком параллелизме списаний $\rightarrow$ Выявлено техническое расхождение.

## 3. Caveats / Оговорки
