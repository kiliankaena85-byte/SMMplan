This report synthesizes the exploration, architecture mapping, and E2E verification planning for requirements **R3 (End-to-End User Flow Tests)** and **R4 (Admin Panel & Operator Roles E2E Tests)**.

### B. User Flow Specifications (R3)
*   **Magic Link authentication flow**: `e2e/user-flow.spec.ts` (lines 180-241) requests the link from `/login`, queries the generated token directly from the database, issues a hashed `AuthToken` record, navigates to `/api/auth/verify?token=...`, asserts redirect to `/dashboard`, and verifies the token is set to `used: true`.
*   **Unit pricing display validation**: `e2e/user-flow.spec.ts` (lines 279-312) checks that option text in the service select dropdown contains `₽ / шт` and excludes `/ 1000 шт` package labels, and asserts that no bulk package labels exist in the form layout.
*   **Link validation targetType logic**: `e2e/user-flow.spec.ts` (lines 317-373) verifies that inputting a channel link `https://t.me/durov` for a Likes service (expected `POST` target) displays a validation error (`/ конкретный пост/i`), while inputting a post link `https://t.me/durov/123` for a Subscribers service (expected `CHANNEL` target) displays a validation error (`/ публичную ссылку на канал/i`).
*   **Sufficient balance order checkout**: `e2e/user-flow.spec.ts` (lines 380-438) checks that submitting a valid order deducts the user's balance directly by the cost of the order (10 units * unit price of 0.24 = 2.40 RUB = 240 cents), redirects to the success page, and creates a `PENDING` order.
*   **Insufficient balance redirection**: `e2e/user-flow.spec.ts` (lines 440-493) asserts that an order with insufficient balance redirects to `/support/payment-error?error=Недостаточно средств`, and checks that no order is created in the database.

### C. Admin Panel & Operator Actions (R4)
*   **Quarantine logic page**: `e2e/admin-panel.spec.ts` (lines 70-125) seeds a quarantined service (`isQuarantined: true`, `pendingRate: 20.0`), visits `/admin/catalog/quarantine`, ensures the quarantine reason is visible, clicks "Отклонить", checks the toast message "Отклонено, цена сохранена", and verifies the service disappears from the table.
*   **Manual balance adjustments**: `e2e/admin-panel.spec.ts` (lines 134-174) navigates to `/admin/clients?userId=...`, inputs amount and reason, accepts the dialog, and clicks "Применить".
*   **Audit logs settings trace**: `src/actions/admin/users.ts` (lines 43-51) calls `auditAdminAwaitable` with action `UPDATE_BALANCE_REQUEST` and target user ID when adjusting a balance.
*   **Escrow Guard mechanism**: `src/services/admin/escrow.service.ts` (lines 44-50) bypasses limits for `OWNER` or `ADMIN` roles and executes balance updates instantly. In contrast, support/operator roles triggers daily trust budget limits (e.g. `supportLimitCents`) or a quarantine bubble (`quarantineBalance`).
*   **Atomic repricing loss-prevention check**: `src/services/admin/catalog.service.ts` (lines 658-700) calculates new prices during an exchange rate change. If the new `pricePerUnitRub` is less than the provider cost `purchaseCostPerUnitRub`, it deactivates the service (`isActive: false`), creates a `LOSS_PREVENTION_BLOCK` inside `db.routingAuditLog`, and triggers a critical admin alert.

## 2. Logic Chain

1.  **Auth Integration**: By default, E2E tests in Playwright use the storage state generated by `auth.setup.ts`. For tests targeting the standard user flow (R3), `user-flow.spec.ts` explicitly overrides this state using `test.use({ storageState: { cookies: [], origins: [] } })` to test raw login flows, ensuring the guest-to-user flow is correctly validated.
2.  **Pricing Compliance**: To enforce the Smmplan pricing model defined in `AGENTS.md` (no "/ 1000 шт" displays to the user, prices shown in `₽ / шт`), `user-flow.spec.ts` parses the text of elements in the catalog form and runs exact string mismatches to prevent regressions.
3.  **Link Validation Consistency**: Category-to-targetType mapping logic defined in `src/utils/target-type.ts` (`inferTargetTypeFromCategory`) must be validated in UI forms. E2E tests input positive/negative links (e.g. channel links vs post links) to verify the UI displays appropriate alert banners and controls the disabled state of the submit button.
4.  **Admin Panel Verification**: Admin actions like resolving quarantines, setup of providers, and updating rates impact background queues. Updating settings (e.g. `exchangeRateUSD` in `settings.ts`) enqueues a `sync-prices-bg` job in the BullMQ `catalogQueue`. This background worker runs `syncDenormalizedPrices` to calculate new retail prices. If the markup safety floor is breached, it deactivates services.
5.  **Ledger Integrity**: Manual adjustments must write to both `LedgerEntry` (financial records) and `AdminAuditLog` (admin trail). While UI E2E tests verify toast notifications and DOM updates, the test logic should inspect database records after browser execution to verify that:
    *   `LedgerEntry` has correct delta, reason, status `'APPROVED'`, and admin identifier.
    *   `AdminAuditLog` records the old balance, new balance, ipAddress, and operation code.

## 3. Caveats

*   **RAG Query Failure**: The external GraphRAG container was offline due to local networking limitations. Context was reconstructed using static analysis of files in `src/actions/`, `src/services/`, and `e2e/`.
*   **BullMQ Execution Delay**: Workers run asynchronously in a separate process. E2E tests checking repricing should wait for queue completion or trigger repricing synchronously through debug API endpoints to avoid race conditions.
*   **Ledger Immutability**: `LedgerEntry` is set as immutable in Prisma. Deletions in `db-cleaner.ts` are wrapped in a try/catch, meaning database size will grow during E2E runs unless a transaction rollback pattern is used.

---

## 4. Conclusion

The existing Playwright suite provides solid structural coverage for basic user flows and admin quarantine/settings management. However, several critical integration verification points are missing or not explicitly verified at the database level:

1.  **Ledger & Audit Log Verification**: Admin balance adjustments must be verified directly against the PostgreSQL `LedgerEntry` and `AdminAuditLog` tables at the end of the test.
2.  **Background Price Synchronization Check**: Settings rate changes should verify that BullMQ processes price changes correctly, applying loss prevention blocks to services that fall below cost.
3.  **Cherry-Pick Shadow Catalog Import UI**: E2E tests must verify the import wizard UI from provider dashboards, checking that only selected services are added to the active database.
