## 1. Резюме для руководителя (Executive Summary)

### 1.1 Что проверялось

Проведена разведка репозитория (структура, стек, схема БД, ~1000 файлов исходников) и последующий глубокий аудит четырёх контуров, на которые пожаловался владелец: (1) управление провайдерами, (2) импорт услуг из провайдеров, (3) отображение услуг в каталоге, (4) административная панель в части перечисленных процессов. Аудит выполнен методом трассировки кода: от кнопки в интерфейсе → через Server Action → сервисный слой → Prisma-запрос → схема БД → публичные запросы каталога. Дополнительно сверено фактическое поведение кода с e2e-тестами и внутренними регламентами репозитория (AGENTS.md, ARCHITECTURE_CONTRACTS.md).

### 1.2 Главный вывод

**Все четыре жалобы владельца подтверждаются кодом и имеют конкретные корневые причины.** Ни одна из них не является «случайным глюком» — это системные дефекты реализованных функций, каждый из которых воспроизводится детерминированно:

| Жалоба владельца | Подтверждение | Корневая причина (кратко) |
|---|---|---|
| «Не могу удалять провайдеров» | ✅ Подтверждено | Функции удаления **не существует** ни в UI, ни в Server Actions; в БД связь `ServiceRoute → Provider` запрещает удаление (`onDelete: Restrict`) |
| «Не могу нормально править провайдеров» | ✅ Частично | Редактирование работает, но сырые ошибки БД (дубликат имени) показываются непонятным текстом; API-ключ и маппинг легко «затереть» неудачным сохранением |
| «При импорте не могу выбрать провайдера» | ✅ Подтверждено | В мастере импорта **нет селектора выбора провайдера** — жёстко берётся первый активный провайдер из списка |
| «Услуги не появляются в каталоге» | ✅ Подтверждено | Комбинация из 5 независимых причин: падение импорта по наценке, молчаливые пропуски дублей, несогласованные мульти-тенантные фильтры, пустой экран при несинхронизированном каталоге, кэш |

### 1.3 Критические дефекты (P0) — чинить немедленно

1. **AUD-01. Удаление провайдера не реализовано.** В таблице провайдеров нет кнопки удаления, в Server Actions нет `deleteProviderAction`, а единственная функция `deleteProvider` похоронена в `settings.service.ts` и не вызывается ни одним интерфейсом. Даже при ручном вызове удаление упадёт с ошибкой внешнего ключа из-за `ServiceRoute`.
2. **AUD-02. В мастере импорта нельзя выбрать провайдера.** `providerId` инициализируется первым активным провайдером и больше нигде не меняется — селектора в интерфейсе нет. Импорт возможен только из одной панели, пока администратор вручную не деактивирует остальные.
3. **AUD-03. Импорт падает из-за конфликта единиц наценки.** Поле в UI — «Наценка (%)» со значением по умолчанию **50**; серверная валидация требует **множитель** от 1.0 до 10.0. Любой импорт со значением по умолчанию (и вообще с любым «процентом» больше 9) завершается ошибкой валидации. Услуга не создаётся — «не появляется в каталоге».
4. **AUD-04. Молчаливые пропуски при импорте.** `createMany({ skipDuplicates: true })` тихо отбрасывает услуги с коллизией slug (одинаковые названия), а «живая проверка цен» тихо пропускает услуги, изменившиеся у провайдера. Итог: «выбрал 30, импортировалось 12, почему — неизвестно».
5. **AUD-05. Мульти-тенантные фильтры каталога несогласованы.** Публичный каталог фильтрует сети/категории/ услуги по тенанту с разными правилами; список категорий в мастере импорта вообще не фильтруется по тенанту. Импорт «не в тот тенант» или категория «чужого» тенанта приводит к тому, что услуга существует в БД, но невидима в каталоге.
6. **AUD-06. Пустой экран при несинхронизированном каталоге.** Если теневой каталог (ShadowService) пуст, сервер возвращает подсказку «Теневой каталог пуст. Нажмите "Загрузить каталог"», но интерфейс это сообщение **не отображает** — администратор видит просто пустую таблицу без объяснений.

### 1.4 Влияние на бизнес

- **Прямая потеря выручки:** импорт — единственный способ наполнить витрину услугами. При текущем состоянии конвейера (AUD-02/03/04/06) массовое подключение новых провайдеров практически невозможно, а точечный импорт требует обходных манёвров и ручной работы.
- **Риск некорректных цен:** смешение «проценты/множители» (AUD-03) и скрытый принудительный минимум наценки ×3.0 (AUD-13) означают, что даже успешный импорт может поставить цену в 3 раза выше запланированной — конкурентная цена уходит в маржу, конверсия падает.
- **Операционные издержки:** невозможность удалить/переподключить провайдера (AUD-01) заставляет вести «кладбище» тестовых и мёртвых панелей; RBAC-путаница (AUD-09) блокирует делегирование работы каталога сотрудникам.
- **Эрозия доверия к тестам:** e2e-тесты импорта провайдера описывают поведение, которого нет в коде (AUD-12), то есть красные тесты «замаскированы» — регрессии не отлавливаются.

### 1.5 Топ-5 действий (кратко)

1. Реализовать безопасное удаление провайдера (экшен + кнопка + каскад `ServiceRoute`).
2. Добавить селектор провайдера в мастер импорта.
3. Унифицировать наценку: одна семантика (множитель) от UI до БД, конвертация «% → множитель» в одном месте.
4. Вернуть видимое состояние «каталог пуст — загрузить» и подробный отчёт импорта (импортировано / пропущено / причины).
5. Синхронизировать тенантные фильтры каталога (category/service/network) и инвалидировать кэш витрины после импорта.

Полная дорожная карта с этапами, приоритетами и оценкой трудозатрат — в разделе 6.

## 4. Детальные находки

Каждая находка содержит: симптом (что видит администратор), корневую причину (с кодом), сценарий воспроизведения и сценарий проверки после исправления.

### AUD-01 [P0] Удаление провайдера не реализовано ни в UI, ни в серверном слое

**Симптом.** На странице «Провайдеры API» (`/admin/providers`) в строке провайдера доступны действия: «Настроить» (переход на страницу редактирования), переключатель активности, сброс счётчика ошибок, копирование URL, кнопка «Обновить» (синхронизация), внешняя ссылка на тикет-систему. Кнопки «Удалить» нет. Удалить нельзя ни тестовую, ни ошибочную, ни более не нужную панель.

**Корневая причина — тройная:**

**(а) В Server Actions функции удаления просто нет.** В `src/actions/admin/providers/crud.ts` экспортированы: `createProvider`, `updateProvider`, `checkProviderConnection`, `probeProviderAction`, `getProviderCatalogPreviewAction`, `getGlobalProviderLiquidity`, `syncProviderCatalogAction`, `inferProviderSchema`, `toggleProviderActiveAction`, `resetProviderErrorsAction`, `createMockProviderPresetAction`. Функции `deleteProviderAction` не существует. Поиск `provider.delete` по всему `src/` находит только:

```text
src/services/admin/settings.service.ts:80:  async deleteProvider(id: string) {
src/services/admin/settings.service.ts:81:    return db.provider.delete({ where: { id } });
```

Этот метод — **dead-code**: `settingsService` импортируется только в `src/actions/admin/settings.ts` и `src/app/admin/settings/page.tsx`, и среди экспортируемых там экшенов (`updateUserRole`, `updateGlobalSettings`, `generateInboundSecretAction`, `getSettingsAction`, `testSmtpConnectionAction`, …) `deleteProvider` не вызывается ни разу. То есть метод висит в сервисе настроек, никем не используется и не покрыт тестами.

**(б) Даже вызванный напрямую, он упадёт из-за ограничения БД.** Схема связей `Provider`:

```prisma
// prisma/schema.prisma
model Service {
  providerId String?
  provider   Provider? @relation(fields: [providerId], references: [id], onDelete: SetNull)  // ОК
}
model Order {
  provider   Provider? @relation(..., onDelete: SetNull)                                     // ОК
}
model ShadowService {
  provider   Provider  @relation(..., onDelete: Cascade)                                     // ОК
}
model ServiceRoute {
  provider   Provider  @relation(..., onDelete: Restrict)                                    // ← БЛОКИРУЕТ
}
```

`ServiceRoute` — таблица маршрутизации заказов на альтернативных провайдеров (`@@unique([serviceId, providerId])`). Как только у провайдера появляется хотя бы один маршрут, `db.provider.delete()` завершится ошибкой внешнего ключа Prisma `P2003`, которая в текущем коде нигде не перехватывается и не переводится в человекочитаемое сообщение.

**(в) UI не содержит ни кнопки, ни модалки подтверждения.** В `client-table.tsx` импортированы только `toggleProviderActiveAction`, `resetProviderErrorsAction`, `createMockProviderPresetAction` — реализация удаления с подтверждением («У провайдера 1 240 услуг и 56 заказов — отвязать услуги и удалить?») не написана.

**Сценарий воспроизведения.** `/admin/providers` → навести курсор на строку любого провайдера → в блоке «Actions» присутствуют только «Настроить» и переключатели. Удаление невозможно. Попытка обхода через URL (`/admin/providers/<id>/delete`) — 404.

**Сценарий проверки после исправления.** (1) Для провайдера без услуг и маршрутов: «Удалить» → подтверждение → строка исчезает, в `Provider` записи нет, в аудите — `PROVIDER_DELETE`. (2) Для провайдера с услугами и маршрутами: модалка показывает счётчики (`услуг: N, маршрутов: M, заказов: K`), удаление проходит: услуги получают `providerId = NULL`, маршруты удаляются, заказы сохраняют `providerId = NULL` (исторические снимки уже продублированы в `providerServiceId`), теневой каталог удаляется каскадом. (3) RBAC: сотруднику с правом `catalog:edit` разрешено, с `catalog:view` — отказ с понятной ошибкой.

### AUD-02 [P0] В мастере импорта невозможно выбрать провайдера

**Симптом.** На странице «Импорт Услуг» (`/admin/providers/import`) администратор видит имя провайдера в сводке сверху, но переключиться на другой каталог нельзя. Импортируются услуги всегда одной и той же панели.

**Корневая причина.** Страница отдаёт в мастер список активных провайдеров:

```tsx
// src/app/admin/providers/import/page.tsx
const providers = await adminProviderService.listProviders();
const activeProviders = providers.filter(p => p.isActive);
...
<ImportWizard categories={categories} providers={activeProviders} />
```

Внутри мастера идентификатор провайдера фиксируется при монтировании и больше не меняется:

```tsx
// src/app/admin/providers/import/components/import-wizard.tsx
const [providerId, setProviderId] = useState<string>(providers[0]?.id || "");  // строка 148
```

Дальше по коду компонента `providerId` используется в `fetchPaginatedExternalServices`, `fetchExternalServices`, `importSelectedServices` и в подписи сводки (`providers.find(p => p.id === providerId)?.name`). В отрендеренном JSX есть ровно один компонент `Select` — «Массовая категория…» (строки 562–573). **Селектора провайдера не существует.** Функция `setProviderId` объявлена, но нигде не вызывается — мёртвый сеттер, который сам по себе указывает на незавершённую фичу.

Косвенное следствие: чтобы импортировать из другой панели, администратору приходится идти на `/admin/providers`, деактивировать текущую панель-«лидер», возвращаться в импорт и работать с.catalog ставшей первой активной панели — именно те «обходные манёвры», на которые жалуется владелец.

Дополнительное неудобство того же класса: `listProviders()` сортирует по `createdAt: 'desc'` — «первый активный» это самый недавно созданный провайдер, что неочевидно и не управляемо.

**Сценарий воспроизведения.** Подключить два активных провайдера A и B (B создан позже). Открыть `/admin/providers/import` → в сводке всегда отображается B, в таблице — каталог B. Никакой элемент UI не позволяет переключиться на A.

**Сценарий проверки после исправления.** Селектор провайдера в шапке мастера: список всех активных провайдеров с именем и числом услуг; переключение сбрасывает выбор/фильтры и перезагружает теневой каталог; счётчики платформ, пагинация и «уже импортировано» пересчитываются для выбранной панели; при синхронизации кэша обновляется именно выбранный провайдер.

### AUD-03 [P0] Конфликт единиц наценки: UI в процентах, сервер — множитель; импорт с настройками по умолчанию всегда падает

**Симптом.** Администратор выбирает услуги, оставляет наценку «как есть» (50), подтверждает импорт — получает ошибку валидации с формулировкой про «1.0 … 10.0», не имеющую отношения к тому, что он видел на экране. Услуга не создаётся.

**Корневая причина — три несогласованных контракта:**

**(а) UI — проценты.** Сводка мастера рендерит поле с подписью «Наценка (%)», начальное значение строки `"50"` задаётся в мастере:

```tsx
// import-wizard.tsx:164
const [markup, setMarkup] = useState<string>("50");
// ...
<SummaryDashboard markup={markup} onMarkupChange={setMarkup} ... />
```

```tsx
// summary-dashboard.tsx
<label ...>Наценка (%)</label>
<Input type="number" step="1" min="0" value={markup} ... />
```

**(б) Server Action — множитель с жёстким диапазоном.** Значение передаётся без какой-либо конвертации (`parseFloat(markup) || 50`) и валидируется Zod-схемой:

```ts
// src/actions/admin/providers/import-cherry-pick.ts:360-369
const importServicesSchema = z.object({
  ...
  defaultMarkup: z.coerce.number().refine(val => val === 0 || (val >= 1.0 && val <= 10.0), {
    message: "Наценка должна быть 0 (автокалькуляция) или от 1.0 (0%) до 10.0 (900%)"
  }),
```

Число 50 не проходит `refine` (50 > 10) → импорт завершается `success: false` с этим сообщением. **Любой импорт со значением по умолчанию обречён.** Проходит только число 1–10, при этом семантика для пользователя инвертирована: введя «5» в поле «Наценка (%)», администратор ожидает +5%, а получает множитель ×5 (+400%).

**(в) Сервисный слой и БД — множитель.** `Service.markup Float @default(3.0)`, формула цены `rate × markup × exchangeRate`, причём ниже по стеку наценка дополнительно принудительно поднимается до `SAFETY_FLOOR_MARKUP = 3.0` (см. AUD-13). Для сравнения, массовое изменение наценки (`bulkUpdateMarkup`) допускает диапазон 1.0–151.0 — третий несовместимый диапазон в том же домене.

**Сверка с e2e-тестом подтверждает, что задумывалась конвертация.** `e2e/providers.spec.ts` (кейс «Admin can import service via Cherry-Pick Wizard») заполняет поле значением `'75'` и затем утверждает:

```ts
await markupInput.fill('75');
...
expect(service!.markup).toBe(1.75);   // 75% → ×1.75
```

То есть ожидаемое поведение — «процент конвертируется в множитель по формуле `1 + p/100`». В продакшн-коде этой конвертации нет ни в мастере, ни в экшене. Тест красный (см. AUD-12), регрессия не поймана.

**Сценарий воспроизведения.** Импорт одной любой услуги со значением поля «Наценка (%)» = 50 (по умолчанию) → тост/баннер «Ошибка валидации: Наценка должна быть 0 (автокалькуляция) или от 1.0 (0%) до 10.0 (900%)», услуга в БД не создаётся. То же с любым значением > 9.

**Сценарий проверки после исправления.** Ввод «75» → в БД `markup = 1.75`; ввод «0» → автокалькуляция по лестнице цен (`markup = 0` передаётся в сервис, `applyPricingLadder`); ввод «300» → `markup = 4.0`; ввод «50» → `markup = 1.5`. Диапазон поля в UI согласован с сообщением об ошибке; e2e-кейс с `fill('75')` проходит зелёно.

### AUD-04 [P0] Молчаливые пропуски при импорте: дубль-slug и live-check отбрасывают услуги без отчёта

**Симптом.** Администратор выбирает 30 услуг, получает «Успешно импортировано 12 услуг!». Где остальные 18 — неизвестно: ни ошибок, ни списка пропущенных. В отдельных случаях (повторный импорт того же каталога) счётчик равен нулю при полном «успехе».

**Корневая причина — два независимых механизма тихих пропусков.**

**(а) `skipDuplicates` + генерация slug из названия.** Slug услуги вычисляется на лету:

```ts
// catalog.service.ts:926
const stableSlug = importedName.toLowerCase().trim()
  .replace(/[^a-z0-9а-яё]+/gi, '-')
  .replace(/^-+|-+$/g, '') || `service-${extId}`;
```

и услуга вставляется пачкой:

```ts
// catalog.service.ts:962-965
const result = await db.service.createMany({
    data: servicesToCreate,
    skipDuplicates: true   // ← тихо отбрасывает строки, конфликтующие с ЛЮБЫМ unique-ограничением
});
importedCount = result.count;
```

В схеме `Service` действует `@@unique([tenantId, slug])`. SMM-каталоги провайдеров изобилуют одноимёнными услугами («Telegram Subscribers HQ» в разных категориях, версии «v1/v2» после нормализации названий). Любое совпадение slug внутри пачки или с уже существующей услугой тенанта → строка отбрасывается **без ошибки и без упоминания в отчёте**. Префикс `service-${extId}` спасает только полностью пустые названия.

Проверка дублей перед вставкой (`existingSet`) ловит лишь пару `tenantId:externalId`, но не slug-коллизии — они проходят мимо логики и гасятся на уровне БД.

**(б) Live-check пропускает изменившиеся услуги.** Перед вставкой каталог провайдера запрашивается повторно целиком:

```ts
// catalog.service.ts:892-905
const liveExt = liveMap.get(extId);
if (!liveExt) {
  console.warn(`[Live-Check] Service ${shadowExt.service} was removed by provider. Skipping.`);
  continue;                    // ← пропуск: услуги уже нет у провайдера
}
const rawRate = parseFloat(liveExt.rate);
if (isNaN(rawRate) || rawRate <= 0) {
  console.warn(`[Live-Check] Service ${shadowExt.service} has invalid rate: ${liveExt.rate}. Skipping import.`);
  continue;                    // ← пропуск: невалидная цена
}
```

Оба `console.warn` видны только в логах сервера. В ответе экшена — только `imported`. Пропущенные идентификаторы и причины пользователю не возвращаются.

**Итоговая формула потерь:** `выбрано = импортировано + slug-дубли + removed-by-provider + invalid-rate + already-exists`, и три слагаемых справа невидимы администратору. Это прямой источник жалобы «услуги не появляются в каталоге».

**Сценарий воспроизведения.** (1) Импортировать услугу «Telegram Subscribers» (externalId=100). (2) Переименовать её в админке или импортировать из другой панели услугу с тем же названием и тем же тенантом. (3) Повторный импорт внешней услуги с совпадающим названием → «успешно», счётчик 0, строка в `Service` не появилась.

**Сценарий проверки после исправления.** Экшен возвращает детализацию: `{ imported: N, skipped: [{ externalId, name, reason: 'DUPLICATE_SLUG' | 'REMOVED_BY_PROVIDER' | 'INVALID_RATE' | 'ALREADY_EXISTS' }] }`. Мастер показывает развёрнутый отчёт с причинами по каждой пропущенной услуге; коллизии slug автоматически разрешаются суффиксом (`-2`, `-<extId>`), если администратор включил опцию «разрешать дубли названий».

### AUD-05 [P0] Мульти-тенантные фильтры каталога несогласованы: услуга есть в БД, но невидима

**Симптом.** После импорта (например, с целевым тенантом `flux` или «оба») администратор открывает витрину/каталог и не находит услуг. В админ-каталоге они видны или не видны в зависимости от переключателя тенанта; на публичной витрине — в зависимости от домена.

**Корневая причина — матрица из четырёх несогласованных фильтров.**

**(а) Список категорий в мастере импорта не фильтруется по тенанту вообще:**

```ts
// src/services/admin/provider.service.ts:140-146
async listCategories() {
  const rows = await db.category.findMany({           // ← нет where по tenantId
    orderBy: [{ network: { slug: 'asc' } }, { sort: 'asc' }],
    include: { network: true },
  });
  return rows;
}
```

Администратор тенанта `smmplan` видит и может выбрать категорию, принадлежащую `flux`. `ensureTaxonomyTenantAccess` при этом «расшаривает» выбранную категорию и её сеть на `all` — то есть импорт **тихо меняет видимость чужой таксономии**.

**(б) Публичное дерево каталога фильтрует сеть, но не фильтрует категории и услуги внутри условия видимости:**

```ts
// src/actions/order/catalog.ts:14-35
db.network.findMany({
  where: {
    isActive: true,
    tenantId: { in: [tenantId, 'all'] },
    categories: { some: { services: { some: { isActive: true, isQuarantined: false } } } } // ← tenantId услуги НЕ проверяется
  },
  include: {
    categories: {
      where: { services: { some: { isActive: true, isQuarantined: false } } },              // ← и здесь
      ...
```

Категория попадает в витрину, если в ней есть хоть одна активная услуга **любого** тенанта.

**(в) Список услуг категории фильтруется по тенанту строго:**

```ts
// src/actions/order/catalog.ts:39-53
db.service.findMany({
  where: {
    categoryId, isActive: true, isQuarantined: false,
    tenantId: { in: [tenantId, 'all'] },   // ← а здесь уже фильтр
    ...
```

**Комбинация (б)+(в) даёт «пустую категорию»:** дерево показывает категорию (потому что в ней есть услуги другого тенанта), но при открытии список пуст, потому что услуг текущего тенанта в ней нет. Для пользователя это выглядит ровно как «услуги не появляются в каталоге».

**(г) Админ-каталог выбирает тенанта по собственным правилам** (`resolveAdminTenantContext` → для OWNER без параметра `?tenant=` берётся домен `x-tenant-id`): администратор, открывший панель с «не того» домена, не увидит импортированные в другой тенант услуги, хотя переключатель `TenantSwitcher` рядом присутствует.

Отдельно отметим, что импорт с `targetTenantId: 'both'` опирается на жёстко зашитые литералы `'smmplan' | 'flux'` (Zod enum в экшене, типы в сервисе) — появление третьего бренда требует правок в трёх слоях, а не конфигурации.

**Сценарий воспроизведения.** Импортировать услуги в тенант `flux`, категории дать тенант `smmplan` (или наоборот). Открыть витрину на домене, чей тенант не совпадает с тенантом услуг: дерево категорий на месте, список услуг пуст.

**Сценарий проверки после исправления.** Во всех четырёх точках (listCategories импорта, дерево сетей, список услуг категории, админ-листинг) действует единое правило видимости (`tenantId IN (текущий, 'all')`); категории «чужих» тенантов не предлагаются в мастере импорта либо помечены; изменение видимости таксономии выполняется только явным действием администратора, а не побочным эффектом импорта; после импорта «в оба тенанта» услуги отображаются на обоих доменах.

### AUD-06 [P0] Состояние «теневой каталог пуст» не отображается: пустой экран вместо подсказки

**Симптом.** Первый визит в мастер импорта после подключения нового провайдера: сводка показывает нули, таблица — пустая, без объяснений. Администратор не понимает, что нужно нажать «Обновить каталог», и считает импорт сломанным.

**Корневая причина.** Сервер возвращает явный маркер и текстовое пояснение:

```ts
// import-cherry-pick.ts:39-42
const shadowCount = await db.shadowService.count({ where: { providerId } });
if (shadowCount === 0) {
  return { success: false, error: 'Теневой каталог пуст. Нажмите «Загрузить каталог».', emptyCache: true };
}
```

Клиентский код ловит маркер, но сообщение отбрасывает, а само состояние никогда не рендерится:

```tsx
// import-wizard.tsx:254-256
} else if ('emptyCache' in res && res.emptyCache) {
  setIsEmptyCache(true);      // ← состояние установлено...
  setServices([]);
}
```

Поиск `isEmptyCache` по всем компонентам импорта даёт единственное вхождение — строку объявления (155). **Ни один `render`-путь не читает это состояние.** Единственная зацепка для пользователя — маленькая кнопка «Обновить каталог» в шапке сводки, о назначении которой при пустой таблице догадаться сложно.

Примечательно, что e2e-тест ожидает полноценную заглушку: `await expect(adminPage.getByText('Каталог провайдера пуст').first()).toBeVisible()` и кнопку `«Загрузить каталог»` — то есть такой экран существовал в замысле (или был утерян при рефакторинге), но в текущем коде отсутствует.

**Сценарий воспроизведения.** Создать провайдера, не нажимая «Обновить» в таблице, открыть `/admin/providers/import` → пустая таблица без сообщений.

**Сценарий проверки после исправления.** При пустом теневом каталоге мастер показывает информационный блок «Каталог провайдера пуст» с кнопкой «Загрузить каталог», которая вызывает `fetchExternalServices(providerId)` (синхронизацию), показывает прогресс и по завершении подгружает первую страницу услуг. e2e-кейс с `getByText('Каталог провайдера пуст')` проходит.

### AUD-07 [P1] Публичная категория обрезается до 100 услуг

**Симптом.** В категории с большим количеством услуг (типично после массового импорта: «Подписчики Telegram» с 200+ вариантами от провайдера) часть услуг на витрине отсутствует. В админ-каталоге они есть, на витрине — нет.

**Корневая причина.** Публичный запрос категории жёстко ограничен:

```ts
// src/actions/order/catalog.ts:37-57
const PAGE_SIZE = 100;
...
const services = await db.service.findMany({
  where: { categoryId, isActive: true, isQuarantined: false, tenantId: { in: [tenantId, 'all'] }, ... },
  orderBy: { rate: 'asc' },
  take: PAGE_SIZE + 1
});
if (services.length > PAGE_SIZE) {
  console.warn(`[catalog] Category ${categoryId} has ${services.length} services, truncating tail to ${PAGE_SIZE}`);
}
return services.slice(0, PAGE_SIZE);   // ← тихое усечение
```

Порядок `rate: 'asc'` означает, что отбрасываются **самые дорогие** услуги категории. Предупреждение пишется только в логи сервера. Пагинации на витрине категории нет — пользователь даже не подозревает об усечении. Аналогичный лимит продублирован в `getServicesByCategoryAction` (`take: 100`).

**Сценарий воспроизведения.** Импортировать 120+ услуг в одну категорию → на витрине категории отображается не более 100 (дешёвых).

**Сценарий проверки после исправления.** Витрина категории либо пагинируется/подгружается лениво, либо лимит поднят и о включении лимита сообщается администратору; количество услуг в категории на витрине совпадает с количеством активных услуг в админ-каталоге (с учётом тенанта).

### AUD-08 [P1] После импорта не инвалидируется кэш витрины; revalidatePath указывает на несуществующий маршрут

**Симптом.** Импорт прошёл успешно, администратор видит услугу в админ-каталоге, но на витрине `/services/...` она появляется с задержкой (до минуты и более), что на практике воспринимается как «не появилась».

// src/actions/order/catalog.ts:32-34
[`public-catalog-networks-v3-${tenantId}`],
{ revalidate: 60, tags: ['catalog', `catalog-${tenantId}`, `networks-${tenantId}`] }

revalidatePath("/admin/catalog");
revalidateTag("catalog", 'default');
revalidateTag("services", 'default');
```

А экшен импорта — нет:

// src/actions/admin/providers/import-cherry-pick.ts:396-398
revalidatePath('/admin/providers/import');

Ошибка с `/admin/services` маскируется тем, что `revalidatePath` на несуществующий путь не бросает исключений.

**Сценарий проверки после исправления.** После успешного импорта: `revalidateTag('catalog')` + `revalidateTag('services')` + `revalidatePath('/admin/catalog')`; витрина показывает новую услугу при первом же открытии после импорта (в пределах секунд).

### AUD-09 [P1] RBAC: секции `catalog` и `providers` перемешаны

**Симптом.** Сотрудник с выданным правом «Провайдеры» не может управлять провайдерами; сотрудник с правом «Каталог» не видит балансы провайдеров. Владельцу приходится выдавать «всё подряд».

**Корневая причина.** Модель RBAC различает секции `catalog` и `providers` (`StaffPermissionSection`, сид `scripts/seed-rbac.ts` создаёт обе). Но фактические проверки разошлись:

| Операция | Проверяемая секция | Файл |
|---|---|---|
| Layout `/admin/providers/**` | `catalog` | `providers/layout.tsx` |
| create/update/sync/toggle провайдера | `catalog` | `providers/crud.ts` |
| Балансы и ликвидность провайдеров | `providers` | `providers/balance.ts` |

Итог: гранулярность «управление панелями» и «каталог» неразделимы в одну сторону и разнесены в другую. Для ролей OWNER/ADMIN действует bypass, поэтому владелец проблемы не ощущает — она проявится при делегировании.

**Сценарий проверки после исправления.** Матрица «операция → секция» выровнена (рекомендация: всё управление провайдерами — секция `providers`; листинг каталога — `catalog`); тест RBAC на каждую операцию; сотрудник с `providers:edit` проходит CRUD провайдеров, но не трогает каталог, и наоборот.

### AUD-10 [P1] updateProvider затирает metadata и показывает сырые ошибки БД

**Симптом.** (а) При сохранении провайдера с дублирующимся именем появляется тост с техническим текстом вида «Unique constraint failed on the constraint: Provider_name_key». (б) Любые сторонние ключи в `metadata` провайдера silently теряются при сохранении из формы.

**Корневая причина.** Экшен строит `updateData.metadata` только из поля формы:

```ts
// crud.ts:161-170
const updateData: Record<string, unknown> = {
  ...
  metadata: {
     mapping: data.mapping || null      // ← перезапись всего JSON-поля
  },
  ...
};
```

Схема комментирует `metadata` как `{ httpMethod, requestType, headers, keyField, actionField }` — потенциальное место для расширенных настроек интеграций; при текущей реализации любой сторонний ключ в `metadata` уничтожается сохранением формы. Дополнительно catch-блок возвращает `err.message` как есть:

```ts
} catch (err) {
  const errorMsg = err instanceof Error ? err.message : String(err);
  return { success: false as const, error: errorMsg || '...' };
}
```

Ошибки Prisma `P2002` (уникальность имени), `P2025` (запись не найдена), ошибки SSRF-гуарда приходят пользователю в исходном виде, по-английски, без указания поля.

**Сценарий проверки после исправления.** (1) Сохранение провайдера с уже существующим именем → человекочитаемое сообщение у поля «Название»: «Панель с таким названием уже подключена». (2) `metadata` мержится (`{ ...existing, mapping }`), а не заменяется. (3) Ошибка P2025 → «Провайдер не найден (возможно, уже удалён)».

### AUD-11 [P1] refreshShadowCatalog: неатомарная перезапись; live-check делает импорт зависимым от доступности API провайдера

**Корневая причина (два аспекта).**

**(а) Wipe-then-insert без транзакции:**

```ts
// catalog.service.ts:466-476
await db.shadowService.deleteMany({ where: { providerId: providerDbRecord.id } });
const chunkSize = 1000;
for (let i = 0; i < servicesToCreate.length; i += chunkSize) {
  const chunk = servicesToCreate.slice(i, i + chunkSize);
  await db.shadowService.createMany({ data: chunk, skipDuplicates: true });
}
```

Сбой между `deleteMany` и завершением вставок (таймаут БД, OOM, рестарт) оставляет теневой каталог частично заполненным. Защита от «усыхания» (`SHRINK_THRESHOLD` на следующем цикле) сработает и заблокирует повторную синхронизацию ошибкой `PROVIDER_CATALOG_SHRUNK_ABNORMALLY` — администратор попадает в ловушку, требующую ручной чистки `ShadowService`.

**(б) Полный live-request каталога внутри импорта** (`providerInstance.getServices()` на каждый вызов `importServices`): при недоступности API провайдера в момент подтверждения импорта весь импорт падает целиком, даже если теневой каталог валиден и свеж. Для панелей с большими каталогами это ещё и заметная задержка на финальном шаге мастера.

**Сценарий проверки после исправления.** Синхронизация выполняется в транзакции (или через upsert-by-batch + удаление отсутствующих); сбой посреди процесса не оставляет полусинхронизированный каталог; импорт использует свежесть теневого каталога (`updatedAt` ShadowService) и делает live-check опциональным/асинхронным, а не блокирующим.

### AUD-12 [P1] e2e-тесты импорта дрейфовали от реализации: ожидания описывают несуществующие функции

**Корневая причина.** Кейс «Admin can import service via Cherry-Pick Wizard» (`e2e/providers.spec.ts:113-229`) ожидает: текст «Каталог провайдера пуст» (в UI отсутствует — AUD-06), кнопку «Загрузить каталог» (отсутствует), конвертацию наценки 75% → `markup=1.75` (отсутствует — AUD-03). Кейс «Provider CRUD» (`:231+`) проверяет Create/Read/Update и аудит-логи, но **не содержит шага Delete** — в полном соответствии с отсутствием самой функции (AUD-01), но в противоречии с собственным названием.

Дополнительно тест очищает Redis-ключ `provider:${id}:catalog`, тогда как текущая реализация теневого каталога хранится в таблице `ShadowService` — тест оперирует устаревшей инфраструктурой.

**Следствие.** Либо эти тесты красные и «замаскированы» (не запускаются в CI-критичном контуре), либо маркированы skip. В обоих случаях регрессию импорта система тестов не ловит — что и позволило AUD-03/06 жить в продакшене.

**Сценарий проверки после исправления.** `npx playwright test e2e/providers.spec.ts` зелёный на актуальном коде; в кейс CRUD добавлен шаг удаления провайдера; тестовые хелперы работают с `ShadowService`, а не с Redis-ключами.

### AUD-13 [P1] Скрытый принудительный минимум наценки ×3.0 при импорте

**Корневая причина.** Независимо от введённой администратором наценки сервис молча поднимает её до константы:

```ts
// catalog.service.ts:919-922
if (effectiveMarkup < SAFETY_FLOOR_MARKUP) {
  effectiveMarkup = SAFETY_FLOOR_MARKUP;   // SAFETY_FLOOR_MARKUP = 3.0
}
```

При этом пользовательский контракт валидации разрешает 1.0–10.0, а экономический смысл константы — «покрытие налогов, эквайринга и маржи» (`financial-constants.ts:119`). Администратор, задавший ×1.5 на дешёвой услуге (хочет aggressive pricing), получает ×3.0 без единого предупреждения; отчёт импорта не отражает корректировку. Дополнительная семантическая путаница: в `financial-constants.ts` формула `SafetyPrice = Cost × (1 + SAFETY_FLOOR_MARKUP) / (1 − TOTAL_MANDATORY_DEDUCTIONS)` трактует 3.0 как +300%, тогда как в импорте тот же литерал — множитель ×3.0 (+200%).

**Сценарий проверки после исправления.** Импорт с наценкой ниже пола либо явно запрещён с понятным сообщением («минимальная наценка ×3.0 для покрытия издержек — увеличить или включить исключение»), либо выполняется с индикацией в отчёте импорта: «наценка скорректирована с ×1.5 до ×3.0 (safety floor)». Семантика константы унифицирована по всему коду.

### AUD-14 [P2] Зомби-статусы и карантин незаметно прячут услуги из витрины

**Корневая причина.** Витрина фильтрует `isActive: true, isQuarantined: false` и `cooldownUntil`. Синхронизация каталога автоматически ставит `cooldownReason: ZOMBIE_AUTO_DISABLED/ZOMBIE_ARCHIVED` и отправляет услуги в карантин при скачке цен > порога. Это осмысленные бизнес-механики (финансовая безопасность), но в сочетании с AUD-04 (отсутствие отчётности) администратор не получает сводки «почему в категории стало меньше услуг». Существующие страницы `/admin/catalog/quarantine` и `/admin/catalog/drift` частично решают задачу, однако из импорта/каталога нет сквозной видимости: «выбрано 30 → импортировано 12 → 6 в карантине → 4 зомби».

**Рекомендация.** Единый «журнал жизни услуги» (импорт → карантин → зомби → возврат) и счётчики этих состояний в шапке админ-каталога.

### AUD-15 [P2] Импорт блокируется, пока каждой услуге не назначена категория вручную

**Корневая причина.** `handleStartImport` требует категорию для каждой выбранной услуги:

```tsx
// import-wizard.tsx:407-418
const missing = new Set<string>();
selectedIds.forEach((id) => {
  const catId = selectedCategories[id] || autoMappedCategories[id];
  if (!catId) missing.add(id);
});
if (missing.size > 0) {
  setMissingCategoryIds(missing);
  setError(`Необходимо сопоставить категорию для ${missing.size} выбранных услуг перед импортом.`);
  return;
}
```

AI-автомаппинг (`autoMapCategory`) присваивает категорию только при `maxScore >= 10` и строгой совместимости типов; всё остальное попадает на ручной труд. При выборе 300 услуг с 60 нераспознанными администратор выполняет 60 ручных назначений по одной, иначе импорт не стартует вовсе. Отсутствуют: «импортировать в категорию по умолчанию», «импортировать как черновик без категории» (в БД `categoryId` обязателен, но можно создать служебную категорию-инбокс), пакетное назначение по фильтру (существует только на текущей странице).

**Рекомендация.** Кнопка «Импортировать нераспределённые в [категорию]» и/или черновой статус услуги (`isDraft`) с последующим пакетным распределением в каталоге.

## 7. Сценарии приёмочной проверки (чек-лист для владельца)

### 7.1 Провайдеры

- [ ] Создать провайдера (mock или реальный) → появился в таблице, статус активен
- [ ] Изменить имя на уже существующее → понятная ошибка у поля «Название», данные не потеряны
- [ ] Сохранить форму без изменения API-ключа → ключ не сломан (проверка соединения проходит)
- [ ] **Удалить** провайдера без услуг → исчез из таблицы, в аудите запись PROVIDER_DELETE
- [ ] **Удалить** провайдера с услугами и маршрутами → модалка показала счётчики; после подтверждения: услуги живы (providerId=NULL), маршруты удалены, заказы целы
- [ ] Деактивировать провайдера → его услуги не принимают новые заказы (существующие дозавершаются)

### 7.2 Импорт

- [ ] Открыть импорт при пустом теневом каталоге → экран «Каталог провайдера пуст» + кнопка «Загрузить каталог»
- [ ] **Выбрать провайдера из списка** → таблица и счётчики переключились на его каталог
- [ ] Оставить наценку по умолчанию → импорт успешен, `markup` в БД соответствует ожиданию (200% → ×3.0)
- [ ] Ввести наценку 75% → в БД `markup = 1.75`
- [ ] Ввести 0 → автокалькуляция по лестнице цен
- [ ] Импортировать услуги с одинаковыми названиями → все созданы (slug продублирован суффиксом) либо в отчёте указаны как пропущенные с причиной
- [ ] Отчёт импорта показывает: импортировано N, пропущено M (причины по каждой)

## 9. Замечание о границах аудита

Аудит сфокусирован на заявленных болевых зонах и выполнялся статически (без запуска продакшн-окружения). Сценарии воспроизведения выведены из трассировки кода и потому детерминированы, но перед началом работ рекомендуется прогнать чек-лист раздела 7 на тестовом стенде, чтобы зафиксировать фактические симптомы «до». Сопутствующие подсистемы (заказы, платежи, работники синхронизации) затрагивались только в части, влияющей на каталог и провайдеров. Отдельные хранящиеся в репозитории отчёты предыдущих итераций (`ADMIN_COMPLETENESS_AUDIT.md`, `admin_usability_audit_report.md`, `CATALOG_MODULE_AUDIT.md` и др.) не переоценивались; настоящий документ опирается исключительно на текущее состояние кода ветки `main`.
