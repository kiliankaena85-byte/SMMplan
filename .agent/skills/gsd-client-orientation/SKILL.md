# 🎯 Client-Orientation Manifest (Smmplan)

Этот скилл — **единственный источник правды** для оценки клиентоориентированности любого пользовательского интерфейса в проекте Smmplan. Каждое UI-решение проходит проверку по 12 взвешенным критериям с примерами, антипримерами и пограничными случаями.

---

## Философия: Два Главных Закона

### Закон 1: Принцип Нулевого Молчания

> **🔴 Система НИКОГДА не молчит.**
> Каждое действие пользователя получает видимую, понятную, помогающую реакцию.
> Если система не может выполнить действие — она ОБЪЯСНЯЕТ почему и ПОДСКАЗЫВАЕТ что делать.

Антипаттерн «disabled button» — это молчаливый отказ. Пользователь не понимает:
- ПОЧЕМУ кнопка серая?
- ЧТО нужно сделать?
- ГДЕ проблема?

Правильный паттерн: кнопка **всегда активна**, но при нажатии показывает конкретное руководство к действию.

### Закон 2: Свобода Пути Пользователя

> **🔴 Мы НЕ навязываем жёсткий порядок действий.**
> Пользователь сам решает как ему удобно:
> 1. Вставить ссылку → система подберёт тарифы (link-first)
> 2. Выбрать тариф → потом вставить ссылку (browse-first)
> 3. Любая комбинация — всё работает

Антипаттерн «принудительный wizard» — это навязывание одного единственного пути. Пользователь знает лучше нас, что ему нужно. Наша задача — поддержать ЛЮБОЙ путь.

## 12 Критериев Клиентоориентированности

Каждому критерию присвоен весовой коэффициент (P0 = 3, P1 = 2, P2 = 1) для обеспечения взвешенной математической оценки.

### Критерий 1: 🚫 Нет Молчаливого Отказа (No Silent Rejection)

- **Вес**: P0-CRITICAL (Вес: 3)

**Определение**: Система никогда не отказывает молча. Каждая ошибка или блокировка сопровождается четким объяснением, рекомендацией к действию и фокусом на элементе. 

**Связанный закон UX**: *Закон Фиттса (Fitts's Law)* — размер интерактивных целей должен соответствовать удобству нажатия. Минимальный физический размер touch target на мобильных устройствах должен составлять не менее 24×24px (минимальный порог WCAG 2.2 AA) или 44×44px (повышенный AAA/iOS HIG стандарт с учетом окружающих отступов).

#### ✅ Рекомендуемый React 19 паттерн для Критерия 1
```tsx
'use client';

import React, { useRef } from "react";
import { toast } from "react-hot-toast";

export function OrderButton({ selectedService, url }: { selectedService: any; url: string }) {
  const urlInputRef = useRef<HTMLInputElement>(null);

  const handleCheckout = () => {
    if (!selectedService) {
      toast.error("Выберите услугу из каталога ниже ↓", { id: "checkout-err" });
      const catalog = document.getElementById("catalog-section");
      catalog?.scrollIntoView({ behavior: "smooth" });
      return;
    }
    if (!url.trim()) {
      toast.error("Вставьте ссылку на канал или пост для продвижения", { id: "checkout-err" });
      urlInputRef.current?.focus();
      return;
    }
    // Логика перехода к оплате...
  };

  return (
    <button 
      onClick={handleCheckout}
      className="w-full min-h-[48px] px-4 py-2 bg-primary text-foreground rounded-[10px] transition-all duration-200 hover:scale-[1.02] focus-visible:ring-2 focus-visible:ring-primary focus-visible:outline-none"
    >
      Оплатить заказ
    </button>
  );
}
```

#### ❌ Ошибочные антипримеры для Критерия 1
```tsx
// АНТИПАТТЕРН: disabled кнопка — пользователь не понимает почему
<button disabled={!selectedService || !url}>Оплатить</button>

// АНТИПАТТЕРН: прямой доступ к DOM через getElementById внутри React вместо useRef
document.getElementById("landing-url")?.focus();
```

#### 🔶 Пограничные случаи для Критерия 1
- **Допустимо**: `disabled` при `isSubmitting` — пользователь видит спиннер, понимает что идёт обработка.
- **Допустимо**: Ссылка на кнопке «Назад к услугам» на мобильном имеет `disabled` во время отправки запроса.
- **Недопустимо**: Любое отключение кнопки по причине «не заполнены обязательные поля» без вывода текста ошибки.

### Критерий 2: 🧠 Минимум Когнитивной Нагрузки (Minimum Cognitive Load)

- **Вес**: P1 (Вес: 2)

**Определение**: Интерфейс ведет себя предсказуемо и не заставляет пользователя расшифровывать шаги.

**Связанный закон UX**: *Закон Хика (Hick's Law)* — время принятия решения увеличивается с ростом числа альтернатив. *Закон Миллера (Miller's Law)* — кратковременная память человека способна удерживать в среднем 7±2 элемента.

#### ✅ Рекомендуемый паттерн для Критерия 2
- Пошаговый индикатор: `1. Ссылка → 2. Категория → 3. Услуга → 4. Оплата`
- Группировка длинных списков услуг по пользовательским целям (Подписчики отдельно, Лайки/Просмотры отдельно).
- Четкие названия действий на кнопках: «Показать тарифы →» вместо абстрактного «Начать».

#### ❌ Ошибочный паттерн для Критерия 2
- Вывод всего хаотичного списка из 200 тарифов без фильтров и категорий.
- Текст кнопки «Далее», когда совершается списание средств.

---

### Критерий 3: ⚡ Минимум Действий до Результата (Frictionless Flow)

- **Вес**: P0 (Вес: 3)

**Определение**: Сокращение физических и умственных шагов от открытия страницы до оформления заказа. Золотой стандарт: **3 шага до оплаты**.

#### ✅ Рекомендуемый паттерн для Критерия 3
- Гостевое оформление (Guest Checkout) без обязательной авторизации.
- Поле сбора email интегрировано прямо в чекаут форму (inline), без модальных всплывающих окон.
- Автоматический выбор единственного тарифа, если в категории представлена только одна услуга.

#### ❌ Ошибочный паттерн для Критерия 3
- Требование зарегистрироваться и подтвердить почту для покупки на 50 рублей.
- Отдельное модальное окно для ввода промокода или почты, прерывающее флоу клика на «Оплатить».

---

### Критерий 4: 📢 Мгновенная Обратная Связь (Instant Feedback)

- **Вес**: P0 (Вес: 3)

**Определение**: Любое взаимодействие с интерфейсом должно давать визуальный отклик в течение **200ms**.

#### ✅ Рекомендуемый паттерн для Критерия 4
- Использование анимационных скелетонов (Skeleton Loading) при подгрузке списка услуг.
- Четкое визуальное изменение активного состояния выбранного тарифа (`transition-all duration-200 scale-[1.01] ring-2 ring-primary`).

#### ❌ Ошибочный паттерн для Критерия 4
- Нажатие на кнопку выбора тарифа не дает визуальных изменений до момента ответа от API.
- Замена контента на странице без плавных переходов или лоадеров (вызывает визуальный скачок).

---

### Критерий 5: 🎭 Прогрессивное Раскрытие (Progressive Disclosure)

- **Вес**: P1 (Вес: 2)

**Определение**: Информация выдается порциями по мере продвижения пользователя, но без жесткого перекрытия свободы выбора (browse-first).

#### ✅ Рекомендуемый паттерн для Критерия 5
- На мобильных: последовательное раскрытие секций (Вставьте ссылку → Появляется выбор соцсети → Открывается тарифная сетка).
- Использование PRO-режима (opt-in переключатель) для опытных пользователей, выводящего всю информацию сразу.
- **Cold Start (Пустая база)**: Если услуг в базе нет, выводится понятный пустой статус (Empty State): «Каталог обновляется, это займет 2 минуты» с кнопкой «Обновить», а не белый экран.

#### ❌ Ошибочный паттерн для Критерия 5
- Скрытие цен или описания тарифов до ввода ссылки на десктопной версии каталога.

---

### Критерий 6: 🤖 Автоматизация Очевидного (Automation of the Obvious)

- **Вес**: P1 (Вес: 2)

**Определение**: Автоматический разбор и нормализация данных пользователя для устранения ручной рутины.

#### ✅ Рекомендуемый паттерн для Критерия 6
- Автоопределение социальной сети при вставке ссылки (например, `t.me/durov` → переключение на Telegram).
- Автоматическая очистка URL от мусорных трекинговых параметров (`?utm_source=...`, `#fragment`).
- Установка дефолтного количества заказа равным минимальному (`minQty`) при выборе услуги.

#### ❌ Ошибочный паттерн для Критерия 6
- Требование от пользователя вручную указать платформу "Telegram" после того, как он вставил ссылку на телеграм-канал.

---

### Критерий 7: 🛡️ Защита от Ошибок (Error Prevention)

- **Вес**: P0 (Вес: 3)

**Определение**: Система проектируется так, чтобы минимизировать вероятность совершения ошибки.

#### ⚖️ Разрешение Конфликта C1 vs C7 для Критерия 7
Существует напряжение между Критерием 1 (кнопка всегда активна, давая обратную связь) и Критерием 7 (предотвращение неверного ввода). 
**Правило разрешения**: Мы не блокируем поле ввода и кнопку. Но если пользователь вводит некорректное значение (например, количество больше максимума `maxQty` или меньше `minQty`), мы **НЕ сбрасываем его молча**. Мы мягко корректируем значение до лимита и **ОБЯЗАТЕЛЬНО выводим тост/микро-плашку** с объяснением причин.

#### ✅ Рекомендуемый React 19 паттерн для Критерия 7
```tsx
'use client';

import React, { useState } from "react";
import { toast } from "react-hot-toast";

export function QuantitySelector({ minQty, maxQty }: { minQty: number; maxQty: number }) {
  const [qty, setQty] = useState(minQty);

  const handleBlur = (e: React.FocusEvent<HTMLInputElement>) => {
    let val = Number(e.target.value);
    if (isNaN(val) || val < minQty) {
      setQty(minQty);
      toast.error(`Минимальный заказ: ${minQty} шт. Значение скорректировано.`, { id: "qty-clamp" });
    } else if (val > maxQty) {
      setQty(maxQty);
      toast.error(`Максимальный заказ: ${maxQty} шт. Значение ограничено лимитом.`, { id: "qty-clamp" });
    } else {
      setQty(val);
    }
  };

  return (
    <div className="flex flex-col gap-2">
      <label className="text-sm text-muted-foreground">Укажите количество</label>
      <input 
        type="number"
        defaultValue={qty}
        onBlur={handleBlur}
        className="w-full h-[44px] px-3 bg-card border-none rounded-[10px] text-foreground focus:ring-2 focus:ring-primary"
      />
    </div>
  );
}
```

#### ❌ Ошибочный паттерн для Критерия 7
- Молчаливый сброс или обрезка некорректного значения без информирования пользователя.
- Отправка формы с неверными лимитами, завершающаяся системным сбоем сервера.

### Критерий 8: 🌊 Восстанавливаемость Состояния (State Recovery)

- **Вес**: P2 (Вес: 1)

**Определение**: Сохранение прогресса ввода пользователя для защиты от случайных прерываний (закрытие вкладки, обновление страницы).

#### ✅ Рекомендуемый паттерн для Критерия 8
- Использование `sessionStorage` (изолированного в рамках вкладки) для сохранения черновика заказа.
- Автоматическое восстановление выбранной вкладки соцсети и ссылки при перезагрузке страницы.

#### ❌ Ошибочный паттерн для Критерия 8
- Случайный рефреш (F5) стирает длинную ссылку и заставляет настраивать параметры заново.

#### ⚠️ Исключения для Критерия 8
- **Категорически запрещено** сохранять в хранилище: пароли, платежные данные, email и одноразовые промокоды.

---

### Критерий 9: 💎 Ценностное Предложение в Каждой Точке (Value Density)

- **Вес**: P1 (Вес: 2)

**Определение**: Вывод только подтвержденных, честных и ценных для пользователя данных без визуального шума и манипуляций.

#### ⚠️ Принцип честности данных (Anti-Fabrication) для Критерия 9
Запрещено выдумывать метрики (например, фейковые оценки 4.9 или обобщенную скорость «Супер-быстро»), если они не подтверждены логами реальных заказов. Фабрикация данных разрушает доверие.
- **Рейтинг**: Показывать только при наличии реальной системы отзывов.
- **Скорость (SLA)**: Показывать только реальное время старта на основе последних 100 заказов. Если неизвестно — писать «Зависит от загрузки сети».
- **Гарантия**: Выводить только точный срок, заданный админом для конкретной услуги.

#### ❌ Ошибочный паттерн для Критерия 9
- Добавление ко всем услугам одинаковой плашки «Гарантия 30 дней», если на некоторые типы накрутки гарантия провайдером не предоставляется.

### Критерий 10: 📱 Адаптивность и Отзывчивость (Adaptivity)

- **Вес**: P0 (Вес: 3)

**Определение**: Удобство использования на экранах любой ширины (от 320px до 4K).

#### ✅ Рекомендуемый паттерн для Критерия 10
- Кнопки действий на мобильном имеют высоту $\ge 44\text{px}$ и расположены в зоне досягаемости большого пальца (bottom sticky layout).
- Использование CSS grid с авто-разметкой (`grid-cols-1 md:grid-cols-2 lg:grid-cols-3`).

#### ❌ Ошибочный паттерн для Критерия 10
- Горизонтальный скролл на экранах мобильных телефонов.
- Элементы перекрывают друг друга при изменении разрешения.

---

### Критерий 11: 💬 Контекстная Помощь (Contextual Assistance)

- **Вес**: P1 (Вес: 2)

**Определение**: Обучение пользователя правильным действиям непосредственно в момент совершения интеракции.

#### ✅ Рекомендуемый паттерн для Критерия 11
- Динамический плейсхолдер в поле ввода, меняющийся в зависимости от выбранной соцсети (`https://t.me/durov` для Telegram, `https://vk.com/id1` для VK).
- Тонкий виджет-подсказка «Как скопировать ссылку», показывающийся только при пустом поле ввода.

#### ❌ Ошибочный паттерн для Критерия 11
- Огромный статичный блок текстовой инструкции над формой, который сдвигает контент вниз.

---

### Критерий 12: 🔐 Доверие и Безопасность (Trust & Safety)

- **Вес**: P1 (Вес: 2)

**Определение**: Формирование ощущения защищенности при совершении транзакции.

**Связанный закон UX**: *Peak-End Rule (Закон кульминации и финала)* — пользователь запоминает опыт по самой яркой точке и по его завершении. Финал заказа (оплата) должен быть максимально комфортным и безопасным.

#### ✅ Рекомендуемый паттерн для Критерия 12
- Размещение сертифицированных логотипов защищенных платежных шлюзов (МИР, СБП) непосредственно под финальной кнопкой оплаты.
- Текст «Безопасный платеж. Мы не храним данные карт».
- Итоговая сумма платежа четко видна на самой кнопке действия: «Оплатить 120 ₽».

#### ❌ Ошибочный паттерн для Критерия 12
- Кнопка «Купить» без отображения финальной стоимости с учетом промокода.
- Отсутствие ссылок на Политику конфиденциальности и Условия оферты в подвале чекаут-зоны.

## Scope boundaries

Скилл применяется исключительно к **клиентским, публичным интерфейсам** Smmplan:
- Форма заказа (SmartOrderForm), мобильный и десктопный каталоги.
- Флоу чекаута, корзины, окна оплаты и ввода промокодов.
- Форма создания тикетов поддержки в личном кабинете.

Скилл **НЕ** применяется к:
- Панели администратора (используется специализированный `gsd-enterprise-ux-manifest`).
- Внутренней структуре API и серверным обработчикам (actions).
- Системным Telegram-ботам (ограничены API мессенджера).

## Protocol: Аудит компонента

### Step 1 — Классификация
Определить тип компонента: `landing` | `checkout` | `form` | `wizard` | `modal`

### Step 2 — Оценка по 12 критериям
Для каждого из 12 критериев выставить статус:
- 🟢 **PASS** — полное соответствие.
- 🟡 **WARN** — частичное соответствие, есть шероховатости.
- 🔴 **FAIL** — критическое нарушение, создающее трение для пользователя.
- ⬜ **N/A** — критерий неприменим к данному типу компонента.

### Step 3 — Взвешенный расчет балла
Используется математическая формула, учитывающая критичность (P0/P1/P2) каждого критерия:

1. Назначить числовые веса применимым критериям:
   - **P0** = 3 балла
   - **P1** = 2 балла
   - **P2** = 1 балл
2. Вычислить максимально возможный вес:
   $$\text{MaxWeight} = \sum \text{Applicable Weights}$$
3. Рассчитать набранный вес:
   - `PASS` = полные баллы критерия ($1.0 \times \text{Weight}$)
   - `WARN` = половина баллов ($0.5 \times \text{Weight}$)
   - `FAIL` = 0 баллов
4. Найти итоговый балл:
   $$\text{Score} = \frac{\text{EarnedWeight}}{\text{MaxWeight}} \times 10$$

> [!IMPORTANT]
> **Минимальный порог применимости**: Если применимо менее **4 критериев**, то числовой балл не рассчитывается. Выставляется статус: **«Недостаточно данных для оценки (N/D)»**.

#### Таблица диапазонов оценок:
*   **9.0 – 10.0**: 🟢 **Эталон клиентоориентированности** (UI идеален, нет трения).
*   **7.0 – 8.9**: 🟢 **Хороший уровень** (допустимы мелкие косметические правки).
*   **5.0 – 6.9**: 🟡 **Средний уровень** (требуется доработка P1/P0 элементов).
*   **3.0 – 4.9**: 🔴 **Плохой уровень** (серьезные барьеры для оформления заказа).
*   **0.0 – 2.9**: 🔴 **Критический уровень** (интерфейс враждебен к клиенту).
