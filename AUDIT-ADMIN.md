## 1. Резюме для руководителя (Executive Summary)

### 1.1 Главный вывод

**Каталог/провайдеры/импорт (первый аудит) были худшими по UX, но остальная админка хуже по консистентности системы прав.** Код business-логики заказов и финансов в целом качественный (транзакции, идемпотентные возвраты, аудит), но **система разграничения доступа RBAC рассинхронизирована на 4 уровнях**: гейты страниц, проверки экшенов, сид-данные ролей и фильтрация сайдбара используют разные наборы секций. Следствие — делегирование работы сотрудников практически невозможно без ручных правок БД:

| Роль (из сида) | Что должна делать | Что фактически может |
|---|---|---|
| **Support** | Отвечать на тикеты | Видит страницу тикетов, но **не может отправить ответ** — экшен требует секцию `support`, которую не имеет никто, кроме OWNER/ADMIN (ADM-01) |
| **Manager** | Управлять клиентами | Не видит пункт «Клиенты» в меню; по прямой ссылке видит страницу, но **бан/пароль/удаление — Forbidden** (нужна `finance`, которой у Manager нет) (ADM-02) |
| **Manager** | Управлять провайдерами | До фиксов Этапа 4 — мог (экшены были на `catalog`). **После Этапа 4 — не может**: экшены переехали на `providers`, которой нет в сид-роли Manager (ADM-00, регрессия моего же фикса) |
| Кассир (роль не создать) | Согласовывать пополнения | Секция `balance_approvals` не сидируется и **не редактируется через UI** — согласование доступно только владельцу (ADM-03, ADM-08) |

### 1.2 Критические дефекты (P0)

1. **ADM-00. Регрессия Этапа 4 для роли Manager.** Экшены управления провайдерами переведены с `catalog` на `providers`, но сид-роль Manager секцию `providers` не получает — после применения патчей Этапа 4 Manager потеряет работавшую ранее возможность управлять панелями. Требуется дополнение сида (или патч 0005).
2. **ADM-01. Тикеты: три секции в одном домене.** Страница — `tickets`, ответ/смена статуса — `support` (несидируемая!), телеграм-бинд и массовые возвраты — `orders`. Роль Support не может отвечать на тикеты.
3. **ADM-02. Клиенты: все мутации за `finance`.** Бан/разбан/ impersonation / смена пароля / удаление / magic-link / отзыв сессий — 12 экшенов на `finance:edit` при гейте страницы `clients`.
4. **ADM-03. Балансовые заявки на несидируемых секциях.** `balance_requests`/`balance_approvals`/`balance_stats` существуют только в типе — согласование пополнений замкнуто на OWNER/ADMIN.

### 1.3 Влияние на бизнес

- **Одноточечный отказ по персоналу:** поддержка, кассиры и менеджеры не могут работать без прав владельца — весь поток тикетов, согласований пополнений и модерации клиентов упирается в одного человека.
- **Скрытые дыры видимости:** страницы аналитики и антифрода открыты любой роли персонала без гейта; SUPPORT может просматривать конфигурацию брендов и **менять домены** тенантов (ADM-07).
- **Мёртвые фичи:** управление паттернами ссылок существует только как бэкенд без единого вызова из UI (ADM-10).
- **Регрессионный риск:** применение Этапа 4 без дополнения сида откатит Manager'ам доступ к провайдерам (ADM-00).

### 1.4 Топ-5 действий

1. Дополнить `seed-rbac.ts` (секции `providers` для Manager; актуальный список секций) и выпустить патч-0005 к пакету.
2. Унифицировать домены: тикеты → одна секция; клиенты → одна секция; согласование балансов → сидируемая секция.
3. Построить **UI-редактор ролей и прав** (создание ролей, матрица секций canView/canEdit) — без него вся система прав неуправляема.
4. Закрыть гейты страниц без секций (analytics, fraud-monitor, tenants) и выровнять SECTION_MAP сайдбара с реальными гейтами.
5. Почистить мёртвые revalidatePath и решить судьбу link-patterns (UI либо удаление).

## 4. Детальные находки

### ADM-00 [P0] Регрессия Этапа 4: Manager теряет управление провайдерами

**Симптом.** После применения патча 0004 (Этап 4 первого аудита) менеджер с сид-ролью Manager открывает «Провайдеры API» (layout-гейт `providers|catalog` пропускает по `catalog`), но создание/правка/удаление/синхронизация панелей возвращают Forbidden.

**Корневая причина.** Этап 4 перевёл экшены `crud.ts` с `catalog` на `providers` (исправление AUD-09), однако сид-роль Manager получает секции: `dashboard, clients, orders, refills, catalog, tickets, marketing, pages` — **без `providers`**. До фикса Manager проходил проверки по `catalog`; после — не проходит по `providers`. Патч 0004 корректен по направлению, но не сопровождался миграцией сида.

**Сценарий проверки после исправления.** Применить дополнение сида (`providers:edit` для Manager) → Manager снова создаёт/редактирует/удаляет панели; Support (без providers) по-прежнему не может.

**Комментарий аудита.** Это ошибка сопровождения МОЕГО фикса — обязательный патч-0005 «seed companion» должен выйти до применения пакета пользователем.

### ADM-01 [P0] Тикеты: три разные секции в одном домене, Support не может отвечать

**Симптом.** Сотрудник с ролью Support открывает «Поддержка», видит тикет, пишет ответ, нажимает отправить — «Forbidden: No permissions for section [SUPPORT]». При этом смена статуса, редактирование и удаление сообщений падают так же, а телеграм-привязка и массовые возвраты — с «[ORDERS]».

**Корневая причина.** В одном файле `src/actions/support/ticket.ts` домен разрезан на три секции:

```ts
// generateSmartReplyAction        → requireStaffPermission('orders', 'view')
// adminReplyTicket                → requireStaffPermission('support', 'edit')
// changeTicketStatus              → requireStaffPermission('support', 'edit')
// editTicketMessage/deleteTicketMessage → 'support'
// requestTelegramBind/adminManualTelegramBind → 'orders'
// bulkRefillOrdersAction/bulkRefundOrdersAction → 'orders'
```

Гейт страницы — `enforceSectionAccess('tickets')`; сайдбар показывает пункт по `orders` (SECTION_MAP). Секция `support` **не входит ни в ALL_SECTIONS сида, ни в роль Support** — её не имеет никто, кроме OWNER/ADMIN (bypass по роли). Роль Support, обладая `tickets:edit`, не проходит ни одну мутацию тикета.

**Сценарий проверки после исправления.** Одна секция `tickets` для всего домена (или сид `support` = синоним) → Support: ответ тикета, смена статуса, привязка Telegram, массовый refill/refund по ордерам тикета — всё проходит; роли без `tickets` — Forbidden на всё.

### ADM-02 [P0] Клиенты: мутации за `finance`, гейт за `clients`, меню за `finance`

**Симптом.** Manager по прямой ссылке открывает `/admin/clients` (гейт `clients` у него есть), видит карточку клиента, но кнопки «Забанить», «Сменить пароль», «Войти как», «Удалить» возвращают Forbidden. Пункта «Клиенты» в меню у него нет вовсе (SECTION_MAP требует `finance`).

**Корневая причина.** Из 13 экшенов `src/actions/admin/users.ts` двенадцать проверяют `finance:edit`:

```ts
// banUserAction, unbanUserAction, loginAsAction,
// adminChangeUserPasswordAction, adminDeleteUserAction,
// adminChangeUserEmailAction, adminGenerateMagicLinkAction,
// adminRevokeUserSessionsAction, approveQuarantineAction,
// rejectQuarantineAction, updateBalanceAction, requestCardRefundAction
//   → requireStaffPermission('finance', 'edit', ...)
// updateUserB2bAction → requireStaffPermission('clients', 'edit', ...)  // единственный
```

Карточка клиента (`client-detail-client.tsx`, 1435 строк) активно вызывает эти экшены. Денежные операции (баланс, возвраты) на `finance` — обоснованно; но бан, пароль, email, сессии, удаление и impersonation — это клиентские операции и должны жить в `clients`. Дополнительно: `loginAsAction` (имперсонация!) вообще стоит рассматривать как минимум OWNER/ADMIN-уровня, а не «finance:edit».

**Сценарий проверки после исправления.** Роль с `clients:edit`: бан/разбан/пароль/email/magic-link/сессии/удаление работают; баланс и возвраты — только при `finance:edit`. Имперсонация — только OWNER/ADMIN или отдельная политика. Меню «Клиенты» видно по `clients`.

### ADM-03 [P0] Согласование балансовых заявок замкнуто на владельца

**Симптом.** Владелец хочет нанять кассира: создаёт роль, но в списке секций UI нет `balance_approvals`; после ручного создания в БД всё работает. Без БД — согласование пополнений может делать только сам владелец.

**Корневая причина.** `src/actions/admin/balance-adjustments.ts` использует секции `balance_requests` (создание/отмена/чтение), `balance_approvals` (approve/reject), `balance_stats` (статистика). Эти секции есть в типе `StaffPermissionSection`, но **отсутствуют в `ALL_SECTIONS` сида** и **не могут быть выданы через UI** (см. ADM-08 — редактора прав не существует). Итог: пройти проверки могут только OWNER/ADMIN через bypass по роли.

**Сценарий проверки после исправления.** Секции сидируются в роли «Кассир»; кассир согласовывает и отклоняет заявки, не видит финансовые отчёты; менеджер не видит заявок.

### ADM-04 [P1] Страница роутинга услуг за несуществующей секцией `services`

**Симптом.** Manager открывает маршрутизацию услуги (failover на альтернативных провайдеров) — редирект на «Доступ запрещён», хотя он управляет каталогом.

**Корневая причина.** `src/app/admin/services/[id]/routing/page.tsx`:

```ts
await requireStaffPermission('services', 'view', async () => {});
```

Секции `services` нет ни в типе `StaffPermissionSection`, ни в сиде. Проходят только OWNER/ADMIN (bypass). При этом сами экшены `routing.actions.ts` проверяют `catalog` — тройное рассогласование: страница `services` / экшены `catalog` / сид `catalog`.

Попутно: маршрут `/admin/services` **не имеет своей page.tsx** (только `[id]/routing` и loading) — ссылочные пути в UI ведут на 404.

### ADM-05 [P1] Контент: гейт `content`, сид `pages`, сайдбар `settings`

**Симптом.** Manager (сид даёт `pages:edit`) открывает «CMS Страницы» / «Статьи блога» / «Страницы» — «Доступ запрещён».

**Корневая причина.** Layout/страницы контента гейтят `content`; сид выдаёт роль Manager секцию `pages`; SECTION_MAP сайдбара мапит UI-секцию `pages` на `settings`. Три имени одной предметной области, ни одна пара не совпадает. Секция `content` корректно проверяется экшенами (`content.ts` → `content`), но недостижима без правки БД.

### ADM-06 [P1] Сайдбар и страницы считают доступ по-разному

**Симптом.** Пункт меню видим, страница закрыта («Доступ запрещён»), и наоборот — рабочий раздел недоступен из меню, только по прямой ссылке.

**Корневая причина.** `src/app/admin/layout.tsx` содержит собственную карту:

```ts
const SECTION_MAP = {
  'dashboard': 'orders', 'tickets': 'orders', 'clients': 'finance',
  'providers': 'catalog', 'pages': 'settings', 'features': 'settings', ...
}
```

которая расходится с реальными гейтами страниц (`dashboard`, `tickets`, `clients`, `content`…). Для OWNER/ADMIN различие незаметно (bypass), для персонала — хаос. Пример: Support имеет `orders:view` → видит «Поддержка», но страница требует `tickets` (у него есть — в данном случае повезло); Manager имеет `clients:edit` → НЕ видит «Клиенты», хотя страница для него открыта.

### ADM-07 [P1] Страницы без секционного гейта; SUPPORT меняет домены брендов

**Симптом.** (а) Любой MANAGER/SUPPORT открывает `/admin/analytics` и `/admin/fraud-monitor`. (б) SUPPORT открывает `/admin/tenants`, видит конфигурацию всех брендов (домены, тестовый режим, maintenance) и может сохранить изменения домена.

**Корневая причина.**
- `analytics/page.tsx` и `fraud-monitor/page.tsx` — ноль проверок в странице; данные тянутся экшенами с гейтами `orders` (аналитика) и `settings` (антифрод) — Support видит аналитику (у него `orders:view`), но антифрод renders без данных.
- `tenants/page.tsx` — ручная проверка `ADMIN_ROLES` (включая SUPPORT/MANAGER) вместо секции; `updateTenantAction`/`toggleTenantStatusAction` в `tenants.ts` повторяют ту же слабую проверку. Только `deleteTenantAction` корректно ограничен OWNER + защита системных брендов.

**Рекомендация.** Tenants — настройки уровня владельца: гейт `settings` минимум, изменения доменов — OWNER/ADMIN. Аналитика — секция `analytics` (сидировать). Антифрод — `settings`.

### ADM-08 [P1] Нет UI управления ролями и матрицей прав

**Симптом.** На странице «Персонал» можно назначить пользователю существующую роль из списка и изменить её — всё. Создать роль, переименовать, выставить секции canView/canEdit — невозможно.

**Корневая причина.** `admin/staff/**` работает только через `updateStaffMemberAction` (назначение staffRoleId пользователю). CRUD ролей и прав в UI отсутствует; `StaffRole`/`StaffPermission` управляются только миграциями БД и `seed-rbac.ts`. В связке с ADM-01..05 это делает систему прав неэксплуатируемой: чтобы выдать сотруднику «support», «content» или «balance_approvals», нужен SQL-доступ.

**Сценарий проверки после исправления.** Экран «Роли и права»: список ролей, редактор матрицы секций (просмотр/правка), создание/удаление нестандартных ролей, журнал изменений прав в аудите.

### ADM-09 [P2] Feature-flags: страница за `settings`, в сиде отдельная `features`

Страница `/admin/system/features` гейтится `settings`, экшены `feature-flags.ts` — `SETTINGS` (нормализуется), но сид создаёт отдельную секцию `features`, которая никем не проверяется. Роль с одной лишь `features` не откроет страницу. Решение: убрать `features` из сида или гейтить по ней.

---

### ADM-10 [P1] Link-patterns: бэкенд-фича без единого вызова из UI

**Симптом.** Управление паттернами ссылок (для smart-анализера) недоступно оператору ни из одного экрана.

**Корневая причина.** `src/actions/admin/link-patterns.ts` экспортирует 6 экшенов (CRUD паттернов, `catalog`-секция). Поиск по `src/app` и `src/components` не находит **ни одного импорта**. Маршрут `/admin/catalog/patterns`, на который ссылаются revalidatePath, не существует — страница не была создана. Фича либо недописана, либо UI был утерян при рефакторинге (аналог AUD-06 первого аудита).

**Решение.** Либо построить страницу управления паттернами (вкладка в каталоге), либо вырезать мёртвый слой до появления потребности.

### ADM-11 [P2] Мёртвые revalidatePath

`/admin/services` ×3 (`ai-enrich.action.ts`, `routing.actions.ts` ×2 — маршрута-страницы нет), `/admin/catalog/patterns` ×2, `/admin/legal/responsibility` ×1. Инвалидация «в никуда» — соответствующие экраны обновляются только собственным TTL. Класс AUD-08 первого аудита; чинится тем же паттерном: замену на реальные маршруты (`/admin/catalog`, страница редактирования услуги).

`academy-client.tsx` 1907 строк, `client-detail-client.tsx` 1435, `provider-form.tsx` 1238, `OrderDetailsModal.tsx` 938, `category-manager.tsx` 892, `smart-client.tsx` 862, `team-management.tsx` 819, `import-wizard.tsx` 781, `finance-client.tsx` 779. ### ADM-13 [P2] Отсутствие error-границ

`error.tsx` существует только в 3 местах (orders и ещё 2). Во всех остальных разделах исключение серверного рендера даёт общий краш вместо локальной заглушки «раздел временно недоступен» с кнопкой «Повторить». Для персонала, работающего в панели целый день, это деградирует до перелогина.

---

### ADM-14 [P2] Побочная запись при GET страницы роутинга

`services/[id]/routing/page.tsx` при отсутствии маршрутов создаёт первичный маршрут из данных услуги (self-healing). Запись при рендере страницы: (а) не идемпотентна при параллельных открытиях (два tab → попытка двойной вставки, спасает только unique-constraint), (б) не попадает в аудит. Правильнее — ensure-маршрут в экшене при первой операции или отдельная кнопка «Создать маршрут из текущего провайдера».

---

### ADM-15 [P2] canSeeRates по строке роли

`orders/page.tsx`: `const canSeeRates = isOwner || (user?.role !== 'SUPPORT')` — логика видимости себестоимости дублирует RBAC строковым сравнением ролей. MANAGER видит rates, кастомная роль без `finance` — тоже. Должно быть `finance:view`-право (в проекте уже есть `canSeeRates` на основе FINANCE-прав в каталоге — orders расходится с этим паттерном).

---

### ADM-16 [P2] Тяжёлый запрос в корневом layout

`admin/layout.tsx` на каждый заход в любой раздел выполняет `db.service.count(...)` (аномалии каталога для бейджа). Для SUPPORT, не работающего с каталогом, это лишний COUNT по растущей таблице. Кэшировать на 30–60 с (unstable_cache) или перенести бейдж в layout каталога.

---

### ADM-17 [P2] Manual-справка за гейтом `settings`

Страница руководств (`/admin/manual`, включая academy-client на 1907 строк) требует `settings` — саппорт, для которого справка написана, её не увидит. Гейт должен быть максимально мягким (любой персонал).

## 5. Положительные находки (что сделано хорошо)

Чтобы аудит был сбалансированным — сильные стороны остальной панели:

- **Заказы** (`actions/admin/orders.ts`): все мутации в `runSerializableTransaction`, возвраты через `WalletOps.refund` с идемпотентными ключами (`refund_${orderId}_${status}`), защита от двойного возврата при переходах между терминальными статусами, обязательный аудит `ORDER_STATUS_OVERRIDE`/`ORDER_FORCE_COMPLETE`, `revalidatePath` по правильному маршруту. Эталон для остальных доменов.
- **Финансы** (`actions/admin/finance/*`): единая секция `finance`, read-only экшены с `view`, сверка (reconciliation) и dispute-pack для платёжных споров.
- **Тенанты**: удаление только OWNER + запрет удаления системных брендов `smmplan`/`flux` — правильная защита.
- **Дашборд**: все виджеты на реальных сервисах (accounting/order/user/ticket/catalog) — моков нет; период/тенант фильтруются.
- **E2E-покрытие**: существуют `admin.spec.ts`, `finance.spec.ts`, `tickets.spec.ts`, `staff-management.spec.ts`, `admin-provider-tickets.spec.ts` — база для регрессии есть (требует актуализации под новые гейты).
