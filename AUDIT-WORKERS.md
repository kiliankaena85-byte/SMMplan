## 1. Резюме для руководителя

### 1.1 Главный вывод

**Воркеры спроектированы зрелo и «деньгосберегающе»**: процессор заказов имеет пятиуровневую защиту от двойной отправки провайдеру (статусный guard, externalId-guard, Redis-мьютекс с TTL, ambiguous-timeout → PENDING_CHECK вместо слепого возврата, fail-fast с авто-возвратом и карантином услуги); DLQ автоматически возвращает деньги при исчерпании ретраев; PENDING_CHECK-заказы разрешаются двухуровневой чисткой (6 ч авто-проверка у провайдера + 24 ч TTL-sweep с возвратом); graceful shutdown и heartbeat на месте.

**Найдено 6 дефектов**, главный — снова «зеркало CHK-01»: страховочный синхронизатор платежей гасит только legacy-связанные заказы, оставляя корзинные (текущая архитектура) в вечном `AWAITING_PAYMENT` при истечении/отмене платежа.

## 2. Детальные находки

### WRK-01 [P1] Страховщик платежей не гасит корзинные заказы

**Симптом.** Клиент оплачивает заказ шлюзом (не YooKassa — Robokassa/CryptoBot), передумывает/платёж истекает. Через 24 часа payment-sync отменяет платёж… но заказы остаются `AWAITING_PAYMENT` навсегда: они не появятся на витрине исполнения, не попадут в orphan-sweep (тот ищет только `PENDING`), и клиент видит «вечное ожидание». Аналогично ветка «удалённо canceled»: платёж отменён — заказы нет.

**Код** (`src/workers/processors/payment-sync.ts`):
```ts
// Stale-путь (24h, non-YooKassa):
if (payment.orderId) {                                   // ← только legacy-указатель!
  await tx.order.updateMany({
    where: { id: payment.orderId, status: 'AWAITING_PAYMENT' },
    data: { status: 'CANCELED', error: 'Оплата не поступила в течение 24ч...' }
  });
}
// Remote-canceled ветка — вообще не трогает заказы:
await db.payment.update({ where: { id: payment.id }, data: { status: 'CANCELED' } });
```

Текущий чекаут (после всех волн рефакторинга) создаёт Payment **без** `orderId` — связь через `Order.paymentId`. `grep paymentId payment-sync.ts` → 0 вхождений. Это точное зеркало CHK-01, исправленного в D0.1 для основного чекаута, но оставшегося в страховщике.

**Фикс (по эталону D0.1):** в обеих ветках гасить корзинно:
```ts
await tx.order.updateMany({
  where: { paymentId: payment.id, status: 'AWAITING_PAYMENT' },
  data: { status: 'CANCELED', error: 'Оплата не поступила в течение 24ч (auto-expire)' }
});
```
(+ тест: платёж с двумя заказами-корзины → оба CANCELED; remote-canceled → то же.)

### WRK-02 [P2] Нереализованный «wait limit»

При отправке провайдеру заказ получает `waitingUntil = now + 60 мин` с комментарием «Set 60 minutes Wait limit». Поиск по коду: поле **никто не читает**. Фактическая логика ожидания другая: статусный sync крутится каждые 5 минут, а застрявшие заказы подбирают PENDING_CHECK-механики. Поле либо удалить (мёртвый вес), либо реализовать: sync.processor при `IN_PROGRESS && waitingUntil < now && remains == quantity` (ничего не сделано за час) — эскалация в PENDING_CHECK/алерт. Рекомендация: реализовать как дешёвый «детектор нулевого старта» — частая болезнь SMM-провайдеров.

---

### WRK-03 [P2] Долгий цикл авто-разрешения PENDING_CHECK

PENDING_CHECK возникает при ambiguous timeout (деньги клиента удержаны, отправка не подтверждена). Разрешение: cleanup-процессор с порогом 6 ч. Но cleanup-cron — `0 3 * * *` (раз в сутки). Худший случай: заказ завис в 03:01 → разрешение в 03:00 следующего дня + 6ч порог → **~27 часов удержания денег без движения**, при том что сам механизм умеет разрешать через 6 часов.

**Фикс:** вынести PENDING_CHECK-блок из ежедневного cleanup в собственный частый тик (например, hourly-cron в cleanupQueue или в sync-цикл, который уже крутится каждые 5 минут и уже имеет похожую логику quarantine-восстановления). Деньги клиента — не та метрика, которую стоит прибивать к ночному расписанию.

---

### WRK-04 [P3] Неполное DLQ-покрытие

`handleDeadLetter` подключён к 7 очередям, но eta/telegram/cleanup пишут только `log.error`. Не деньги — допустимо, но ETA-статистика (P50/P90 на витрине) может молча устаревать неделями. Минимум: алерт при N подряд провалов etaWorker; максимум — провести через DLQ без авто-действий.

---

### WRK-05 [P3] Усеченная синхронизация без индикации

`MAX_SYNC_PER_PROVIDER = 1000, orderBy: updatedAt asc` — при всплеске заказы за пределами тысячи ждут следующего 5-минутного тика; алгоритм честный (старые первыми, кольцо замыкается), но факт усечения не логируется. Добавить `log.warn` при `activeOrders.length === MAX_SYNC_PER_PROVIDER`.

---

### WRK-06 [P3] Мёртвый статус PROVISIONING

Enum `OrderStatus.PROVISIONING` не устанавливается нигде в коде (учтён только в счётчике дашборда оператора). Либо удалить из enum (миграция), либо не использовать. Косметика схемы.

## 3. Что сделано хорошо (подтверждения)

- **order.processor — эталон денежной безопасности:** guard «не PENDING → skip»; guard `externalId` (повторная джоба); Redis-мьютекс `order:dispatched:{id}` (TTL 1 ч) против дабл-диспатча при падении записи в БД; **ambiguous timeout → PENDING_CHECK + CRITICAL-алерт** вместо слепого возврата (защита от «бесплатной доставки»); fail-fast: явный отказ провайдера → мгновенный терминал с возвратом + карантин услуги (Trigger A); test-order guard против утечки тестов в прод; UnrecoverableError для остановки ретраев там, где они опасны.
- **DLQ-конвейер:** исчерпание попыток → dead-letter запись + **авто-возврат заказа** (`failOrderTerminal`) + ERROR-статус докрутки + CRITICAL-алерт. Пороговый счётчик попыток берётся из опций джобы.
- **Двухуровневое разрешение PENDING_CHECK:** 6 ч — спросить провайдера и принять статус; провайдер не знает → терминал с возвратом; 24 ч TTL-sweep — страховка страховки.
- **Graceful shutdown полный:** все 10 воркеров закрываются параллельно, heartbeat-ключ удаляется, БД/Redis отключаются, сигналы SIGTERM/SIGINT/IPC/stdin (для виндовых тест-раннеров).
- **Heartbeat** с TTL 2× интервала — health-эндпоинт видит смерть воркера.
- **Smart-drip:** авто-завершение кампании, частичный возврат за ERROR-части, компенсационный тик в sync-цикле.
- **jitteredBackoff** — ретраи не бьют синхронными волнами; concurrency=2 у sync; rate-limiter у telegram.
