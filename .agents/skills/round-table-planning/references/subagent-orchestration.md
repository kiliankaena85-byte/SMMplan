# Subagent orchestration — параллельный запуск ролей

Этот файл описывает, как модератор запускает специалистов через Antigravity `invoke_subagent`. Это ключевой механизм скилла для Level 2 и Level 3 (см. `triage.md`).

## Зачем subagents

Antigravity поддерживает `invoke_subagent` — реальную параллельную работу подагентов в изолированных контекстах. Это меняет архитектуру скилла радикально:

**Без subagents (один агент меняет шляпы):**
- ❌ Self-agreement bias: тот же агент не хочет критиковать себя
- ❌ Контекст растёт с каждым раундом, к концу забывается начало
- ❌ Последовательное выполнение = долго

**С subagents:**
- ✅ Изолированный контекст: каждый специалист не видит свою «предыдущую шляпу»
- ✅ Реальная критика: нет self-agreement bias
- ✅ Параллельное выполнение: 5 раундов за время 1
- ✅ Каждый subagent можно специализированно промптить

## Когда использовать subagents

| Level | Режим | Когда |
|-------|-------|-------|
| Level 0 | — | Skip, без скилла |
| Level 1 | Один агент (без subagents) | Простые задачи, 3 роли, выигрыш от параллелизма минимальный |
| Level 2 | Subagents (4-5 параллельно) | Средние задачи, реальный выигрыш |
| Level 3 | Subagents (6-7 параллельно) | Сложные задачи, максимальный выигрыш |

## Как Antigravity invoke_subagent работает

Из документации Antigravity:

```
Tool: invoke_subagent
Arguments:
  Subagents (array of specs):
    - Prompt: строка с задачей для подагента
    - Role: роль подагента
    - TypeName: тип (например, "general-purpose")
    - Workspace (optional): рабочая директория
```

Также доступны:
- `define_subagent` — создать кастомного подагента с system_prompt
- `manage_subagents` — список/терминация активных подагентов
- `send_message` — коммуникация между агентами

## Архитектура запуска

### Последовательные раунды (не параллелятся)

**Архитектор** — должен быть первым, задаёт фундамент. Без него остальным нечего критиковать.

**Data Engineer** — проектирует схему под архитектуру Архитектора. Должен видеть Архитектора.

Запуск: один за другим, последовательно. Результаты собираются в общую «базу знаний» раундов.

### Параллельные раунды (запускаются одновременно)

После Архитектора и Data Engineer, эти роли можно запускать параллельно — они в основном критикуют архитектуру и схему, между собой пересекаются мало:

- **Security** — STRIDE threat model
- **Performance (backend)** — latency, N+1, индексы
- **Frontend Performance** — bundle, CWV
- **DevOps/SRE** — CI/CD, observability, deployment
- **SEO/SSR** — rendering, metadata

Запуск: все одновременно через один вызов `invoke_subagent` с массивом Subagents. Каждый получает:
1. Оригинальную задачу
2. Резюме Архитектора (200-300 слов)
3. Резюме Data Engineer (200-300 слов)
4. Свою роль и фокус из `references/<role>.md`

### Продуктовая группа (после технических)

После параллельных технических раундов модератор собирает их результаты и передаёт в:

- **UI/UX** — flow, экраны (видит все технические раунды)
- **PM** — приоритеты, метрики (видит UX, проверяет сценарии)

UI/UX и PM можно запускать параллельно друг с другом (PM видит только задачу + технические раунды, не UX). Но если PM должен критиковать UX — он идёт после.

### Финал: QA (после всех)

QA — всегда последний, видит все раунды, формирует DoD и тест-стратегию.

## Подготовка резюме раундов

**Критично:** не передавай в subagent полный текст предыдущих раундов. Каждый раунд = 10-20 KB, 5 раундов = 50-100 KB на каждый subagent. Контекст взорвётся.

**Решение:** модератор после каждого раунда пишет **резюме** (200-300 слов):

```
## Резюме раунда: Архитектор

**Подход:** [2-3 предложения основного решения]
**Ключевые решения:**
- [решение 1]
- [решение 2]
- [решение 3]
**Альтернативы (названия, без деталей):** [A, B, C]
**Шаги плана:** [N шагов с названиями]
**Риски для передачи дальше:** [top-3]
**Что оспорить:** [1-2 пункта, где другие роли могут не согласиться]
```

Именно это резюме (а не полный текст) передаётся в следующие subagents. Полный текст раундов сохраняется в файл для синтеза.

## Шаблон вызова invoke_subagent

Модератор формирует один вызов `invoke_subagent` с массивом всех параллельных ролей:

```
invoke_subagent({
  Subagents: [
    {
      Prompt: """
        Ты — Security-инженер в круглом столе планирования.
        
        ЗАДАЧА: [оригинальная задача пользователя]
        
        КОНТЕКСТ:
        - Архитектор предложил: [резюме 200 слов]
        - Data Engineer спроектировал: [резюме 200 слов]
        
        Твоя роль описана в references/security-engineer.md — прочитай её.
        Используй STRIDE threat model.
        
        ВАЖНО: Найди МИНИМУМ 3 пункта для оспаривания в плане Архитектора.
        Если согласен со всем — пересмотри ещё раз, ты что-то упустил.
        
        Выведи:
        1. Принимаю (кратко)
        2. Оспариваю (с обоснованием)
        3. STRIDE threat model (таблица)
        4. Блокеры релиза
        5. Резюме для передачи в следующий раунд (200 слов)
      """,
      Role: "Security Engineer",
      TypeName: "general-purpose"
    },
    {
      Prompt: """...Performance...""",
      Role: "Performance Engineer",
      TypeName: "general-purpose"
    },
    // ... другие параллельные роли
  ]
})
```

## Сбор результатов

После возврата от `invoke_subagent` модератор получает результаты всех subagents одновременно. Дальше:

1. **Сохранить полные тексты** в `/home/z/my-project/download/rounds/[role].md` — для синтеза
2. **Извлечь резюме** из каждого (последний раздел каждого ответа) — для передачи дальше
3. **Найти конфликты** между ролями (где они оспорили одно и то же по-разному)
4. **Передать резюме** в следующую группу (UI/UX, PM)

## Конфликты между параллельными ролями

Поскольку роли работают параллельно, они могут прийти к противоречащим выводам:

**Пример конфликта:**
- Security: «логировать все PII для audit»
- Performance: «логирование убивает latency, sampling 10%»

**Разрешение в синтезе:**
Модератор собирает все конфликты в таблицу и решает:

| Конфликт | Security | Performance | Решение |
|----------|----------|-------------|---------|
| Логирование | Полное (audit) | Sampling 10% | Sampling для не-критичных, полное для critical ops |

Если конфликт не разрешим без пользователя — в «Открытые вопросы» плана.

## Fallback: если subagents недоступны

Если Antigravity не поддерживает `invoke_subagent` или упал, модератор переключается на **последовательный режим одним агентом**:

1. Сообщает: «Subagents недоступны, переключаюсь на последовательный режим (медленнее)»
2. Запускает роли по очереди, меняя «шляпы»
3. После каждого раунда — резюме (как описано выше)
4. Контекст контролируется через резюме, не полный текст

Это медленнее, но работает.

## Принципы

### Изоляция — главное преимущество
Каждый subagent не видит свою предыдущую «шляпу». Это убирает self-agreement bias. Не нарушай изоляцию, передавая между subagents больше, чем резюме.

### Резюме — контракт между раундами
Полный текст раунда — для финального плана. Резюме — для передачи в следующие раунды. Не путай эти два назначения.

### Параллельные роли действительно параллельны
Если ты запускаешь 5 ролей через invoke_subagent, они выполняются одновременно. Не пытайся «помочь» им, передавая данные друг другу в реальном времени. Каждый работает с тем, что получил на старте.

### Adversarial prompting обязателен
В каждом subagent prompt добавляй: «Найди МИНИМУМ 3 пункта для оспаривания. Если согласен со всем — пересмотри ещё раз». Без этого LLM соглашается с предыдущими раундами в 80% случаев.

### Fallback — норма, не исключение
Если что-то пошло не так с subagents, переключайся на последовательный режим без паники. Лучше медленный план, чем никакого.

- [ ] invoke_subagent вызывается с массивом всех ролей одновременно
- [ ] После возврата — полные тексты сохранены в файлы, резюме извлечены
- [ ] Конфликты выявлены и зафиксированы для синтеза

## Что происходит после параллельных раундов

1. UI/UX subagent (видит все технические резюме)
2. PM subagent (видит технические резюме + UX резюме)
3. QA subagent (видит все резюме)
4. Модератор собирает финальный план по `plan-template-compact.md` или `plan-template.md`
5. Выводит чат-рецепт по `developer-output.md`
6. Сохраняет полный план в `/home/z/my-project/download/plan-[task].md`
7. Запрашивает подтверждение

Каждый последующий subagent получает **только резюме** предыдущих, не полные тексты. Это сохраняет контекст управляемым.
