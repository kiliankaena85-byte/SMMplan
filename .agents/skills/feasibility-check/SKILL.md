# Feasibility Check — «Можем ли мы это сделать»

## When to activate

- Выбрано дизайн-решение и нужно проверить реализуемость
- Пользователь спрашивает «можем ли мы это сделать?»
- Перед обещаниями клиенту о функциональности
- После competitor analysis — понравившийся элемент нужно проверить
- При оценке scope проекта

## МАТРИЦА РЕАЛИЗУЕМОСТИ (4 оси)

### ОСЬ 1: КОНТЕНТНАЯ ГОТОВНОСТЬ
- [ ] У нас есть реальные фото продукта/команды? → Если нет: illustration / 3D / abstract
- [ ] У нас есть видео контент? → Если нет: cinemagraph / CSS animation
- [ ] У нас есть данные для social proof? → Если нет: начать собирать ДО лонча
- [ ] У нас есть testimonials с фото, именем, должностью? → Если нет: сначала собрать

### ОСЬ 2: ТЕХНИЧЕСКАЯ ГОТОВНОСТЬ
- [ ] Наш стек поддерживает эту анимацию?
- [ ] Производительность: не упадёт ли LCP > 2.5s? → Если риск: progressive enhancement
- [ ] Мобильный опыт: работает ли это на touch? → Если нет: mobile-first альтернатива
- [ ] Accessibility: работает ли с screen reader? → Если нет: ARIA labels + skip nav

### ОСЬ 3: БРЕНДОВАЯ СОВМЕСТИМОСТЬ
- [ ] Соответствует ли tone of voice нашему бренду?
- [ ] Цветовая палитра совместима?
- [ ] Типографика совпадает с нашим дизайн-гайдом?
- [ ] Не противоречит ли нашему позиционированию?

### ОСЬ 4: РЕСУРСНАЯ РЕАЛИЗУЕМОСТЬ
- [ ] Сколько времени разработки требует? (S < 4h / M < 2d / L < 1w / XL > 1w)
- [ ] Требует ли дизайн-ресурсы?
- [ ] Есть ли зависимости от других частей проекта?
- [ ] ROI: насколько это влияет на ключевую метрику?

## ИТОГОВЫЙ SCORE

Каждый элемент получает Feasibility Score (0-10):
- ≥ 8: Реализовать немедленно
- 5-7: Реализовать с адаптацией
- 3-4: Включить в backlog
- < 3: Отклонить

## Step-by-step execution protocol

1. **List design elements**: Составить список всех дизайн-элементов, которые нужно проверить
2. **Content axis**: Для каждого — проверить наличие контента
3. **Technical axis**: Проверить совместимость со стеком (прочитать package.json)
4. **Brand axis**: Сверить с client-dna и бренд-гайдом
5. **Resource axis**: Оценить время и ресурсы для реализации
6. **Score**: Присвоить Feasibility Score каждому элементу
7. **Recommend**: Сформировать рекомендации (implement / adapt / backlog / reject)
8. **Report**: Вывести итоговую матрицу с приоритетами

## Scope boundaries

### DOES
- Проверять реализуемость по 4 осям
- Присваивать количественный Feasibility Score
- Предлагать альтернативы для нереализуемых решений
- Учитывать текущий стек проекта

### DOES NOT
- Заменять техническую оценку от разработчиков
- Оценивать стоимость в деньгах (только время)
- Принимать решение за клиента (только рекомендации)
- Гарантировать что реализуемое = эффективное (нужен A/B тест)

## Error handling

| Scenario | Response |
|----------|----------|
| Неизвестный стек проекта | Запросить package.json у пользователя, или предложить universal решения |
| Недостаточно данных для brand axis | Запустить client-dna skill для сбора контекста |
| Противоречие между осями (технически да, бренд — нет) | Пометить как «needs client decision», показать trade-off |
| Нет времени на полную проверку | Провести быстрый чек по Осям 1 и 2, остальные отметить как TBD |
