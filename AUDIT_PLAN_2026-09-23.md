## 2. Методика аудита (что и чем проверяем)

**Принцип:** ни одна находка не считается дефектом без воспроизводимого доказательства (команда + вывод + файл/строка) и без проверки радиуса поражения (AGENTS.md §0.7).

### 2.1. Уровни проверки

| Уровень | Инструмент | Что выявляет | Артефакт |
|---|---|---|---|
| L1. Статика типов | `npm run typecheck` (`tsc --noEmit`) + классификация диагностик по кодам | смешение bigint/number, nullable-deref, `{}`-shape, битые контракты | `audit/evidence/tsc-*.md` |
| L2. Статика архитектуры | `npm run lint:debt` (knip), `npm run lint:guardrails` (ast-grep), `npm run lint:tenant`, скрипты поиска дублей/годфайлов | дубли экспортов, мёртвый код, годфайлы > 200 строк, нарушение границ слоёв, BOLA/IDOR | `audit/evidence/arch-*.md` |
| L3. Дифф-анализ | `git diff` baseline ↔ декомпозиция ↔ откат (history восстановлена) | что именно потеряно/продублировано при откате | `audit/evidence/diff-*.md` |
| L4. Поведение | `vitest run` (unit+integration), `playwright test` (e2e) | падения тестов, «пустые» снапшот-тесты, отсутствие покрытия критических путей | `audit/evidence/tests-*.md` |
| L5. Динамика в браузере | Blue-Green stage :3005, Puppeteer/Playwright, роли GUEST/USER/SUPPORT/OWNER, тенанты smmplan/flux | NaN/undefined в UI, ошибки консоли, гидратация, горизонтальный скролл, «мёртвые» кнопки | `audit/evidence/visual-*.png` + матрица |
| L6. Дизайн-система | `npm run layout:audit`, `theme:audit`, `theme:contrast` + ручной WCAG 2.2 AA чеклист | контраст < 4.5:1, тач-таргеты < 44px, расхождения между параллельными реализациями | `audit/evidence/design-*.md` |
| L7. Данные | Prisma-инварианты, `dailyReconciliation`, `balance-verifier`, ledger-аудит (на тестовой БД) | тенант-утечки, расхождения леджер ↔ баланс, смешение единиц (рубли/копейки) | `audit/evidence/data-*.md` |

### 2.2. Требования к окружению для L4–L7 (сейчас недоступны в песочнице агента)

В текущей песочнице **невозможны**: `prisma generate` (заблокирован `binaries.prisma.sh`), запуск приложения и БД, прогон vitest (падает на импорте `@prisma/client`), браузерный аудит.
Поэтому:

* Фазы 1 и частично 3 выполняются **здесь** (статика, диффы, инвентаризация, подготовка harness).
* Фазы 2, 4–7 требуют **stage-окружения** (порт 3005, БД + Redis + сгенерированный Prisma Client) — по BGS-2026. Если stage недоступен заказчику — фиксируем это как блокер и запускаем аудит в CI-джобе с БД (docker compose already in repo).

### Фаза 1 — Статический аудит и триаж дефектов (1–2 дня)
**Цель:** полный, воспроизводимый реестр дефектов с приоритетами (без правок кода).

1. **Типы:** прогнать `tsc` с сгенерированным Prisma Client, классифицировать диагностики по кодам и модулям, отделить каскадные от структурных; сформировать реестр «файл:строка → дефект → владелец».
2. **Деньги:** отдельный проход по `bigint/number` (8 подтверждённых мест) + аудит единиц измерения (копейки/рубли) в `ledger`, `wallet`, `checkout`, `reconciliation`, `balance-verifier`, `client-financial-summary`.
3. **Shape-дыры:** типизировать источники `{}` (JSON.parse, `unknown`, `Record<string, unknown>`), проверить наличие Zod-валидации на входах.
4. **Дубли и split-brain:** машинный инвентарь дублирующихся экспортов и параллельных реализаций (визарды, транзакции, тенант-резолверы, чекаут-варианты) → карта «кто кого перекрывает».
5. **Годфайлы:** список > 200 строк с разметкой по критичности контура (деньги/заказы — приоритет).
6. **Мультитенант:** аудит 54 моделей без `tenantId`, проверка путей, где запросы идут без tenant-фильтра, проверка кэшей (`catalog-${tenantId}`) и событий (BullMQ payload).
7. **Дифф-анализ отката:** что именно потеряно при откате декомпозиции каталога и возврате knip-дублей; какие модули содержат «старую» и «новую» логику одновременно.

**Цель:** подтвердить/опровергнуть статические находки на живом поведении.

## 6. Правила безопасности изменений (обязательны для Фаз 4–6)

1. **Impact Radius** — до правки: `grep` всех зависимостей; компонент/функция с 2+ вызовами → обратная совместимость обязательна (AGENTS.md §0.7).
2. **Pre-Mortem на 3 шага** — что сломается в аутентификации/балансе/кэше/вебхуках/мультитенанте.
3. **Spec→Tests→Code** — Tier 1 (деньги, заказы, миграции, очереди, auth) обязательно Red-тест до реализации (AGENTS.md §0.11).
4. **Один дефект — один коммит**, отдельно от косметики; сообщение с ID задачи.
5. **Проверка на stage 3005**, скриншоты до/после; прод — только после явного одобрения.
6. **Откат обязан быть полным**: возвращаем код и удаляем оставленные артефакты модулей, которые откатывали (иначе получаем текущий split-brain).
7. **Никаких массовых автоправок** (`fix.js`, `auto-fix-linter.js`) без ревью диффа и прогонов — именно этот путь дал 101 файл «inline fixes» без поведенческой проверки.

## 7. Чего делать НЕ нужно (анти-паттерны, которые уже стоили регрессий)

* Массовая декомпозиция «всех годфайлов сразу» без поведенческих тестов.
* Снапшот-тесты архитектуры по тексту исходников (`expect(file).toContain(...)`) — зелёные, ничего не гарантируют, и краснеют от косметики.
* Автоматические «фиксы» изоляции тенантов по сотне файлов вместо слоя доступа к данным.
* Правки «заодно» (логика + верстка + тексты в одном коммите) — ломает дифф-анализ при откате.
* Хранение откатов в виде дампов/zip/бэкапов в git.
* Удаление дублей «по имени», без проверки, какая из реализаций используется в каждом контуре.
* Включение блокирующих гейтов «на всё сразу» до обнуления долга (гарантированный красный CI и соблазн откатить гейты).
