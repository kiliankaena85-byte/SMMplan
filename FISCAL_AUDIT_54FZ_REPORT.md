# Аудит соответствия платёжной инфраструктуры требованиям 54-ФЗ («О применении ККТ»)

**Дата аудита**: 29 июля 2026 г.  
**Объект аудита**: Платёжные интеграции ЮKassa, Robokassa, CryptoBot (`src/services/financial/payment-gateway.service.ts`), механизмы фискализации, передача чеков ОФД и обработка возвратов в SMMplan.  
**Статус аудита**: ✅ Завершено.

---

## 1. Executive Summary

Проведен глубокий правовой и технический аудит платёжной инфраструктуры SMMplan на соответствие требованиям Федерального закона № 54-ФЗ «О применении контрольно-кассовой техники при осуществлении расчётов в Российской Федерации» и приказам ФНС по форматам фискальных документов (ФФД 1.05 / 1.2).

Аудит показал, что в системе реализована интеграция с облачной фискализацией ЮKassa Receipt API и сервисом «Робочеки» от Robokassa. При пополнении баланса картой или через СБП агрегаторам передаются фискальные блоки `receipt` с признаком способа расчёта `full_prepayment` и предметом расчёта `service`. Внутренние операции списания с баланса при заказе услуг и внутренние возвраты при отмене заказов на виртуальный баланс клиентам обоснованно не вызывают повторного формирования чеков ККТ, что полностью соответствует разъяснениям Минфина РФ.

Вместе с тем выявлено 3 ключевых рисковых зоны: 
1) **Использование заглушки `no-reply@domain` при отсутствии email у покупателя**, что нарушает п. 2 ст. 1.2 54-ФЗ о направлении чека на реальный адрес/телефон покупателя;
2) **Ошибочный порог уплаты НДС 5% на УСН**: в коде установлен порог оборота 20 млн руб. вместо законодательно установленного 60 млн руб. (ФЗ № 176-ФЗ);
3) **Отсутствие передачи фискальных данных при выводах/физических возвратах денежных средств на банковские карты** (если таковые производятся в обход автоматического рефанда ЮKassa).

## 3. Анализ формирования чека в платёжных шлюзах

### 3.1. ЮKassa Receipt API (`YooKassaGateway`)
При создании платежа в `src/services/financial/payment-gateway.service.ts` (строки 68–93) формируется следующий фискальный блок:
```json
{
  "amount": { "value": "100.00", "currency": "RUB" },
  "capture": true,
  "confirmation": { "type": "redirect", "return_url": "..." },
  "description": "Пополнение баланса (Счёт: clx...)",
  "receipt": {
    "customer": { "email": "user@example.com" },
    "items": [{
      "description": "Информационные услуги",
      "quantity": "1.00",
      "amount": { "value": "100.00", "currency": "RUB" },
      "vat_code": 1,
      "payment_mode": "full_prepayment",
      "payment_subject": "service"
    }]
  }
}
```

### 3.2. Robokassa («Робочеки»)
В `RobokassaGateway` (строки 364–383) используется встроенный фискальный механизм Robokassa:
```json
{
  "Receipt": "{\"items\":[{\"name\":\"Информационные услуги\",\"quantity\":1,\"sum\":\"100.00\",\"tax\":\"none\",\"payment_method\":\"full_prepayment\",\"payment_subject\":\"service\"}]}"
}
```

## 4. Детальные находки аудита по 54-ФЗ

### 4.1. Использование фейкового email (`no-reply@domain`) для покупателя
- **Severity**: 🟠 High / P1 (Правовой риск по 54-ФЗ)
- **Ссылка на Закон**: 54-ФЗ, Ст. 1.2, п. 2 (Обязанность передать чек покупателю в электронной форме на предоставленный абонентский номер или адрес электронной почты).
- **Координаты кода**: `src/services/financial/payment-gateway.service.ts:83`
- **Анализ**: 
  Код формирует customer-блок следующим образом:
  ```typescript
  customer: { email: params.email || `no-reply@${supportDomain}` }
  ```
  Если у зарегистрированного пользователя в профиле отсутствует email (например, авторизация через Telegram без почты), система генерирует несуществующий почтовый адрес `no-reply@smmplan.pro`. Чек отправляется в ОФД с этим адресом, но физическое лицо (покупатель) чек не получает.
  Налоговые органы при проверке соблюдения 54-ФЗ интерпретируют систематическую отправку чеков на вымышленные адреса как невыполнение обязанности по отправке чека покупателю (штраф по ч. 6 ст. 14.5 КоАП РФ — предупреждение или 2 000 руб. на должностное лицо, 10 000 руб. на ЮЛ за каждый случай).
- **Рекомендация**: Обязать пользователя указывать e-mail при создании платежа или запрашивать его на форме пополнения счета до перехода в ЮKassa.

---

### 4.2. Некорректный порог оборота для динамического переключения ставки НДС (5%)
- **Severity**: 🟡 Medium / P2 (Фискальная точность)
- **Ссылка на Закон**: НК РФ ст. 346.11, ФЗ от 12.07.2024 № 176-ФЗ (Реформа УСН 2025–2026).
- **Координаты кода**: `src/services/financial/payment-gateway.service.ts:79-80`
- **Анализ**: 
  В коде ЮKassa переключение `vat_code` с `1` (Без НДС) на `7` (НДС 5%) происходит по условию:
  ```typescript
  const isVatThresholdExceeded = annualRevenue >= 2000000000; // 20 млн рублей (в копейках)
  const vatCode = isVatThresholdExceeded ? 7 : 1; // 7 = НДС 5%, 1 = Без НДС
  ```
  Однако по налоговому законодательству РФ порог доходов для уплаты НДС на УСН с 2025 года составляет **60 миллионов рублей в год** (а не 20 миллионов рублей). Из-за ошибки в константе система начнёт преждевременно проставлять НДС 5% в фискальных чеках при достижении 20 млн руб., что создаст расхождения между данными ОФД и налоговыми декларациями по УСН.
- **Рекомендация**: Изменить порог с `2000000000` (20 млн руб) на `6000000000` (60 млн руб) или вынести параметр в настройки администратора.

---

### 4.3. Отсутствие фискализации при физическом возврате средств клиенту на банковскую карту
- **Severity**: 🟠 High / P1 (54-ФЗ Применение ККТ при возврате)
- **Ссылка на Закон**: 54-ФЗ, Ст. 1.1, Ст. 1.2 (Расчёты включают прием и возврат денежных средств).
- **Координаты кода**: `src/services/financial/refund-policy.service.ts`
- **Анализ**: 
  Все автоматические возвраты в системе отменяют заказы и возвращают баланс на внутренний wallet (`WalletOps.refund`). Это не требует ККТ.
  Однако если клиент обращается в техподдержку с заявлением на полный вывод неиспользованного аванса обратно на банковскую карту через ЮKassa (`POST /v3/refunds`), в текущей кодовой базе отсутствует метод отправки запроса возврата в ЮKassa с фискальным чеком «Возврат прихода».
- **Рекомендация**: При реализации ручного или автоматического вывода денег на карту через API ЮKassa передавать фискальный блок `receipt` с признаком `payment_mode: "full_prepayment"`.

## 6. Рекомендации по устранению (Remediation Roadmap)

### Приоритет P1 (Высокий):
1. **Валидация Email при пополнении**: В форме пополнения счета (`top-up.action.ts`) сделать введение/наличие email обязательным условием для карт ЮKassa, исключив генерацию заглушек `no-reply@domain`.
2. **Корректировка порога НДС 60 млн**: В `payment-gateway.service.ts` изменить `annualRevenue >= 2000000000` на `annualRevenue >= 6000000000` (60 млн руб).

### Приоритет P2 (Средний):
3. **Фискализация выводов средств (Refund API)**: При реализации функционала возврата денег из кабинета на банковские карты использовать `POST /v3/refunds` ЮKassa с передачей объекта `receipt` (признак «Возврат прихода»).
