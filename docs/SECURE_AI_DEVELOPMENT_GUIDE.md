# 🛡️ Руководство: Как новичку писать безопасный Enterprise-код с помощью ИИ

> **Главный парадокс разработки с ИИ:**  
> Искусственный интеллект по умолчанию пишет код по принципу «Happy Path» (главное, чтобы фича заработала прямо сейчас). Он обучался на миллионах учебных примеров и туториалов из интернета, где 90% кода лишены проверок прав, транзакций и защиты от атак.  
> Чтобы ИИ писал **Enterprise-безопасный код с первой попытки**, ему нужно задавать жесткие **инварианты (границы)** до написания первой строчки кода.

---

## 🧠 ЧАСТЬ 1. Почему ИИ генерирует уязвимый код (и как это устроено)

1. **Туннельное зрение генерации:**  
   Когда вы просите: *«Сделай кнопку отмены заказа»*, ИИ думает: `Найти заказ по ID -> Поставить статус CANCELED -> Вернуть успех`.  
   Он НЕ думает автоматически:
   - *«А принадлежит ли этот заказ именно этому пользователю?»* (IDOR).
   - *«А что, если пользователь нажмет кнопку 50 раз за 1 секунду?»* (Race Condition).
   - *«А вернулись ли деньги в копейках и зафиксированы ли в аудит-логе?»* (Financial Integrity).

2. **Авторская предвзятость (Author Bias):**  
   Агент, который пишет фичу (Maker), психологически (вероятностно) уверен, что его код идеален. Чтобы найти бреши, нужен **режим Разрушителя / Хакера (Checker / Red Teamer)**.

---

## 🔑 ЧАСТЬ 2. «Золотая формула» промпта для безопасной разработки

Когда вы даете задачу любому ИИ (Antigravity, Cursor, Claude Code, Qwen, ChatGPT), используйте универсальный шаблон из 4 блоков:

```text
[1. ЧТО СДЕЛАТЬ (Бизнес-логика)]
Сделай функцию/экран: <описание того, что нужно пользователю>.

[2. КТО ДЕЛАЕТ И ГДЕ ПРОВЕРЯТЬ (Контекст безопасности)]
- Стек: Next.js 16 (App Router), Prisma, PostgreSQL.
- Пользователь может быть злоумышленником: всё, что приходит с клиента (ID, суммы, статусы, ссылки) — ВСЕГДА враждебно и недоверенно.

[3. ЖЕСТКИЕ ИНВАРИАНТЫ (Security Invariants)]
1. IDOR: Всегда проверяй `where: { id, userId: session.userId }`. Не доверяй ID из аргументов без проверки владельца.
2. ФИНАНСЫ: Любые деньги — строго через WalletOps / транзакции с уровнем Serializable и idempotencyKey. Никаких прямых мутаций balance!
3. RBAC: Все экшены закрой через verifySession() или requireStaffPermission().
4. ВАЛИДАЦИЯ: Все входящие данные валидируй через Zod.
5. ДАННЫЕ: Не возвращай на клиент себестоимость, API-ключи и системные логи.

[4. ДВУХПРОХОДНЫЙ КОНТРОЛЬ (Maker-Checker)]
Сначала напиши код. Затем ПЕРЕД тем, как отдать результат, проведи атаку на свой же код по 5 векторам (IDOR, Race Condition, Injection, Data Leak, Missing Auth) и устрани все найденные бреши.
```

## 🏛️ ЧАСТЬ 3. Шесть фундаментальных правил Enterprise-безопасности (на простом языке)

Вам не нужно быть программистом, чтобы контролировать ИИ. Достаточно знать эти 6 понятий и требовать их соблюдения:

| № | Принцип безопасности | Простыми словами для новичка | Что требовать от ИИ в промпте |
|---|---|---|---|
| 1 | **Trust Boundary (Граница доверия)** | Никогда не верь клиенту/браузеру. Браузер можно взломать через F12 за 2 секунды. | *«Цены, скидки и баланс считай ТОЛЬКО на сервере. С клиента принимай только ID услуги и количество.»* |
| 2 | **IDOR (Защита от чужих ID)** | Если злоумышленник подставит чужой номер заказа в URL, он не должен его увидеть или отменить. | *«В каждом запросе к БД добавляй проверку владельца `userId: session.userId`.»* |
| 3 | **Race Condition & Двойные траты** | Если кликнуть «Оплатить» 10 раз за миллисекунду, деньги должны списаться один раз, а не уйти в минус. | *«Оборачивай операции с деньгами в Serializable транзакцию и используй уникальный idempotencyKey.»* |
| 4 | **Data Minimization (Минимизация данных)** | Не отдавай клиенту лишнее. Если отдаешь список услуг — не прикрепляй к ним себестоимость поставщика. | *«Возвращай на клиент только публичный DTO-объект без полей providerCost, secretKey и markup.»* |
| 5 | **Fail-Closed (Отказ в пользу безопасности)** | Если база зависла, сеть моргнула или произошла ошибка — действие должно отмениться, а не выполниться бесплатно. | *«При любой ошибке делай откат (Rollback) и возвращай понятную ошибку, не раскрывая стек вызовов.»* |
| 6 | **SSRF Guard (Защита от поддельных ссылок)** | Если система парсит ссылку (например, соцсеть клиента или API провайдера), она не должна лезть на внутренние IP сервера. | *«Проверяй внешние URL через ssrfGuard и assertSafeUrl перед отправкой fetch.»* |

## 🔄 ЧАСТЬ 4. Протокол совместной работы двух агентов (Maker + Checker)

Самый мощный способ получения 100% безопасного кода — **разделение ролей**:

```
                  ┌──────────────────────────────┐
                  │ 1. Пользователь (Вы)         │
                  │ Задает цель с инвариантами   │
                  └──────────────┬───────────────┘
                                 │
                                 ▼
                  ┌──────────────────────────────┐
                  │ 2. Maker (Генератор фич)     │
                  │ Пишет код + запускает тесты  │
                  └──────────────┬───────────────┘
                                 │
                                 ▼
                  ┌──────────────────────────────┐
                  │ 3. Checker (Qwen / Red Team) │
                  │ Проводит аудит уязвимостей   │
                  │ Выдает отчет SECURITY_*.md   │
                  └──────────────┬───────────────┘
                                 │
                                 ▼
                  ┌──────────────────────────────┐
                  │ 4. Maker (Ремедиация)        │
                  │ Внедряет патчи и тесты       │
                  │ Build: 0 errors | Types: OK  │
                  └──────────────────────────────┘
```

## 📋 ЧАСТЬ 5. Чек-лист для новичка перед деплоем любой фичи

Просто отправьте этот чек-лист вашему ИИ-ассистенту:

- [ ] 1. **Проверка типов:** `npx tsc --noEmit` выдает ровно 0 ошибок?
- [ ] 2. **Проверка сборки:** `npm run build` проходит успешно?
- [ ] 3. **Проверка Server/Client:** Все `'use server'` стоят на первой строке?
- [ ] 4. **Проверка авторизации:** Защищены ли все Server Actions через `verifySession` или `requireAdmin`?
- [ ] 5. **Проверка финансов:** Есть ли `idempotencyKey` у всех денежных списаний?
- [ ] 6. **Проверка IDOR:** Везде ли есть `where: { userId: session.userId }`?
